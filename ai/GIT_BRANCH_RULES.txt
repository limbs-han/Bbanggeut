# S15P11E201 Git 브랜치 규칙

저장소의 기본 브랜치는 master다.
main이라는 브랜치는 사용하지 않는다.

## 장기 브랜치

- master: 최종 통합 및 Backend 운영 배포 기준
- develop/frontend: Flutter 개발 통합
- develop/backend: Spring Boot 개발 통합
- develop/device: IoT, Raspberry Pi, Jetson, AI 개발 통합

master와 develop 브랜치에는 직접 push하지 않는다.
항상 Merge Request를 사용한다.
master와 develop 브랜치는 삭제하지 않는다.

## 기능 브랜치

Frontend:

feat/frontend/<기능명>

Backend:

feat/backend/<기능명>

IoT, AI, Raspberry Pi, Jetson:

feat/device/<기능명>

Jenkins와 CI/CD:

feat/jenkins-<기능명>

브랜치 이름에 codex, 사용자 이름, 의미 없는 숫자를 사용하지 않는다.

## 기능 개발 시작

Frontend:

git fetch origin --prune
git switch develop/frontend
git pull origin develop/frontend
git switch -c feat/frontend/<기능명>

Backend:

git fetch origin --prune
git switch develop/backend
git pull origin develop/backend
git switch -c feat/backend/<기능명>

Device:

git fetch origin --prune
git switch develop/device
git pull origin develop/device
git switch -c feat/device/<기능명>

기능 브랜치는 반드시 자신의 역할별 develop 브랜치에서 만든다.

## Merge Request 대상

- feat/frontend/* → develop/frontend
- feat/backend/* → develop/backend
- feat/device/* → develop/device
- feat/jenkins-* → 별도 지시가 없다면 master

일반 기능 브랜치를 master에 바로 병합하지 않는다.
다른 역할의 develop 브랜치로 병합하지 않는다.

## CI 확인

Frontend CI:

- flutter pub get
- flutter analyze
- flutter test
- APK와 AAB를 빌드하지 않는다.
- Frontend CD는 존재하지 않는다.

Backend CI:

- Backend 빌드
- 단위 테스트
- PostgreSQL 통합 테스트

Device CI:

- Device Agent 테스트
- AI Python 테스트
- Python 및 Shell 문법 검사

CI가 실패하면 병합하지 않는다.
문제를 수정하고 같은 기능 브랜치에 다시 push한다.

## 병합과 브랜치 삭제

CI가 통과하면 기능 브랜치를 역할별 develop에 병합한다.

Merge Request에서 다음 옵션을 활성화한다.

Delete source branch when merge request is accepted

병합 후 삭제 대상:

- feat/frontend/*
- feat/backend/*
- feat/device/*
- feat/jenkins-*

삭제하면 안 되는 브랜치:

- master
- develop/frontend
- develop/backend
- develop/device

기능 브랜치는 병합 후 남겨 두지 않는다.

## master 반영

배포 또는 최종 통합이 필요할 때 역할별 develop에서 master로
Merge Request를 만든다.

- develop/frontend → master
- develop/backend → master
- develop/device → master

develop에서 master로 병합할 때는 source branch 삭제 옵션을 끈다.

## 배포

Frontend:

- CI까지만 수행한다.
- 실제 기기 실행은 개발자 PC에서 flutter run으로 확인한다.
- APK, AAB, 앱 스토어 자동 배포를 하지 않는다.

Device와 AI:

- CI까지만 수행한다.
- 장치나 EC2에 자동 배포하지 않는다.

Backend:

- master CI가 성공하면 운영 배포 승인 작업이 생성된다.
- 사용자 요청 없이 운영 배포를 승인하지 않는다.
- 필요 없는 배포 작업은 Abort한다.

## LLM 작업 절차

1. git status와 현재 브랜치를 확인한다.
2. git fetch origin --prune을 실행한다.
3. 역할에 맞는 develop에서 기능 브랜치를 만든다.
4. 관련 코드와 테스트를 작성한다.
5. 로컬 검증을 수행한다.
6. 변경 파일과 diff를 확인한다.
7. 기능 브랜치에만 commit과 push를 수행한다.
8. 같은 역할의 develop을 대상으로 MR을 만든다.
9. CI 결과를 확인한다.
10. CI 성공 후에만 병합한다.
11. 병합 후 기능 브랜치를 삭제한다.
12. 사용자 요청 없이 운영 배포를 승인하지 않는다.
13. 각 단계 결과를 한국어로 쉽게 보고한다.
