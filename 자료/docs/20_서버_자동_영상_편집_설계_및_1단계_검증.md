# 서버 자동 영상 편집 설계 및 1단계 검증

작성일: 2026-08-01

## 결정

자동 자르기와 자동 줌 초안은 요청 시 서버에서 실행한다.

모바일 앱은 저해상도 프록시를 재생하고 컷·줌·자막·AR 편집 명령을 조작한다.

최종 MP4는 서버의 한 렌더러가 생성한다.

모바일은 원본 전체 다운로드, Whisper 추론, 최종 MP4 내보내기를 수행하지 않는다.

편집 상태의 원본은 versioned JSON recipe다.

AR은 Banuba를 필수로 사용하지 않는다.

초기 AR은 MediaPipe 얼굴 landmark와 투명 PNG/WebP overlay로 구현한다.

Banuba는 고급 3D·뷰티 효과가 실제 요구될 때만 다시 비교한다.

## 개발 순서

1. STT/VAD/YAMNet/dBFS 기반 적응형 자동 자르기
2. 얼굴 track 기반 자동 줌 인·아웃
3. Flutter recipe 편집 UI와 서버 재렌더

앞 단계의 사람 평가가 실패하면 다음 단계로 진행하지 않는다.

## 1단계 구현

`ai/video_editor`에 다음을 구현했다.

- faster-whisper small/int8 한국어 STT와 단어 타임스탬프
- Silero VAD 발화·비발화 경계
- MediaPipe YAMNet TFLite 웃음·발화·무음·음악·반응 점수
- 0.5초 RMS dBFS, 음량 상승, spectral flux, spectral centroid, zero-crossing rate
- STT/VAD/YAMNet/경량 음향 특징 융합
- 1초 사건 점수 타임라인과 가변 길이 선택
- versioned edit recipe JSON
- 결정론, 경계 우선, fallback, 겹침 오류 단위 테스트

기존 45~65초 방식은 사용자 평가에서 폐기했다.

새 선택기는 영상별 평상시 점수 중앙값을 baseline으로 계산한다.

가장 두드러지는 사건 seed에서 시작해 점수가 유지되는 동안 확장한다.

긴 대화는 강한 발화 공백으로 둘러싸인 이야기 블록으로 확장한다.

공공장소 소음 때문에 Silero VAD가 긴 구간 전체를 발화로 판단할 수 있다.

이 경우 YAMNet `Speech` 점수가 낮고 `Laughter`도 아닌 창을 보조 경계로 사용한다.

로컬 CPU에서 다섯 영상 STT/VAD 전체 처리에 약 115초가 걸렸다.

웃음·음악·반응과 상위 카테고리까지 저장하는 YAMNet v2는 다섯 영상 전체 처리에 약 3.2초가 걸렸다.

경량 음향 특징 다섯 영상 전체 처리에는 약 1초가 걸렸다.

따라서 자르기 분석만을 위해 GPU를 24시간 유지할 필요는 없다.

YAMNet은 LLM 토큰 API를 사용하지 않는다.

## 아직 통과하지 않은 조건

기계 조건은 적응형 v2 기준 다섯 영상 모두 통과했다.

사람이 각 검증본을 `그대로 사용`, `5초 이내 수정`, `5초 초과 수정`, `실패`로 평가해야 한다.

새 v2 검증본에서 최소 4/5개가 `그대로 사용` 또는 `5초 이내 수정`이어야 자동 줌 단계로 진행한다.

단어 오인이 관측되어 자르기용 경계와 별개로 자막 모델 품질 비교가 필요하다.

로컬 다국어 MiniLM 문장 임베딩도 실험했지만, 짧은 감탄사와 STT 오인 문장이 서로 높은 유사도를 보였다. 현재 끝점 결정에는 사용하지 않고 분석 후보로만 남긴다.

## 참고한 구현 패턴

- Google MediaPipe Face Landmarker: 얼굴 landmark, blendshape, 효과용 변환 행렬

- Remotion Lambda: 요청이 있을 때만 렌더 컴퓨팅 실행

## 2026-08-01 영상 정보 v3 조사와 적용

공개 구현을 기준으로 자동 편집의 영상 분석 방식을 다시 비교했다.

- Auto-Editor는 축소한 회색 프레임을 블러 처리한 뒤 이전 프레임과 비교해 움직임 구간을 만든다.
- PySceneDetect ContentDetector는 HSV 색상과 밝기 차이를 사용하고 AdaptiveDetector는 주변 프레임 변화량의 이동 평균과 비교한다.
- Adobe Premiere Auto Reframe은 화면의 동작을 추적해 위치/크기 키프레임을 만들며 영상 특성에 따라 추적 속도를 조절한다.
- MediaPipe Face Detector는 얼굴 bounding box와 주요점을 출력하며 full-range 모델은 약 5m 거리 얼굴을 대상으로 한다.

적용 구현은 `ai/video_editor/video_features.py`다.

- 0.5초 간격으로만 프레임을 읽는다.
- 움직임 계산 프레임은 폭 320px로 축소한다.
- 얼굴 검출 프레임은 폭 640px로 축소하고 BlazeFace full-range를 사용한다.
- 움직임, HSV 내용 변화, 적응형 장면 전환, 밝기, 대비, 선명도를 저장한다.
- 얼굴 수, 가장 큰 얼굴 면적, 화면 중심도, 얼굴 면적 변화를 저장한다.
- 분석 결과는 자르기, 줌, 사용자 편집 UI가 같은 JSON을 재사용한다.

다섯 검증 영상의 CPU 처리시간은 영상당 3.9~4.8초, 평균 4.3초였다.

다섯 영상 모두 얼굴 검출 프레임 비율이 99.2~100%였다.

가장 큰 얼굴의 프레임 면적 중앙값은 영상별 1.2~2.5%였다.

검증 영상은 고정 홈캠의 단일 장면이라 의미 있는 장면 전환은 거의 없었다.

영상 움직임을 하이라이트 주 점수로 사용한 실험에서는 2번 영상의 seed가 58초에서 81초로 잘못 이동했다.

따라서 영상 v3는 다음 역할로 제한했다.

- STT/VAD/YAMNet/dBFS 사건 점수가 하이라이트 seed를 결정한다.
- 영상은 음향 사건이 없는 영상의 약한 fallback으로만 사용한다.
- 심한 노출/흐림 저하 구간은 감점한다.
- 실제 장면 전환은 시작/종료 경계 후보로 사용한다.
- 얼굴 위치/면적/움직임은 2단계 줌 키프레임에서 사용한다.

피크만 남기는 방식은 원인과 결과를 잘라내므로 사건 종류별 흐름 확장을 추가했다.

- 영상 처음부터 끝까지 STT 대화가 이어지고 명확한 단절이 없으면 전체 흐름을 유지한다.
- 중간에 5초 이상 발화 단절이 있으면 seed가 포함된 대화 블록만 유지한다.
- 음악 사건은 음악 피크만 남기지 않는다.
- 음악 사건 이전의 지속 움직임을 원인 행동으로 보고 최대 8초의 잠깐 멈춤을 건너 연결한다.
- 음악 종료 후 움직임이 안정되거나 원본이 끝나는 지점까지 유지한다.
- recipe의 `flowExpansion`에 `dialogue-story` 또는 `music-motion-episode`를 기록한다.

## 2026-08-01 사용자 길이 프리셋과 줌 v4

이 절의 사건 점수 기반 느린 줌은 v5 표정 기반 하드 줌으로 대체했다.

AI가 적정 이야기 길이를 완전히 추론하지 않고 사용자가 `short`, `medium`, `long`을 선택한다.

- `short`: 15~30초
- `medium`: 35~65초
- `long`: 70~120초

분석은 프리셋마다 다시 실행하지 않는다.

동일한 STT/VAD/YAMNet/dBFS/영상 점수 타임라인에서 프리셋 후보만 다시 계산한다.

자동 사건 흐름이 선택 범위 안이면 해당 흐름을 그대로 사용한다.

범위를 초과하면 사건 seed를 반드시 포함하고 앞뒤 문맥을 확보한 후보만 비교한다.

후보 점수는 평균 사건 점수 68%, 시작 경계 14%, 종료 경계 14%, seed 문맥 4%를 사용한다.

줌은 사용자 on/off 값으로 제어한다.

줌 on 처리 규칙은 다음과 같다.

- 얼굴이 검출된 사건 피크만 후보로 사용한다.
- 서로 10초 미만인 후보는 하나만 유지한다.
- 결과 길이 30초당 최대 한 개, 전체 최대 네 개를 사용한다.
- 각 줌은 4초다.
- 얼굴 면적이 3% 미만이면 1.16배, 그 이상이면 1.11배다.
- 얼굴 중심은 주변 3초 검출값의 중앙값으로 고정한다.
- 650ms 동안 줌 인하고 650ms 동안 줌 아웃한다.
- FFmpeg `zoompan`으로 H.264/AAC MP4를 렌더링한다.

지정 검증 설정과 결과는 다음과 같다.

| 영상 | 프리셋 | 선택 구간 | 길이 | 줌 횟수 |
| --- | --- | ---: | ---: | ---: |
| 1 | medium | 0.00~39.00초 | 39.00초 | 1 |
| 2 | medium | 47.00~82.00초 | 35.00초 | 2 |
| 3 | long | 39.02~138.48초 | 99.46초 | 3 |
| 4 | short | 56.72~83.31초 | 26.59초 | 1 |
| 5 | medium | 58.00~120.00초 | 62.00초 | 2 |

다섯 결과 MP4 모두 영상과 오디오 스트림을 포함하며 요청 길이로 재생되는 것을 확인했다.

이 단계는 Python 편집 워커 코어 구현이다.

Spring API, 작업 큐, MinIO 입출력, 작업 상태 저장 연결은 아직 구현하지 않았다.

## 2026-08-02 표정 기반 하드 줌 v5

v4의 사건 피크 기반 650ms 줌 인/아웃은 화면 전환처럼 보여 폐기했다.

줌 on은 줌을 강제하는 값이 아니라 표정 기반 줌을 허용하는 값이다.

표정 피크가 기준보다 낮으면 줌을 생성하지 않는다.

MediaPipe Face Landmarker를 0.25초 간격으로 실행한다.

최대 네 얼굴의 478 landmark와 blendshape를 분석한다.

표정 반응 점수는 다음 신호를 사용한다.

- `mouthSmileLeft`, `mouthSmileRight`
- `eyeSquintLeft`, `eyeSquintRight`
- `jawOpen`
- `eyeWideLeft`, `eyeWideRight`
- `browInnerUp`

여러 얼굴 중 표정 반응 점수가 가장 높은 얼굴을 줌 대상으로 선택한다.

표정 점수는 3개 분석 창으로 평활화하고 최소 0.45 이상인 로컬 피크만 사용한다.

서로 10초 이내인 표정 피크는 가장 강한 하나만 유지한다.

줌 길이는 약 2.25초다.

줌 인/아웃 램프는 사용하지 않고 하드 컷으로 전환한다.

얼굴 높이가 전체 화면 높이의 약 29%가 되도록 배율을 계산한다.

배율은 화질과 과도한 크롭을 막기 위해 1.25~2.20배로 제한한다.

지정 검증본의 결과는 다음과 같다.

| 영상 | 프리셋 | 줌 횟수 | 표정 | 배율 범위 |
| --- | --- | ---: | --- | ---: |
| 1 | medium | 0 | 기준 이상 표정 없음 | - |
| 2 | medium | 1 | smile | 1.25배 |
| 3 | long | 4 | smile | 1.25~1.31배 |
| 4 | short | 1 | smile | 1.25배 |
| 5 | medium | 1 | smile | 1.38배 |

다섯 영상 표정 분석은 로컬 CPU에서 총 51.7초, 영상당 평균 10.3초가 걸렸다.

Google Face Landmarker 결과는 얼굴 landmark와 선택적 face blendshape 목록을 제공한다.

## 2026-08-02 표정·소리 결합 가변 줌 v6

표정만 강하고 소리 반응이 없는 구간은 줌하지 않는다.

표정 분석 창마다 같은 시점의 1초 점수 타임라인에서 다음 소리 신호를 결합한다.

- YAMNet 웃음 점수
- YAMNet 반응음 점수
- dBFS 음량 상승 점수의 80%
- social event 점수
- music event 점수

표정 점수는 영상 내부 중앙값과 피크를 기준으로 동적 임계값을 계산하되 최소 0.40을 요구한다.

소리 점수도 영상 내부 중앙값과 피크를 기준으로 동적 임계값을 계산하되 최소 0.15를 요구한다.

표정과 소리가 둘 다 임계값을 넘은 로컬 피크만 줌 후보가 된다.

최종 줌 후보 점수는 표정 65%, 소리 35%다.

줌 길이는 후보 앞뒤에서 표정과 소리가 각 임계값의 65% 이상 유지되는 구간으로 계산한다.

최소 1.2초, 최대 4초로 제한한다.

결합 반응이 약하면 얼굴 높이 목표는 화면의 34%, 가장 강하면 50%다.

배율은 `목표 얼굴 높이 / 현재 얼굴 높이`로 계산하고 1.20~2.80배로 제한한다.

줌 인/아웃 전환 램프는 사용하지 않는다.

| --- | ---: | --- | --- | --- |
| 1 | 0 | - | - | - |
| 2 | 0 | - | - | - |

## 2026-08-02 모바일·서버 배치 결정

STT 제거 후 모델과 연산은 모바일에서도 실행 가능한 크기다.

로컬 CPU의 2분 영상 분석 시간은 YAMNet 약 0.6초, 음향 약 0.2초, 영상 특징 약 4~5초, 표정 약 9~13초였다.

얼굴 검출 모델은 약 1.03MiB, Face Landmarker는 약 3.58MiB다.

그러나 원본 영상이 이미 MinIO에 있으므로 모바일 분석은 원본 다운로드와 편집본 재업로드를 추가한다.

MVP 배치는 Spring API, PostgreSQL edit job, Python CPU worker, MinIO 입출력으로 한다.

Redis는 기존 인증·상태 용도와 편집 큐를 섞지 않고 PostgreSQL job row와 lease를 작업의 기준 상태로 사용한다.

앱은 길이 프리셋, 줌 on/off, 시작·끝, 줌 구간과 크기를 조작하고 recipe revision을 서버에 보낸다.

서버는 분석 캐시, 후보 생성, 저해상도 preview, 최종 FFmpeg 렌더, 재시도, 진행률과 실패 상태를 담당한다.

MVP는 GPU를 요구하지 않는다.

고사양 모델은 경량 신호로 해결되지 않는 이야기 의미 판단을 실제 사용자 평가에서 개선한다는 증거가 생길 때 선택적 2차 분석기로 추가한다.

서버 편집의 제품 가치는 단순 컷 API가 아니라 여러 후보 제공, 무의미한 영상 감지, 설명 가능한 점수, 사용자 수정 후 재렌더까지 완성될 때 생긴다.

## 2026-08-02 로컬 편집 API와 고정 검증 데이터

앱 편집기를 반복 검증하는 동안에는 별도 클라우드 서버를 추가하지 않고 개발자 PC의 Docker Compose를 사용한다.

- FastAPI `editor-api`는 `127.0.0.1:18080`에서 요청을 받는다.
- Android 실기기는 `adb reverse tcp:18080 tcp:18080`으로 개발 PC API에 접속한다.
- MinIO에는 다섯 원본 영상을 `edit-fixtures/`에, 자동·사용자 recipe를 `edit-projects/<videoId>/`에 저장한다.
- `POST /v1/edit-recommendations`는 촬영 시각으로 고정 검증 영상을 찾아 실제 YAMNet·음향·영상·표정 분석값을 재사용한다.
- 응답 recipe는 추천 시작·끝, 줌 구간, 줌 배율과 초점, 점수 타임라인을 포함한다.
- `PUT /v1/edit-projects/{videoId}`는 사용자가 수정한 recipe revision을 MinIO에 저장한다.

로컬 API 단위 테스트 3개, 자동 자르기·줌 단위 테스트 23개와 Python 문법 검사를 통과했다.

이 API는 고정 다섯 영상에 대한 편집 UI 통합 검증용이다. 임의 영상의 실시간 분석 작업 큐와 최종 서버 렌더는 다음 단계에서 같은 recipe 계약을 유지한 채 교체한다.
