# 서보 비전 진단 대시보드

## 1. 목적

Jetson에서 실행되는 YOLO 자동 구도와 PCA9685 서보 제어 상태를 같은 화면에서
확인하기 위한 개발·보정용 로컬 웹 대시보드다.

이 화면은 일반 사용자용 앱 기능이 아니다. 카메라 영상과 객체 위치가 노출되므로
Jetson과 같은 신뢰할 수 있는 로컬 네트워크에서만 사용한다.

## 2. 접속

디스크 기반 Edge AI 서비스가 실행 중일 때 SSH 로컬 포트 포워딩으로 접속한다.
대시보드는 Jetson의 loopback 주소에만 바인딩되며 LAN에 직접 공개되지 않는다.

```powershell
ssh -N -L 8765:127.0.0.1:8765 ssafy@<JETSON_IP>
```

터널을 실행한 터미널을 유지한 채 같은 PC의 브라우저에서 연다.

```text
http://localhost:8765
```

`/etc/william-james/device-agent.env`에서 포트와 영상 품질을 변경할 수 있다.

```text
SERVO_DASHBOARD_HOST=127.0.0.1
SERVO_DASHBOARD_PORT=8765
SERVO_DASHBOARD_FRAME_WIDTH=960
SERVO_DASHBOARD_JPEG_QUALITY=72
SERVO_DASHBOARD_FRAME_INTERVAL_SECONDS=0.2
```

`SERVO_DASHBOARD_PORT=0`이면 대시보드를 열지 않는다.

## 3. 화면에 표시되는 값

### 카메라

- YOLO가 검출한 사람·고양이·강아지 바운딩 박스
- 선택된 추적 객체 ID와 그룹 영역
- 화면의 고정 중앙점
- 선택 객체들의 원본 중심과 EMA 평활화 추적점
- 화면 중앙에서 객체 추적점으로 향하는 오차 벡터
- 중앙 데드존과 안전 여백

대시보드 영상은 YOLO가 이미 만든 주석 프레임을 JPEG로 변환한다. 대시보드가
카메라 또는 RTSP 스트림을 별도로 열지 않으므로 기존 AI 캡처와 충돌하지 않는다.

사람 전신 박스의 정중앙은 화면 중앙과 겹치기 쉬워 세로 명령이 거의 발생하지
않는다. 기본 세로 추적점은 객체 박스의 위에서 35% 지점이며
`YOLO_SUBJECT_Y_RATIO`로 조정한다. `0`은 박스 위쪽, `0.5`는 기존 정중앙,
`1`은 박스 아래쪽이다.

```text
YOLO_SUBJECT_Y_RATIO=0.35
YOLO_DEADZONE_WIDTH=0.08
YOLO_DEADZONE_HEIGHT=0.06
YOLO_TRACKING_MODE=safe-frame
YOLO_SAFE_FRAME_START_MARGIN=0.08
YOLO_SAFE_FRAME_STOP_MARGIN=0.12
YOLO_SAFE_FRAME_EDGE_GUARD=0.04
YOLO_TARGET_LOSS_FOLLOW_SECONDS=0.5
```

운영 기본 추적 방식은 `safe-frame`이다. 감지된 각 사람마다 가로는 사람 박스 중앙,
세로는 박스 상단에서 `YOLO_SUBJECT_Y_RATIO`만큼 내려온 추적점을 계산한다. 기본값
0.35는 기존 얼굴·상반신 추적에 사용하던 35% 지점이다. 안정화된 사람 전원을
포함하며, 모든 사람의 추적점이 화면의 8%~92% 안전 영역 안에 있을 때만 중앙에
맞추지 않고 해당 축을 `HOLD`한다. 이동을 시작한 뒤에는 모든 점이 12%~88% 영역에
들어와야 멈추므로 경계에서의 반복 이동을 줄인다.

한 사람의 점이라도 왼쪽·오른쪽·위·아래 경계를 벗어나면 그 방향으로 이동한다.
서로 다른 사람의 점이 같은 축의 양쪽 경계를 동시에 벗어나 팬·틸트만으로 모두
포함할 수 없으면 해당 축을 계속 끝단으로 밀지 않고 `HOLD`한다.

추적점이 안전 영역 안에 있어도 전체 person 박스가 화면 가장자리 4% 영역에 닿으면
사람 이탈을 막기 위해 해당 축을 안쪽으로 움직인다. 박스가 양쪽 가장자리에 동시에
닿아 팬·틸트만으로 해결할 수 없는 축은 계속 끝단으로 밀지 않고 정지한다.

가장자리에서 사람이 감지되지 않으면 마지막 이탈 방향을 최대 0.5초 동안만
`TARGET_LOSS_FOLLOW` 상태로 유지한다. 이후 5초까지는 `NO_TARGET_HOLD`, 5초가
지나면 `RETURN_HOME`으로 전환한다. 중앙에서 confidence만 잠깐 떨어진 경우에는
마지막 박스가 가장자리 근처가 아니므로 예측 이동 없이 즉시 `NO_TARGET_HOLD`한다.

대시보드에서 빨간색 선은 person 박스 이탈 방지 경계, 주황색 선은 추적점 이동 시작
경계, 청록색 선은 이동 정지 경계다. 각 사람 위의 자홍색 십자는 실제 제어에
사용하는 개별 35% 추적점이다.

기존 중앙점 추적이 필요한 경우에는 `YOLO_TRACKING_MODE=center`로 되돌릴 수 있다.
`YOLO_SUBJECT_Y_RATIO`는 두 모드 모두에서 세로 추적점을 결정한다.
`YOLO_DEADZONE_WIDTH`와 `YOLO_DEADZONE_HEIGHT`는 `center` 모드에서만 사용한다.

데드존은 화면 중앙에서 작은 흔들림을 무시하는 영역이다. 값이 작을수록 서보가
민감하게 반응하지만 검출 좌표의 미세한 변화에도 모터가 떨릴 수 있다.

그룹 선택용 여백은 `--edge-margin` 실행 인자(기본 0.10, 0~0.45 제한)로 정한다.
서보 이동 시작·정지 경계인 `YOLO_SAFE_FRAME_START_MARGIN`과
`YOLO_SAFE_FRAME_STOP_MARGIN`과는 별개의 값이다.

팬과 틸트의 논리 HOME은 각각 `0°`이며 두 축 모두 아래 범위로 제한한다.
추적 명령이 범위를 벗어나더라도 서보 컨트롤러가 경계값에서 더 움직이지 않는다.

```text
SERVO_PAN_MIN_DEG=-90
SERVO_PAN_MAX_DEG=90
SERVO_TILT_MIN_DEG=0
SERVO_TILT_MAX_DEG=110
SERVO_PAN_PARK_DEG=0
SERVO_TILT_PARK_DEG=0
```

TILT에 음수 구간이 없는 것은 `0°`가 곧 짐벌의 기계적 스톱이고 거기서 앞으로만
숙일 수 있기 때문이다. 객체가 5초 이상 감지되지 않아 `RETURN_HOME` 상태가 되면
두 축 모두 `0°` PARK 위치로 복귀한다. 대시보드와 상태 토픽에 표시되는 상태
이름은 `HOME`이지만 **실제 이동 지점은 PARK다.**

`SERVO_*_HOME_PULSE_US`는 논리 `0°`가 어느 물리 위치인가를 고정한다. PAN
`1500us`는 카메라 정면, TILT `611us`는 짐벌 정지 위치다. 환산율
`11.1111us/°`에서 `495~2505us`가 물리 180°를 덮으므로 대시보드에 보이는 논리
각도가 곧 물리 각도다.

### 전원 재인가 시 안전 시작

기본값 `SERVO_STARTUP_POSITION=park`에서는 기동 시 저장 파일을 무시하고 PARK
각도(두 축 모두 `0°`)를 첫 PWM으로 출력한다. 무전원 상태의 서보가 실제로
쉬는 각도가 PARK이므로 전원이 들어오는 순간 움직일 이유가 없다. 실제 위치와
무관하게 HOME `0°`를 먼저 출력하던 기존 급회전을 이렇게 없앤다.

`SERVO_STARTUP_POSITION=persisted`로 바꾸면 컨트롤러가 마지막으로 출력한
PAN/TILT 각도를 0.25초 간격으로 원자 저장하고, 재시작 후 저장된 각도를 첫
PWM으로 그대로 복원한 뒤 다음 제어 주기부터 속도 제한을 적용한다. 서보 전원을
한 번도 끊지 않는 운용에서만 쓴다.

```text
SERVO_STARTUP_POSITION=park
SERVO_START_ARMED=true
SERVO_STATE_FILE=/var/lib/william-james-servo/position.json
SERVO_STATE_MAX_AGE_SECONDS=604800
SERVO_STATE_SAVE_INTERVAL_SECONDS=0.25
SERVO_SHUTDOWN_HOME_TIMEOUT_SECONDS=3
```

상태 파일 복원과 `STARTUP_WAITING` 판정은 `SERVO_ENABLE_HARDWARE=true`일 때만
동작한다. 기본값 `false`(DRY-RUN)에서는 초기 상태가 `HOLD`이며 `STARTUP_WAITING`은
표시되지 않는다.

`persisted` 모드에서 상태 파일이 없거나, 7일보다 오래됐거나, 값이 각도 제한
밖이거나, `schema_version`·`device_id`가 현재 장치와 다르거나, JSON 파싱에
실패하거나, 저장 시각이 5분(300초) 이상 미래이면 파일을 거부하고 대시보드 서보
상태가 `STARTUP_WAITING`으로 표시되며 PWM 출력은 비활성 상태를 유지한다. 이때는
`SIGUSR1`을 보내도 무장을 거부한다. 컨트롤러가 실제 각도를 모르기 때문이다.

정상 종료 시에는 최대 7초 동안 속도 제한을 지키며 PARK 위치(두 축 모두 `0°`)로
이동하고 최종 위치를 저장한 뒤 출력을 끈다. 최악의 복귀는 TILT `+110°`에서
5.5초이므로 7초 안에 끝난다. 속도나 각도 범위를 바꾸면 이 값과 systemd
`TimeoutStopSec`(12초)을 다시 계산해야 한다.

### 추적 판단

- `TRACKING`, `NO_TARGET_HOLD`, `RETURN_HOME` 상태(비전 상태 원문 그대로 표시)
- `LEFT`, `RIGHT`, `UP`, `DOWN` 축별 명령
- 화면과 객체 중심의 픽셀 좌표
- 정규화 중심 좌표와 `error_x`, `error_y`

검출 객체별 클래스·추적 ID·신뢰도·정규화 바운딩 박스는 화면 패널에는 그리지
않고 `/api/state`의 `vision.objects`와 `servo_dashboard.jsonl` 로그에만 기록된다.

`MOVEMENT TIMELINE` 패널은 PAN/TILT 각도와 오차 변화를 시간축 차트로 보여준다.

### 서보

- PAN/TILT 현재 논리 각도와 목표 각도
- 현재 위치와 목표 위치의 차이
- 설정된 최소·최대 안전 각도
- 현재 각도에 대응하는 PWM 펄스 폭
- 실제 PCA9685 출력 여부
- 수신·거부 메시지 수와 타임아웃 HOLD 횟수

`DRY-RUN`이면 각도 계산과 MQTT 상태는 정상적으로 보이지만 실제 모터에는 PWM을
출력하지 않는다.

### 직접 담기 버튼

카메라 화면 아래 버튼 두 개로 원하는 순간을 직접 웃음 영상으로 담을 수 있다.

| 버튼 | 동작 |
| --- | --- |
| `2분 담기` | 누른 순간부터 2분을 담는다. 한 번만 누르면 된다. |
| `녹화 시작` / `녹화 종료` | 시작을 누른 순간부터 종료를 누를 때까지 담는다. |

두 버튼 모두 누르기 **1초 전**부터 담는다. 사람이 무언가를 보고 손을 뻗기까지
걸리는 시간이 있어서, 그 1초에 정작 담고 싶은 장면의 시작이 들어 있다.

담기는 감지와 똑같은 `*.trigger.json`을 남긴다. 클립 생성·업로드·앱 알림은
웃음 감지와 완전히 같은 경로를 탄다. 앱에는 `웃음 영상이 도착했어요`로 온다.

알아둘 것이 네 가지 있다.

- **영상은 즉시 오지 않는다.** 담기가 끝난 시각을 포함한 녹화 세그먼트가
  완결돼야 잘라낼 수 있어서, 대개 1분쯤 뒤에 앱에 도착한다.
- **종료를 누르지 않으면 10분에서 자동 종료된다.** 상한이 없으면 잊어버린
  세션이 끝없이 길어지고, 업로드 경로에는 크기 제한이 없다.
- **5초보다 짧게 눌러도 5초로 담는다.** 두 번 연달아 누르면 길이가 0이 되어
  업로더가 거부한다.
- **대시보드가 재시작되면 진행 중인 담기는 사라진다.** 시작 시각을 메모리에만
  두기 때문이다. 다시 시작을 누르면 된다.

담기로 만든 영상은 근처에서 박수가 감지돼도 **합쳐지지 않는다.** 사람이 한
순간을 지목한 것이므로 구간이 밀리거나 제목이 `웃음과 박수가 함께 담긴 순간`으로
바뀌면 안 되기 때문이다. 감지로 잡힌 웃음과 박수는 종전대로 합쳐진다.

`EVENT_DIR`가 지정되지 않은 구성에서는 트리거를 쓸 곳이 없으므로 버튼이 아예
표시되지 않는다.

### 웃음 감지와 영상 업로드

- YAMNet의 현재 최상위 소리, 실시간 웃음 점수, 판정 기준, 입력 RMS
- 연속 양성 판정 횟수와 추론 시간
- YAMNet이 로컬 Mosquitto의
  `homecam/v2/{device_id}/ai/laughter/detected`로 보낸 감지 신호
- 감지 시각, 점수, 클래스, 이벤트 ID
- 녹화 세그먼트 대기·클립 생성·업로드 URL 요청·스토리지 전송·완료 처리 단계
- 재시도 횟수와 대기 시간, HTTP 상태, 차단 사유, 완료된 영상 ID

운영 스크립트는 YAMNet을 외부 MQTT에 직접 연결하지 않고
`LOCAL_MQTT_HOST`/`LOCAL_MQTT_PORT`의 로컬 Mosquitto에만 연결한다. 감지 신호의
이벤트 ID는 로컬 `*.trigger.json`의 이벤트 ID와 같으므로 이후 업로드 상태를 한
흐름으로 추적할 수 있다.

운영 스크립트는 YAMNet을 단독으로 먼저 시작하고 첫 추론을 기다리는 동안 다른 AI
프로세스와의 초기 자원 경합을 줄인다. 프로덕션 RTSP 경로에서는 사용하지 않는
`sounddevice`/PortAudio를 불러오지 않는다. 모델·RTSP 오디오·첫 추론까지 실제로
성공했는지를 readiness 기준으로 사용하며, 제한 시간은 wall-clock 시각으로 계산한다.
readiness는 상태 관측용이며 전체 Edge AI 서비스의 성공·실패를 결정하는 치명적
게이트가 아니다. 기본 대기 시간은 90초이며 필요하면 다음 값으로 조정한다.

```text
YAMNET_READY_TIMEOUT_SECONDS=90
YAMNET_RESTART_DELAY_SECONDS=5
```

제한 시간 안에 첫 추론이 기록되지 않으면 마지막 YAMNet 로그를 journal에 출력하고
`UNAVAILABLE` 상태를 기록한 뒤, 살아 있는 YAMNet은 백그라운드에서 준비를 계속한다.
업로더, 선택적 호출어 감지기, YOLO와 대시보드는 degraded 모드로 정상 시작한다.
YAMNet 프로세스가 실제로 종료되면 다른 프로세스를 종료하지 않고 기본 5초 뒤
YAMNet만 재시작한다. 대시보드의 `YAMNet 상태`에는 `STARTING`, `UNAVAILABLE`,
`RESTARTING`, `READY`가 표시되며, 사용할 수 없는 동안 이전 실시간 점수는 숨긴다.
정상 추론 JSONL이 다시 들어오면 자동으로 `READY`와 최신 점수로 복구된다.

Edge AI 서비스 전체 종료 시에는 SIGINT, SIGTERM, SIGKILL 순으로 제한 시간을 두고
승격하므로 네이티브 라이브러리 안에서 멈춘 자식 프로세스 때문에 systemd 재시작이
무기한 막히지 않는다. 웃음 판정값의 스크립트 기본은 `mean / 0.125 / 3회`이지만,
Jetson 배포 env(`device-agent.jetson.env.example`)가 `0.05 / 2회`로 덮어쓴다 —
실행 스크립트가 기본값을 대입하기 전에 env 파일을 읽으므로 실제 적용값은 env
쪽이다.

## 4. 로그

화면 하단에는 최근 비전 판단, 서보 상태, 웃음 감지와 영상 업로드 상태가 최신
항목이 위로 오는 역순으로 표시된다. 화면에는 최근 80건만 그리고 서버는 240건을
보관한다. `일시정지` 버튼으로 갱신을 멈출 수 있고, `JSON 저장` 버튼은 브라우저가
받은 스냅샷 전체(최대 240건)를 내려받는다.

Jetson에도 실행 단위 JSON Lines 로그를 남긴다.

```text
~/ai_events/logs/<실행시각>/servo_dashboard.jsonl
```

각 레코드에는 기록 시각, 소스(`vision`, `servo`, `laughter`), 객체 중심·오차,
검출 객체 목록, PAN/TILT 현재·목표 각도와 하드웨어 출력 여부가 포함된다. 웃음
레코드에는 이벤트 ID, 점수, 업로드 상태, 재시도 정보, HTTP 상태와 영상 ID가
포함된다.

업로더는 이벤트 폴더에 `<eventId>.upload-status.json`을 원자적으로 갱신한다.
최종 상태가 `UPLOADED`이면 정상 완료, `RETRYING`이면 일시 오류로 재시도 중,
`BLOCKED`이면 인증·검증·충돌 같은 영구 오류이므로 `detail`과 `httpStatus`를
확인해야 한다. 60초 전후 영상을 만드는 기본 설정에서는 감지 후 녹화 세그먼트가
완결될 때까지 약 1~2분간 `WAITING_RECORDING`으로 보일 수 있다. 그 사이의
`BUILDING_CLIP`, `REQUESTING_UPLOAD`, `UPLOADING`, `COMPLETING`은 정상 진행
중의 중간 단계이며 오류가 아니다. 인접 웃음 이벤트와 하나로 병합된 클립은
대시보드에 `MERGED`로 표시된다.

기존 상세 자동 구도 명령은 같은 실행 폴더의 `autoframe_commands.jsonl`에
계속 기록된다.

### 이벤트 저장 공간 정리

`wj-event-prune.timer`는 10분마다 `~/ai_events`를 정리한다. 기본 보존기간은
영구 업로드 실패 묶음 3일, 일반 이벤트 묶음 7일, 실행·진단 로그 3일이다.
이벤트 전체 사용량이 2GiB를 넘거나 파일시스템 여유 공간이 4GiB 아래로 내려가면
보존기간 전이라도 다음 우선순위로 오래된 항목부터 삭제한다.

1. `<eventId>.upload-blocked.json`이 있는 영구 실패 이벤트 묶음
2. 업로드 또는 병합 완료 이벤트 묶음
3. `logs/`, `diagnostics/`의 오래된 실행 기록
4. 아직 완료되지 않은 이벤트 묶음

최근 15분 안에 변경된 파일과 디렉터리는 현재 생성·업로드 중인 것으로 보고
삭제하지 않는다. 정리기는 `~/ai_events/.william-james-events` 안전 마커가 없으면
실행을 거부한다. 녹화 정리 서비스는 이벤트 정리 서비스를 먼저 실행하므로 디스크
압박 시 영구 실패 클립이 오래된 순환 녹화 세그먼트보다 먼저 공간을 양보한다.

설정값은 `/etc/william-james/device-agent.env`에서 변경한다.

```text
EVENT_BLOCKED_RETENTION_DAYS=3
EVENT_RETENTION_DAYS=7
EVENT_LOG_RETENTION_DAYS=3
EVENT_MAX_GIB=2
EVENT_MIN_FREE_GIB=4
EVENT_ACTIVE_GRACE_MINUTES=15
```

실시간 YAMNet 진단값은 같은 실행 폴더에 별도 JSON Lines로 기록된다.

```text
~/ai_events/logs/<실행시각>/yamnet_diagnostics.jsonl
```

각 행에는 관측 시각, 최상위 소리와 점수, 웃음 max·mean·p90 점수, 현재 선택
점수, 판정 기준, 연속 횟수, RMS와 추론 시간이 포함된다. 대시보드는 이 파일을
tail하여 최신 값을 표시하므로 MQTT 웃음 이벤트가 발생하지 않아도 모델이 실제로
소리를 분석 중인지 확인할 수 있다.

```bash
curl http://127.0.0.1:8765/api/state
```

정상적인 `/healthz` 응답 예시는 다음과 같다.

```json
  "servo_available": true,
```

`yamnet_status`는 `READY`/`STARTING`/`UNAVAILABLE`/`RESTARTING` 중 하나다.

## 6. 문제 해결

### 페이지에 접속되지 않음

1. `wj-edge-ai-recording.service` 상태를 확인한다.
2. 서비스 로그에서 `Servo dashboard: http://127.0.0.1:8765`를 확인한다.
3. SSH 터널 프로세스가 종료되지 않고 실행 중인지 확인한다.
4. PC의 8765 포트를 다른 프로그램이 사용 중이지 않은지 확인한다.
5. `SERVO_DASHBOARD_PORT`가 `0`이 아닌지 확인한다.

### 영상은 보이지만 서보 값이 없음

1. `wj-servo-controller.service`가 실행 중인지 확인한다.
2. 로컬 Mosquitto가 실행 중인지 확인한다.
3. 두 프로세스의 `DEVICE_ID`가 같은지 확인한다.
4. `homecam/v2/{device_id}/control/framing/status` 메시지를 확인한다.

### 웃음은 감지됐지만 영상이 올라오지 않음

1. 대시보드의 `LAUGHTER PIPELINE` 상태와 로그의 `detail`을 확인한다.
2. `WAITING_RECORDING`은 오류가 아니다. 기본 60초 후구간과 현재 세그먼트 완료를
   기다린다.
3. `RETRYING`이면 네트워크·백엔드·스토리지의 일시 오류이며 표시된 시간 후 다시
   시도한다.
4. `BLOCKED`이면 `~/ai_events/<eventId>.upload-blocked.json`과
   `<eventId>.upload-status.json`의 HTTP 상태·응답 내용을 확인한다.
5. 감지 자체가 표시되지 않으면 로컬 Mosquitto와
   `homecam/v2/{device_id}/ai/laughter/detected` 토픽, YAMNet 로그를 확인한다.

### 실시간 웃음 점수와 RMS가 표시되지 않음

1. `~/ai_events/logs/<실행시각>/yamnet_diagnostics.jsonl`이 생성되고 크기가
   증가하는지 확인한다.
2. 서비스 로그에서 `YAMNet ready: first inference telemetry received`를
   확인한다.
3. `YAMNet readiness timed out`이면 로컬
   `rtsp://127.0.0.1:8554/homecam/ai`의 오디오와 YAMNet 모델 로딩 상태를
   확인한다.
4. 다음 명령으로 마지막 startup 단계를 확인한다.

   ```bash
   sudo journalctl -u wj-edge-ai-recording --since "3 minutes ago" \
     --no-pager | grep '\[startup '
   ```

   `importing sounddevice`, `importing tensorflow`, `hub.load(...) starting`,
   `opening audio input` 중 마지막으로 출력된 줄이 정지 구간을 나타낸다.
5. readiness가 성공했는데 화면만 비어 있으면 `/api/state`의 `yamnet` 필드를
   확인한다.

### 영상 갱신이 장치에 부담을 줌

`SERVO_DASHBOARD_FRAME_INTERVAL_SECONDS`를 `0.5`로 높이거나
`SERVO_DASHBOARD_FRAME_WIDTH`를 `640`으로 낮춘다. JPEG 품질은 30~95 범위에서
조정한다.

## 7. 주의 사항

- 이 대시보드는 인증 기능이 없으므로 인터넷에 포트를 공개하지 않는다.
- 실제 모터 출력 활성화는 대시보드와 별개다.
- `SERVO_ENABLE_HARDWARE=true` 전환 전에는 별도 5V 전원, 공통 GND, I2C 주소,
  기구물 안전 범위를 먼저 확인한다.
- 비상 상황에서는 소프트웨어보다 외부 서보 전원을 먼저 차단한다.

## 8. 관련 진단 도구

같은 데이터를 다른 각도에서 보는 도구가 두 가지 더 있다.

- **WJ Edge Observatory**(`ai/model_benchmark_dashboard/`): YAMNet 진단
  JSONL·YOLO 로그·tegrastats를 읽는 별도 진단 대시보드다. Node/pnpm 기반이며
  개발 서버는 `:3000`, Jetson 쪽 수집기는 `:18765`를 쓴다 — `8765`는 이 서보
  대시보드가 사용하므로 피한다.
- **비전 벤치마크 러너**(`ai/model_benchmark/vision_benchmark_runner.py`):
  manifest 기반 데이터셋으로 로컬 YOLO를 돌려 `summary.json`/`progress.json`을
  남긴다. 이 산출물이 Edge Observatory의 모델 비교 표를 채운다.
- **비전 정확도 러너**(`ai/model_benchmark/vision_accuracy_runner.py`): YOLO 형식의
  정답 박스가 있는 동일 프레임 데이터셋으로 모델별 정확도를 계산한다.
- 표준 정확도는 낮은 confidence 후보를 포함한 `mAP50`과 `mAP50-95`로 기록한다.
- 운영 정확도는 confidence `0.25`, 매칭 IoU `0.5`에서 Precision·Recall·F1으로
  기록한다.
- 시나리오별 TP·FP·FN과 대표 실패 프레임을 남겨 전체 평균 뒤에 숨은 실패를
  확인한다.
- 모델 파일과 데이터셋의 SHA-256을 남겨 같은 입력으로 비교했는지 확인한다.
- `run_yolo_accuracy_comparison.sh`는 YOLOv8n·YOLO11n·YOLO26n을 같은 설정으로
  순차 실행한다.
- 기본 비교는 모델별 3회 반복한다.
- 회차마다 시작 모델을 바꿔 열·캐시·실행 순서 편향을 줄인다.
- 각 결과에는 비교 ID, 회차와 실제 실행 순서를 기록한다.
- 정확도 비교 중에는 운영 `wj-edge-ai-recording`을 동시에 실행하지 않는다.
- 기본 서비스 게이트는 FPS 20 이상이다.
- 기본 서비스 게이트는 wall-clock P95 지연 50ms 이하이다.
- 기본 서비스 게이트는 운영 Recall 0.90 이상이다.
- 기본 서비스 게이트는 최고 `mAP50-95`와의 차이 0.02 이하이다.
- 네 게이트를 모두 통과한 후보 중 FPS가 가장 높은 모델을 우선 후보로 표시한다.
- 기본 게이트와 대시보드 추천은 잠정 기준이며 최종 모델 선정은 실제 Jetson
  측정 결과와 실패 사례 검토 후 확정한다.

## 9. 운영 YOLO 런타임 선택과 롤백

`run_edge_ai_recording.sh`는 YOLOv8n 모델 계열을 유지하면서 실행 형식만
PyTorch `.pt` 또는 Jetson에서 빌드한 TensorRT FP16 `.engine`으로 선택한다.
TensorRT 엔진 파일은 JetPack·TensorRT 버전과 GPU에 종속되므로 Git에 커밋하지
않고 Jetson의 `/home/ssafy/ai_models/yolo-detect-engine`에 보관한다.

`/etc/william-james/device-agent.env`에서 다음 값을 설정한다.

```text
YOLO_RUNTIME=auto
YOLO_TENSORRT_ENGINE_PATH=/home/ssafy/ai_models/yolo-detect-engine/yolov8n-fp16-b1-640.engine
YOLO_TENSORRT_ENGINE_SHA256=<검증한 엔진 SHA-256>
YOLO_PYTORCH_MODEL_PATH=/home/ssafy/ai/yolo/yolov8n.pt
YOLO_TENSORRT_PROBE=true
YOLO_TENSORRT_PROBE_DEVICE=0
```

런타임 모드의 의미는 다음과 같다.

- `auto`: 엔진 파일·선택적 SHA-256·실제 640 입력 추론을 점검한 뒤 TensorRT를
  사용한다. 점검에 실패하면 이유를 로그에 남기고 PyTorch 모델로 시작한다.
- `tensorrt`: TensorRT를 엄격하게 검증한다. 점검 실패를 PyTorch로 숨기지 않고
  서비스를 실패시켜 전환 시험에서 오류를 바로 확인한다.
- `pytorch`: TensorRT를 건너뛰고 기존 `yolov8n.pt`로 즉시 롤백한다.

서비스를 시작할 때 `yolo_runtime_selection.tsv`가 해당 실행 로그 디렉터리에
남는다. 저널과 `yolo.log`에는 선택된 모델 형식이 각각 아래처럼 표시된다.

```text
YOLO runtime: requested=auto selected=tensorrt model=...engine
[YOLO] Model runtime: TensorRT
```

운영 전환은 먼저 `YOLO_RUNTIME=tensorrt`로 엄격 검증한 뒤 수행한다. 같은 RTSP
입력에서 ByteTrack 추적, 그룹 중심 선택, MQTT 프레이밍 명령, 서보 이동과 HOME
복귀를 확인한다. 이어서 Live View 영상·음성, 1분 순환 녹화, 실제 이벤트 감지와
약 2분 클립 업로드, 서비스 재시작 수를 확인한다. 30분 이상 연속 실행에서 오류가
없을 때 `auto`를 운영값으로 사용한다.

엔진 자체 문제로 복귀해야 할 때는 코드나 엔진을 삭제하지 않고
`YOLO_RUNTIME=pytorch`로 바꾼 뒤 `wj-edge-ai-recording`만 재시작한다. 녹화와
Device Agent는 별도 서비스이므로 함께 중지하지 않는다.
