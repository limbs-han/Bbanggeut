# 오디오 이벤트 감지 요구사항과 파라미터 튜닝 결정

## 1. 문서 목적

이 문서는 YAMNet, EfficientAT MN10, PANNs CNN10 비교 결과를 검토한 뒤
웃음·박수 이벤트의 실제 서비스 요구사항과 후속 튜닝 방향을 합의한 기록이다.
단순히 “F1이 높은 모델을 선택한다”는 결론을 남기지 않고, 어떤 이벤트를 반드시
감지해야 하는지, 어떤 소리를 오탐으로 보는지, 현재 데이터로 무엇까지 판단할 수
있는지를 구분한다.

관련 비교 결과는
[`32_웃음_박수_탐지_모델_비교_결과.md`](./32_웃음_박수_탐지_모델_비교_결과.md)에
정리돼 있다.

## 2. 합의한 서비스 요구사항

### 2.1 감지 대상

다음 소리는 사람이 카메라 화면 안에 있는지와 관계없이 감지 대상이다.

- 실제 사람의 분명한 웃음
- 실제 사람의 작은 웃음과 `Chuckle`
- 아기와 어린이의 웃음
- 여러 사람이 동시에 웃는 소리
- 실제 사람이 치는 연속 박수
- 실제 사람의 웃음과 연속 박수가 함께 발생한 상황

화면 밖의 사람도 감지 대상이므로 사람 검출 여부를 오디오 이벤트 생성의 필수
조건으로 사용하지 않는다. 영상에 사람이 없다는 이유로 웃음·박수 이벤트를
억제하면 요구사항에 맞지 않는다.

### 2.2 감지하지 않을 대상

다음 소리는 이벤트를 만들지 않아야 한다.

- TV에서 재생되는 웃음과 박수
- 휴대전화와 다른 스피커에서 재생되는 웃음과 박수
- 일반 대화
- 음악과 일반 TV 소리
- 문 닫기, 물체 충돌과 같은 단발 충격음
- 키보드, 의자, 발걸음과 같은 생활 소음

YAMNet과 EfficientAT 같은 범용 음향 분류 모델은 소리가 웃음처럼 들리는지는
판단하지만 실제 사람과 스피커 중 어느 쪽에서 발생했는지를 직접 판별하지 않는다.
따라서 재생 웃음·박수 억제는 임계값만으로 해결된다고 가정하지 않는다.

### 2.3 거리와 하드웨어

- 카메라와 사람은 벽이나 문이 없는 같은 공간에 있다.
- 현재 하드웨어는 Logitech BRIO 100의 내장 모노 마이크로 고정한다.
- 서비스가 고려하는 최대 거리는 약 10m다.
- 거리마다 임계값을 다르게 적용하지 않는다.
- 웃음 임계값 하나와 박수 임계값 하나를 모든 거리에서 공통으로 사용한다.

Logitech이 공개한 BRIO 100 내장 마이크 범위는 최대 1.22m다. 10m는 공식 범위
밖이므로 필수 성능이 이미 입증된 거리로 표현하지 않고 하드웨어 한계까지 확인하는
스트레스 조건으로 기록한다.

공식 사양:
<https://support.logi.com/hc/en-au/articles/16131342728471-Specification-Brio-100-Webcam>

BRIO 100에서 성능이 좋으면 제한된 입력에서도 모델이 견고하다는 근거가 될 수
있다. 그러나 이후 더 좋은 마이크를 연결하면 감도, 게인, AGC, 주파수 응답과
주변 소음 수집 범위가 달라진다. 실제 이벤트와 재생음이 함께 더 선명해질 수
있으므로 기존 임계값이 그대로 유효하다고 단정하지 않고 마이크 교체 시 다시
검증한다.

## 3. 평가 우선순위

실제 웃음·박수를 놓치는 거짓 음성(False Negative, FN), 즉 미탐의 비용이
오탐보다 크다.
따라서 Recall을 핵심 지표로 사용한다. 다만 모든 소리를 이벤트로 예측하면
Recall 1.0을 만들 수 있으므로 Recall만 단독으로 최대화하지 않는다.

다음 원칙으로 임계값을 비교한다.

1. 모델과 이벤트별로 validation의 모든 임계값 후보를 평가한다.
2. 웃음과 박수의 Recall을 각각 계산한다.
3. Recall이 높은 후보 사이에서 거짓 이벤트 수가 적은 후보를 비교한다.
4. Precision, F1, F2와 시간당 거짓 이벤트를 함께 공개한다.
5. 하나의 종합 점수로 숨기지 않고 Recall과 오탐의 Pareto 후보를 남긴다.
6. 선택한 웃음·박수 임계값은 거리와 관계없이 고정한다.

F1은 Precision과 Recall을 같은 비중으로 결합하므로 서비스 우선순위를 완전히
표현하지 못한다. F2는 Recall에 더 큰 비중을 두므로 보조 지표로 추가하되, F2
하나만으로 임계값을 자동 확정하지 않는다.

## 4. 다시 계산할 결과

기존 9회 추론에서 저장한 원시 window 점수를 재사용한다. 모델 추론을 다시 하지
않고 다음 운영점을 계산할 수 있다.

- 현재 임계값의 결과
- validation에서 Recall이 가장 높은 임계값
- validation F2가 가장 높은 임계값
- Recall을 유지하면서 거짓 이벤트가 감소하는 Pareto 임계값
- 각 후보를 기존 test에 적용한 Precision, Recall, F1, F2
- 각 후보의 클립 거짓 양성과 연속 음성 거짓 이벤트/시간
- 웃음 단독, 연속 박수, 웃음+박수 조건별 FN과 FP 목록

기존 test 결과를 이미 확인한 뒤 수행하는 사후 튜닝이므로 test를 완전히 보지
않은 최종 평가 세트라고 다시 주장하지 않는다. validation에서 후보를 만들고
test는 후보의 민감도를 비교하는 진단 자료로 사용한다. 새로운 일반화 성능을
주장하려면 별도의 미사용 데이터 또는 향후 섀도 운영의 수동 검수가 필요하다.

재계산은 다음 명령으로 수행한다.

```bash
python3 ai/model_benchmark/audio_threshold_tuning.py \
  --results-dir \
    ~/ai_benchmark_results/audio-accuracy-comparison-20260803T235943Z \
  --dataset-root \
    ~/ai_datasets/model_benchmark/office-audio-events-v1
```

도구는 validation의 모든 원시 점수 임계값과 연속 양성 창 1·2·3개 조합을
평가한다. `threshold-tuning.md`에는 요약과 섀도 후보를 기록한다.
`threshold-tuning.json`에는 전체 Pareto 후보와 test 사후 진단을 기록한다.
`threshold-sweep.jsonl`에는 전체 탐색 결과를 기록한다.
`failure-cases.jsonl`에는 추천 섀도 후보의 test FN·FP를 기록한다.

## 5. 파라미터별 조정 범위

### 5.1 기존 예측으로 바로 비교할 값

- 웃음 클래스 점수 임계값
- 박수 클래스 점수 임계값
- 필요한 연속 양성 window 수
- 이벤트 쿨다운
- 웃음·박수 교차 유형 병합 시간

쿨다운과 병합 시간은 감지 Recall이 아니라 중복 이벤트와 영상 병합에 영향을
준다. 모델이 실제 소리를 양성으로 판단했는지와 업로더가 여러 판단을 하나로
합쳤는지를 분리해 평가한다.

### 5.2 기존 점수만으로 바꿀 수 없는 값

- EfficientAT의 10초보다 짧은 새 입력 문맥
- 기존에 계산하지 않은 더 촘촘한 hop
- 박수 onset 수와 간격을 다른 방식으로 추출하는 로직
- BRIO 100의 거리별 음질과 SNR
- 실제 사람과 스피커 재생음의 출처 판별

이 값은 음성을 다시 처리하거나 새로운 현장 음성을 확인해야 한다. 시간이 없다는
이유로 원시 근거 없이 성능 수치를 만들지 않는다.

## 6. 기존 데이터로 검증되지 않은 요구사항

현재 `office-audio-events-v1`에는 다음 전용 코호트가 없다.

- `small-laughter`
- `baby-laughter`
- 어린이 웃음
- `multiple-laughter`
- 1m, 3m, 5m, 10m 거리 구분
- TV·휴대전화에서 재생한 웃음·박수 hard negative

따라서 파라미터를 조정한 뒤에도 이 상황을 잘 감지하거나 억제한다고 수치로
주장할 수 없다. 이 항목은 제품 요구사항에는 포함하지만 현재 검증 상태는
`미검증`으로 남긴다.

작은 웃음과 10m 음성은 모델 한계와 마이크 한계를 분리해야 한다. 녹음된
파형에서 사람도 목표 소리를 구분하기 어렵다면 모델 미탐으로만 해석하지 않는다.
향후 검증할 때 RMS, peak, 배경 소음과 SNR을 모델 점수와 함께 기록한다.

## 7. 웃음+박수 평가 방법

혼합 샘플은 웃음과 박수 평가에 각각 양성으로 들어가지만 개별 Recall만으로는
혼합 이벤트 성공을 설명하지 못한다. 다음 값을 별도로 집계한다.

- 혼합 샘플의 웃음 Recall
- 혼합 샘플의 박수 Recall
- 같은 샘플에서 웃음과 박수를 모두 감지한 비율
- 두 가상 이벤트가 12초 병합 범위 안에 들어온 비율
- 실제 업로더에서 영상 하나와 두 이벤트 유형으로 처리된 비율

섀도 모드에서는 EfficientAT이 실제 trigger나 영상을 만들지 않으므로 앞의 네
항목을 가상 이벤트로 계산한다. 실제 업로드 병합률은 모델 전환 전 별도 종단
검증에서 확인한다.

## 8. 섀도 모드 원칙

- YAMNet만 실제 이벤트 생성 권한을 가진다.
- EfficientAT은 동일 RTSP 오디오에서 점수와 가상 이벤트만 기록한다.
- EfficientAT은 trigger, MQTT 이벤트, 영상 업로드를 생성하지 않는다.
- 두 모델은 동일한 타임스탬프 기준으로 비교한다.
- 섀도 결과에서는 FN을 먼저 검토하고 FP 원인을 함께 분류한다.
- YOLOv8n TensorRT FP16의 FPS, GPU, 온도와 서비스 재시작 여부도 기록한다.

섀도 모드에 자연스럽게 아기·어린이·다인 웃음이나 10m 이벤트가 나타나면 수동
검수 근거로 남길 수 있다. 그러나 계획된 표본이 아니므로 해당 사례 몇 건만으로
전체 성능이 검증됐다고 표현하지 않는다.

## 9. 현재 결정

1. BRIO 100을 유지한다.
2. 이벤트별 전역 임계값을 사용한다.
3. Recall을 핵심 지표로 두고 오탐을 함께 최소화한다.
4. 기존 원시 예측으로 임계값 Pareto 분석을 다시 수행한다.
5. 기존 데이터에 없는 요구사항은 검증됐다고 주장하지 않는다.
6. 임계값 후보를 정한 뒤 YAMNet과 EfficientAT 섀도 비교로 확인한다.
7. 섀도 검증 전에는 운영 이벤트 모델을 교체하지 않는다.

이 결정은 데이터 수집 시간이 부족한 현재 상황에서 가능한 범위를 명확히
제한한다. 파라미터 튜닝으로 확인할 수 있는 것과 새로운 데이터 없이는 확인할
수 없는 것을 구분하는 것이 결과를 과장하지 않는 방법이다.

## 10. 재튜닝 실행 결과

2026-08-04에 비교 ID `audio-accuracy-comparison-20260803T235943Z`의 원시 예측
9회를 재계산했다. 총 3,768개 임계값·연속 창 조합을 평가했다.

- EfficientAT의 전체 test 웃음 Recall 최저는 `0.933333`이다.
- EfficientAT의 전체 test 박수 Recall 최저는 `0.933333`이다.
- EfficientAT의 60분 연속 음성 웃음 오탐은 최대 `2.0건/시간`이다.
- EfficientAT의 혼합 이벤트 동시 감지 비율 최저값은 `0.80`이다.
- PANNs의 전체 test 웃음 Recall 최저는 `0.866667`이다.
- PANNs의 전체 test 박수 Recall 최저는 `0.90`이다.
- PANNs의 60분 연속 음성 오탐은 두 이벤트 모두 `0건/시간`이다.
- PANNs의 혼합 이벤트 동시 감지 비율 최저값은 `0.80`이다.
- YAMNet의 전체 test 웃음 Recall 최저는 `0.833333`이다.
- YAMNet의 전체 test 박수 Recall 최저는 `0.883333`이다.
- YAMNet의 60분 연속 음성 오탐은 두 이벤트 모두 `0건/시간`이다.
- YAMNet의 혼합 이벤트 동시 감지 비율 최저값은 `0.70`이다.

Recall이 가장 높은 EfficientAT을 첫 섀도 후보로 유지한다. 웃음 오탐
`2.0건/시간`은 해결된 값으로 보지 않고 섀도 모드의 최우선 검수 항목으로 둔다.
운영 이벤트 생성 권한은 여전히 YAMNet에만 둔다.

EfficientAT 섀도 후보 설정은 다음과 같이 확정한다.

- 웃음 임계값은 `0.01691491`이다.
- 웃음 연속 양성 창은 1개다.
- 박수 임계값은 `0.08725224`다.
- 박수 연속 양성 창은 1개다.
- 모델 입력 문맥은 10초다.
- 모델 점수 갱신 hop은 2.5초다.
- 이벤트 쿨다운은 12초다.

웃음 임계값 `0.00376541`은 Recall `1.0`을 만들었지만 연속 음성 오탐이
`37건/시간`이어서 제외한다. 선택한 임계값의 오탐 `2건/시간`은 모두 직접
수집한 TV·음악 연속 구간에서 발생했다. 섀도 모드에서는 TV·음악 재생 구간을

## 11. 섀도 구현 상태

`audio_shadow_runner.py`는 EfficientAT의 실시간 점수와 가상 이벤트만 기록한다.

섀도 실행기에는 trigger, MQTT, API, 영상 업로드 인자가 존재하지 않는다.

운영 스택의 `AUDIO_SHADOW_ENABLED` 기본값은 `false`다.

섀도 실행기가 비정상 종료돼도 YAMNet 운영 판정은 계속된다.

섀도 실행기는 비정상 종료 후 독립적으로 다시 시작한다.

`audio_shadow_report.py`는 YAMNet과 EfficientAT 이벤트를 12초 범위에서 비교한다.

모델별 단독 이벤트는 수동 검수 전까지 FP 또는 FN으로 확정하지 않는다.

Jetson 적용과 검증 절차는
[`34_YAMNet_EfficientAT_섀도_검증.md`](./34_YAMNet_EfficientAT_섀도_검증.md)에
기록한다.
