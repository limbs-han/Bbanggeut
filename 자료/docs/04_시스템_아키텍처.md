## 1. 목적과 설계 원칙

윌리엄 제임스는 카메라 영상을 짧은 세그먼트로 계속 순환 보관하다가 웃음·호출어·터치 이벤트가 발생하면 지나간 장면을 추출해 기기별 비공개 영역에 저장하는 서비스다.

- **[기본] 온디바이스 우선:** 카메라·마이크 원본은 Jetson에서 처리한다. 영구 저장은 선택된 이벤트 영상으로 제한하고, 실시간 영상은 권한 있는 활성 세션 동안만 별도 경로로 전달한다.
- **[기본] 직접 업로드:** 대용량 영상은 Spring Boot를 경유하지 않고 MinIO/S3로 직접 업로드한다.
- **[기본] 서버 측 권한 검사:** 앱이 전달한 사용자·기기·역할 값을 신뢰하지 않고, 사용자 JWT와 대상 `video.device_id`의 활성 `DeviceMembership`으로 매 요청을 검증한다.
- **[기본] 온디맨드 라이브:** 시청 세션이 있을 때만 기기 송출을 시작하고, 여러 시청자는 기기당 하나의 송출을 공유한다.
- **[기본] 라이브 요청 재검증:** 저장 영상 서명 URL과 라이브 재생 자격을 분리한다. 라이브 playlist·segment 요청마다 세션 소유자·상태·만료와 활성 멤버십을 검사하는 인증 계층 후보를 두고, 종료·만료·권한 회수 후 새 미디어 요청을 즉시 차단한다.
- **[기본] 단일 인코딩:** Jetson의 단일 H.264/AAC 인코더 출력을 순환 버퍼와 기기 live publisher로 tee한다. 별도 미디어 계층 후보는 publisher의 ingest를 재인코딩하지 않고 HLS로 remux·fan-out(`-c copy`)한다.
- **[기본] 경로 분리:** 이벤트 MP4의 MinIO/S3 직접 업로드와 라이브 ingest·HLS 전달을 서로 다른 데이터 경로로 운영한다.
- **[기본] 단일 백엔드:** 개발 기간을 고려해 Spring Boot 모놀리식 애플리케이션으로 구성한다.
- **[기본] 장애 격리:** AI 감지 실패가 순환 녹화·터치 저장을 중단시키지 않도록 이벤트 수집과 영상 버퍼를 분리한다.
- **[심화] 비동기 처리:** 편집·썸네일·콘텐츠 생성 작업을 별도 작업 큐와 워커로 분리한다.

## 3. 보드 배치와 폴백 전략

### 3.1 권장 이중 보드 구성

- **Jetson Orin Nano:** USB 카메라와 **USB 마이크**를 직접 연결한다. AI 추론과 순환 영상 버퍼를 한 프로세스 경계 안에서 운영해 이벤트 시각과 영상 타임라인 오차를 줄인다.
- **Raspberry Pi 5:** 터치 센서, 프라이버시 LED, 선택적 LCD를 연결한다. 로컬 네트워크를 통해 Jetson에 이벤트를 전달한다.
- 두 보드의 시간은 같은 NTP 기준으로 동기화하고, 로컬 이벤트에는 UTC 시각과 단조 증가 시계 값을 함께 포함한다.

### 3.2 한 보드 폴백

이중 보드 통신이 7월 24일까지 안정화되지 않으면 **Jetson 단일 보드 MVP**로 전환한다.

1. USB 카메라·USB 마이크는 기존처럼 Jetson에 유지한다.
2. 터치 센서와 LED를 Jetson의 3.3V GPIO 호환 핀에 연결한다.
3. Raspberry Pi 연동, LCD, 팬·틸트는 심화 범위로 이동한다.
4. Jetson GPIO 라이브러리·핀 번호·전압은 실제 개발 키트 리비전의 공식 핀맵으로 다시 검증한다.

Jetson을 사용할 수 없는 비상 상황에서는 Raspberry Pi 5 단일 보드로도 순환 녹화·터치 저장은 가능하지만, YOLO·YAMNet의 입력 크기와 추론 주기를 낮춰야 한다. 이 경로는 성능 검증 후 선택하며 기본 배포 경로로 간주하지 않는다.

웃음 이벤트 병합 규칙은 설정 시간 내 반복 감지가 들어오면 최초 감지 이벤트를 대표 이벤트로 유지하되, 실제 종료 시각을 고정할지 마지막 감지까지 연장할지는 **[미확정]**이다. MVP 기본안은 요구사항 그대로 최초 감지 시각 기준 <code>T-60초 ~ T+60초</code>의 한 영상만 생성하는 것이다.

### 4.2 호출어·터치 저장

- 호출어 “헤이 제임스” 또는 터치 시각을 <code>T</code>로 기록한다.
- 순환 버퍼에서 <code>T-120초 ~ T</code> 세그먼트를 선택한다.
- 호출어 모델이 미완성 또는 불안정하면 터치가 동일한 저장 흐름을 보장한다.
- 이벤트 ID를 멱등 키로 사용해 네트워크 재시도 중 동일 영상이 중복 등록되지 않게 한다.

### 4.4 영상 구간 편집

1. 앱은 원본 영상 ID, 시작 오프셋, 종료 오프셋만 보낸다.
2. API는 `video.device_id`의 활성 멤버십과 편집 역할, 오프셋 범위를 검증한다.
3. 작업 상태를 <code>PENDING → PROCESSING → COMPLETED</code> 또는 <code>FAILED</code>로 관리한다.
4. FFmpeg가 비공개 저장소에서 원본을 읽어 새 객체를 생성한다.
5. 원본 보존·대체 정책은 사용자가 선택하게 하며 기본값은 원본 보존이다.

### 4.5 온디맨드 라이브 세션

~~~mermaid
sequenceDiagram
    participant APP as Flutter 앱
    participant API as Spring Boot
    participant DB as PostgreSQL
    participant S as 세션 상태 저장소(구현 선택)
    participant MQ as MQTT
    participant E as Jetson 단일 인코더
    participant P as 기기 live publisher
    participant G as 라이브 요청 인증 후보
    participant M as 라이브 미디어 계층 후보

    APP->>API: POST /api/devices/{id}/stream-sessions + JWT
    API->>DB: active DeviceMembership(OWNER/MEMBER) 확인
    alt 활성 멤버십 없음
        API-->>APP: 404 Not Found · 존재 은닉
    else 기기 오프라인
        API-->>APP: DEVICE_OFFLINE
    else 접근 허용
        API->>S: PENDING 생성 · lastActivityAt=createdAt · viewerExpiresAt=createdAt+45초
        alt 이 기기의 첫 활성 시청자
            API->>MQ: commands · START_STREAM(streamId, hardExpiresAt=+120초)
            MQ->>P: 멱등 START_STREAM
            E->>P: 단일 H.264/AAC 인코더 출력
            P->>M: 기기당 하나의 ingest publish
            P->>MQ: STREAM_READY
        else 이미 송출 중
            API->>S: 기존 기기 송출 참조
        end
        API-->>APP: sessionId + PENDING/READY · READY이면 매우 짧은 재생 자격
        opt READY 이후 각 playlist·segment 요청
            APP->>G: HLS 요청 + live token
            G->>API: token introspection
            API->>S: 세션 소유자·READY·viewerExpiresAt 확인
            API->>DB: active DeviceMembership 재확인
            API-->>G: allow 또는 deny
            alt CLOSED/EXPIRED·다른 사용자·멤버십 없음
                G-->>APP: 이후 미디어 요청 즉시 거부
            else 유효
                G->>M: 검증된 HLS 요청
                M-->>G: playlist 또는 segment
                G-->>APP: HLS 응답
            end
        end
        loop PENDING/READY 화면 유지 중 15초마다
            APP->>API: stream session heartbeat
            API->>S: lastHeartbeatAt·lastActivityAt 갱신 · viewerExpiresAt=+45초
            API->>MQ: commands · EXTEND_STREAM(hardExpiresAt=+120초)
            MQ->>P: 멱등 EXTEND_STREAM
        end
        alt 정상 화면 종료
            APP->>API: DELETE stream session
        else 앱 종료·네트워크 단절
            API->>S: viewerExpiresAt에 EXPIRED · 첫 heartbeat 없으면 createdAt+45초
        end
        alt 마지막 활성 시청자 0명
            API->>API: lastActivityAt/DELETE 기준 +60초 · 첫 heartbeat 없으면 createdAt+60초
            API->>MQ: commands · STOP_STREAM(streamId)
            MQ->>P: 멱등 STOP_STREAM
            P->>M: ingest 종료
        else 다른 활성 시청자 존재
            API->>API: 기기 송출 유지
        end
    end
    Note over P: STOP 유실·제어 경로 장애 시 마지막 hardExpiresAt에 자체 종료
~~~

첫 재생은 기기 송출 시작과 첫 HLS 세그먼트 생성 때문에 수초간 `PENDING`일 수 있다. 세션 생성 시 heartbeat가 아직 없어도 `lastActivityAt=createdAt`, `viewerExpiresAt=createdAt+45초`로 둔다. 유효 heartbeat는 권장 15초마다 `lastActivityAt`과 `viewerExpiresAt`을 갱신한다. 따라서 앱이 `POST` 직후 사라져 첫 heartbeat가 한 번도 없어도 `createdAt+45초`에 세션이 `EXPIRED`되고, 마지막 시청자라면 STOP deadline은 `createdAt+60초`다. 일반적인 STOP deadline은 마지막 유효 `lastActivityAt` 또는 정상 `DELETE` 시각 `+60초`이며, TTL 만료 뒤 60초를 다시 더하지 않는다. 이 deadline 전에 새 세션 또는 유효 heartbeat가 들어오면 예약된 `STOP_STREAM`을 취소한다. 서버의 활성 시청자 수는 유효한 `viewerExpiresAt`을 가진 세션만 집계하며, 앱 연결 수와 기기 ingest 수를 혼동하지 않는다.

저장 영상의 MinIO/S3 서명 URL은 이미 발급되면 만료까지 남을 수 있지만 라이브 자격에는 같은 방식을 사용하지 않는다. 라이브는 ① 인증 프록시가 매 playlist·segment 요청을 검사하거나 ② 미디어 계층이 매우 짧은 opaque token을 요청마다 introspection하는 후보 중 하나를 채택한다. 두 후보 모두 세션 소유자, `READY`, `viewerExpiresAt`, 활성 `DeviceMembership`을 서버 상태로 재검증하고 `CLOSED/EXPIRED` 또는 권한 회수 이후의 새 요청을 즉시 거부해야 한다. 자체 검증 JWT의 짧은 만료만 기다리는 방식은 이 기준을 충족하지 않으며, 구체 제품과 배치 방식은 아직 미확정이다. 이미 단말에 내려간 버퍼는 회수할 수 없고 차단 기준은 이후 playlist·segment 요청이다.

라이브 제어는 `{env}/wj/v1/devices/{deviceId}/commands` 단일 토픽과 `START_STREAM/EXTEND_STREAM/STOP_STREAM` 타입을 사용한다. `START_STREAM`과 `EXTEND_STREAM` payload의 `hardExpiresAt`은 기본적으로 명령 발행 시점에서 120초 뒤이며 서버는 활성 시청자가 있을 때만 주기적으로 연장한다. 서버 또는 MQTT 제어 경로가 끊기면 기기 live publisher는 마지막 유효 `hardExpiresAt`, 즉 마지막 연장으로부터 약 120초 안에 자체 종료한다.

### 4.6 단일 인코더와 전달 경로

~~~mermaid
flowchart LR
    INPUT["카메라·마이크"] --> ENC["Jetson H.264/AAC 인코더<br/>GOP/keyframe 기준 2초"]
    ENC --> TEE{"tee"}
    TEE --> BUFFER["순환 세그먼트<br/>이벤트 MP4 조립"]
    BUFFER -->|"서명 URL 업로드"| STORE[("MinIO/S3")]
    TEE --> PUBLISHER["기기 live publisher"]
    PUBLISHER -->|"별도 live ingest"| MEDIA["미디어 계층 후보<br/>HLS remux · -c copy<br/>fan-out"]
    MEDIA --> VIEWERS["여러 앱 시청자"]
~~~

- Jetson은 순환 녹화와 라이브를 위해 H.264/AAC를 각각 인코딩하지 않는다. 하나의 인코더 출력을 순환 버퍼와 기기 live publisher로 tee한다.
- 기기 live publisher는 인코더 출력을 별도 미디어 계층 후보에 publish하고, 미디어 계층은 코덱을 다시 압축하지 않고 HLS 컨테이너로 remux·fan-out한다. `-c copy`가 불가능한 입력 설정이면 조용히 재인코딩하지 말고 통합 시험에서 실패로 처리해 Jetson 인코더 설정을 수정한다.
- GOP/keyframe 간격은 2초를 기준으로 HLS 세그먼트 경계와 정렬한다. 확정값은 실제 장비의 첫 재생 시간·안정성 측정 후 고정한다.
- 이벤트 MP4 업로드 경로와 라이브 ingest·HLS 경로를 분리하며, 라이브 데이터를 MinIO/S3 이벤트 객체로 영구 저장하지 않는다.
- MediaMTX 같은 전용 미디어 계층은 다중 시청자 fan-out과 HLS 전달을 위한 구현 후보다. 제품 채택은 아직 확정하지 않으며 동등한 구성을 비교할 수 있다.

### 5.1 기기별 권한 관계

~~~mermaid
erDiagram
    USER ||--o{ DEVICE_MEMBERSHIP : "여러 기기에 참여"
    DEVICE ||--o{ DEVICE_MEMBERSHIP : "UNCLAIMED는 0개 가능"
    DEVICE ||--o{ VIDEO : "영상 생성"

    DEVICE_MEMBERSHIP {
        uuid user_id FK
        uuid device_id FK
        string role "OWNER or MEMBER"
        string status "ACTIVE or REVOKED"
    }
    VIDEO {
        uuid id PK
        uuid device_id FK
        string object_key
    }
~~~

- `(user_id, device_id)`는 중복될 수 없다. `UNCLAIMED` 기기는 멤버십이 0개일 수 있고, 등록 완료 후 기기의 활성 `OWNER`는 정확히 1명이다.
- 사용자는 여러 기기에 참여할 수 있으며 기기마다 역할이 달라도 된다.
- 초대는 대상 `device_id`에 고정되고, 수락 시 그 기기의 `DeviceMembership(MEMBER)`만 생성한다.
- 영상 접근은 클라이언트가 보낸 기기 ID가 아니라 서버가 조회한 `video.device_id`의 활성 멤버십과 역할로 판정한다.
- 앱 사용자는 JWT로, IoT 기기는 별도 기기 자격 증명으로 인증한다. 두 인증 주체는 서로 대체할 수 없다.

## 7. 저장 형식과 상태

### 7.1 권장 객체 키

객체 키는 외부에 공개하지 않으며 서버가 생성한다.

~~~text
private/{deviceId}/original/{videoId}.mp4
private/{deviceId}/edited/{editId}.mp4
private/{deviceId}/thumbnail/{videoId}.jpg
~~~

경로 분리는 관리 편의를 위한 것이며 보안 경계는 버킷 비공개 정책과 API 권한 검사다.

### 7.2 주요 상태 머신

~~~mermaid
stateDiagram-v2
    [*] --> BUFFERING
    BUFFERING --> ASSEMBLING: 이벤트 발생
    ASSEMBLING --> UPLOADING: 로컬 영상 생성 성공
    ASSEMBLING --> FAILED: 생성 실패
    UPLOADING --> AVAILABLE: 업로드·등록 검증 성공
    UPLOADING --> RETRY_WAIT: 네트워크 실패
    RETRY_WAIT --> UPLOADING: 백오프 재시도
    RETRY_WAIT --> FAILED: 재시도 한도 초과
    AVAILABLE --> DELETED: 사용자 삭제·보관기간 만료
~~~

### 7.3 라이브 세션 상태

~~~mermaid
stateDiagram-v2
    [*] --> PENDING: POST 세션
    PENDING --> PENDING: 15초 heartbeat · 만료 연장
    PENDING --> READY: 기기 STREAM_READY
    PENDING --> FAILED: 오프라인·시작 실패·준비 timeout
    PENDING --> EXPIRED: 첫 heartbeat 없이 createdAt+45초
    READY --> READY: 15초 heartbeat
    READY --> CLOSED: DELETE
    READY --> EXPIRED: viewerExpiresAt 도달
    PENDING --> CLOSED: 사용자 취소
    FAILED --> [*]
    CLOSED --> [*]
    EXPIRED --> [*]
~~~

개별 앱 세션 상태와 기기 송출 상태는 분리한다. API 상태는 `PENDING/READY/CLOSED/EXPIRED/FAILED`로 통일하고, 앱에서는 `CLOSED/EXPIRED`를 모두 “종료됨”으로 표시할 수 있다. 세션 하나가 `CLOSED` 또는 `EXPIRED`가 되어도 다른 활성 세션이 있으면 기기 송출은 `RUNNING`을 유지한다. 첫 heartbeat 전에는 `createdAt`이 `lastActivityAt`이며 `viewerExpiresAt=createdAt+45초`, STOP deadline은 `createdAt+60초`다. heartbeat 후에는 마지막 `lastActivityAt+45초`에 `EXPIRED`, STOP deadline은 같은 `lastActivityAt+60초`다. 정상 `DELETE`는 삭제 시각+60초를 사용한다. 즉 세션 만료 뒤 새 60초를 시작하지 않으며, deadline 전에 새 세션이 생기면 `STOP_STREAM`을 취소한다.
