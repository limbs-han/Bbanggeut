# Flutter 푸시·라이브·갤러리 연동

## 영상 편집 SDK

- Banuba `ve_sdk_flutter` 의존성과 Android 네이티브 패키징 설정을 제거했다.
- Banuba 라이선스 로더, 외부 편집기 진입 UI와 약 56MB의 마스크 리소스를 제거했다.
- 영상 편집은 `LocalEditScreen`과 `VideoEditorExporter` 기반의 앱 자체 로컬 편집기를 사용한다.
- 효과 탭의 인앱 색감과 스티커 꾸미기는 유지하며 얼굴 추적 마스크는 제공하지 않는다.
- 편집 결과의 기기 갤러리 저장은 `gal` 플러그인을 사용한다.

## 푸시 알림

Flutter 앱은 Firebase Cloud Messaging 토큰을 발급받아 다음 기존 API에
연결한다.

- 로그인 또는 저장된 세션 복원: `PUT /api/notifications/push-tokens`
- FCM 토큰 갱신: 같은 API로 새 토큰 재등록
- 로그아웃 또는 회원 탈퇴: `DELETE /api/notifications/push-tokens/{installationId}`

`installationId`는 앱 설치별 임의 값이며 Secure Storage에 저장한다.
포그라운드에서는 OS 알림과 중복되지 않도록 Firebase의 전경 alert/sound를
끄고 앱 내부의 크림·핑크 알림 카드 하나만 표시한다. 백그라운드와 종료
상태에서는 서버가 보낸 notification payload를 OS가 표시한다.

알림 payload의 `type`과 `resourceId`를 사용한다.

- `INVITATION_RECEIVED`: 받은 초대함으로 이동하고 목록을 다시 조회한다.
- `LAUGHTER_VIDEO_READY`: 서버에서 영상 상세를 조회한 뒤 상세 화면으로
  이동한다. 웃음 전용이 아니다 — 박수·호출·직접 촬영으로 담긴 영상도 이
  타입으로 오며, 무엇 때문에 담겼는지는 알림 제목이 말해 준다.
- `COMIC_SCRIPT_READY`·`COMIC_READY`: 만화 화면으로 곧장 간다. 대사 준비와
  그림 완성이 같은 목적지인 이유는, 만화 화면이 저장된 구성을 읽어 대사
  편집으로 이어 주기 때문이다.

알림 센터는 `GET /api/notifications`의 실제 응답을 사용하고, 개별 읽음과
모두 읽음 API를 호출한다.

### 알림 종류 구분

이모지·배경색·카테고리 라벨을 `core/notification_visuals.dart` 한 곳에서
정한다. 알림함 목록과 포그라운드 배너가 같은 값을 읽는다.

같은 매핑이 두 벌 있던 동안에는 알림함이 여섯 종을 알고 배너가 네 종만 알아서,
같은 알림이 배너에서는 🔔, 목록에서는 🎨로 보였다. 기념일과 주간 리포트는
양쪽 모두 기본값으로 떨어져 초대와 구분되지 않았다.

배너 눈썹은 앱 이름(`빵긋`) 고정이 아니라 카테고리를 적는다. 배너는 한 번에
하나만 보이므로 그 한 줄이 갈래를 말해 주는 쪽이 쓸모 있다.

목록 카드에는 제목 위에 카테고리 칩을 둔다. `...이 도착했어요` 꼴의 제목이
여럿이라 이모지 하나만으로는 훑어 읽을 때 갈라지지 않았다.

모르는 타입은 기본값(🔔 · `알림`)으로 떨어진다 — 서버가 새 종류를 먼저 보내도
앱이 빈칸을 그리지 않아야 한다.

### 필수 운영 설정

현재 저장소에는 `frontend/android/app/google-services.json`이 없다.
실제 Firebase 프로젝트에서 Android application id
`com.williamjames.william_james_app`으로 발급한 파일을 추가해야 FCM이
초기화된다. 파일이 없으면 앱의 로그인·일반 기능은 계속 동작하지만 푸시만
비활성화된다.

현재 저장소에는 `frontend/ios` 플랫폼 프로젝트 자체가 없다. iOS 지원 시
Flutter iOS 플랫폼을 생성·통합하고 실제 `GoogleService-Info.plist`,
Push Notifications capability, Background Modes의 Remote notifications,
`NSPhotoLibraryAddUsageDescription`을 추가해야 한다.

백엔드 운영 환경에서는 `FCM_ENABLED=true`, `FIREBASE_PROJECT_ID`, Firebase
Admin 자격 증명이 실제 프로젝트와 일치해야 한다.

## WHEP 라이브와 전체 화면

운영 라이브 규격은 MediaMTX의 WHEP/WebRTC 수신 전용이다. 현재 API와 WHEP
응답에는 재생 위치, DVR 윈도우, seek 가능 범위가 없으므로 과거 구간
진행 바를 만들지 않는다. 프런트에서 임의 길이의 가짜 진행 바도 표시하지
않는다.

연결 중에는 빨간 점과 빨간 `LIVE`를 표시한다. 이를 누르면 기존 세션을
닫고 새 WHEP 세션을 열어 최신 프레임으로 복귀한다. 전체 화면은 임베디드
화면과 같은 `RTCVideoRenderer`를 재사용하며 별도 플레이어를 만들지 않는다.
전체 화면 라우트가 검정 배경으로 먼저 덮인 뒤 가로 방향을 적용하고, 종료
후 세로 방향과 edge-to-edge 시스템 UI 복원을 기다린다.

DVR이 필요하면 MediaMTX 앞단 또는 별도 재생 API가 실제 seek window와
재생 위치를 제공하도록 서버 계약을 먼저 확장해야 한다.

### 끊겼을 때 스스로 다시 붙는다

WebRTC가 끊기면 곧바로 오류를 띄우지 않고 120초 동안 다시 붙어 본다. 서버가
미디어 끊김을 30초에 판정하고 그때 세션을 죽이지 않고 재연결 대기로 내리며
120초까지 살려 둔다(`StreamMediaReconcileWorker`) — 앱이 더 짧게 포기하면
살아 있는 세션을 앞에 두고 "다시 시도해 주세요"를 띄우게 된다.

세션이 재연결 대기(`PENDING`)로 내려가면 `whepUrl`이 응답에서 빠지므로, 죽은
재생 주소로 다시 붙는 일은 생기지 않는다. 폴링이 `READY`를 다시 보는 순간
재생을 다시 연다.

재연결 중에는 LIVE 칩이 `LIVE 재연결 중`이다. 처음 여는 `LIVE 연결 중`과
갈라 적는 이유는, 사용자가 아무것도 하지 않아도 된다는 것을 알아야 하기
때문이다.

세션이 끝났을 때는 서버 실패 코드를 그대로 찍지 않고 사람이 읽는 문구로
바꾼다. 화면에 `MEDIA_NOT_FLOWING`이 떠 있으면 사용자는 무엇을 해야 하는지
알 수 없다.

## 영상 갤러리 저장

영상 상세의 저장 버튼은 다음 순서로 동작한다.

영상 상세 화면은 둥근 영상 플레이어 아래에 추억 제목, 촬영 시각, 이벤트 배지를 한 카드로 표시한다.

메모(영상 `description`) 기능은 2026-08-05에 걷어냈다. 상세 카드의 메모 상자와 그 안의 마스코트 장식, 편집 다이얼로그의 메모 입력, 목록 카드의 메모 줄, 검색의 메모 대조가 함께 사라졌다. 백엔드도 2026-08-05에 `description`을 더 이상 읽지도 쓰지도 않는다(API 응답·요청 필드와 SQL에서 제거). DB 칼럼만 남아 있다 — 무중단 배포에서 구 슬롯이 구 코드로 서비스하는 구간이 있어 칼럼 삭제는 이 변경이 모든 슬롯에 반영된 뒤 별도 릴리스로만 가능하다.

기기가 붙인 기본 제목은 화면에서 `8월 5일(수) 오전 9:27 · 웃음` 형태로 바꿔 그린다. 기기는 이벤트 종류만 보고 제목을 정하므로 같은 종류의 클립이 모두 같은 문구가 되어 목록에서 영상을 구분할 수 없었다.

바꿔 그리는 대상은 `widgets.dart`의 `deviceDefaultVideoTitles`에 열거한 문구뿐이다. 사용자가 편집한 제목은 그 목록에 없으므로 그대로 표시한다. 저장된 제목 자체는 바꾸지 않으며, 제목 편집 입력창에도 저장된 값이 그대로 들어간다.

기기 쪽 원본은 `ai/yolo/segment_clip_uploader.py`의 `EVENT_TITLES`·`MIXED_EVENT_TITLES`다. 거기에 문구가 추가되면 앱 목록에도 더해야 하며, 빠뜨리면 그 종류만 예전처럼 고정 제목으로 보인다.

달력에서 고른 날의 목록은 날짜가 이미 맥락이라 시각과 종류만 적는다.

목록 카드의 시간 범위는 `durationMs`로 끝 시각을 잡는다. 끝을 시작 + 2분으로 박아 두었을 때는 30초 클립도 2분짜리로 보였다. 길이를 모르는 영상이나 시작과 끝이 같은 분에 드는 짧은 클립은 시작 시각만 적는다.

영상 삭제 확인창은 삭제 전용 캐릭터 이미지와 복구 불가 안내를 표시하고, 취소와 삭제 버튼을 나란히 구분한다.
영상 편집 종료 확인창은 저장 전용 캐릭터 이미지와 편집 유실 경고를 표시하고, 계속 편집과 저장하기 버튼을 나란히 구분한다.
제목 옆 수정 버튼은 제목만 편집하는 다이얼로그를 연다.
제목 편집 다이얼로그는 빼꼼 마스코트, 제목 입력, 저장 버튼을 표시한다.
제목을 저장하면 목록의 그 한 줄만 갈아 끼우고 화면을 바로 바꾼다. 예전에는 저장 뒤 그 영상을 다시 받고 기기 데이터 여섯 요청까지 기다려, 사용자가 자기가 누른 결과를 몇 초 뒤에 봤다.

제목 수정 버튼과 목록의 삭제 버튼은 권한을 보고 감춘다. 기기가 담아 온 원본은 OWNER에게만 띄우고, 편집본은 구성원에게도 띄운다(`widgets.dart`의 `canManageVideo`).

편집본 삭제는 서버가 "만든 사람 또는 OWNER"로 한 번 더 거른다. 앱은 누가 만들었는지 모른다 — 영상 응답에 생성자가 없다. 그래서 편집본은 버튼을 띄우고 판정을 서버에 맡기며, 남의 편집본이면 서버가 이유를 담아 거절한다. 생성자를 응답에 노출하면 그때 앱에서도 감출 수 있다.

편집 완료 영상도 원본 상세와 같은 재생 표면(`MediaPlayerSurface`)을 쓴다. 편집본만 손으로 만든 `VideoPlayer` + 눌러서 재생·정지였던 동안에는 진행 바가 없어 처음부터 끝까지 보는 수밖에 없었다 — 몇 분 몇 초로 옮기거나 10초를 되감을 방법이 없었고 남은 길이도 알 수 없었다.

편집 완료 영상 화면의 댓글은 각 줄 오른쪽 메뉴에서 수정·삭제한다. 자기 댓글은 수정과 삭제가 모두 뜨고, OWNER에게는 남의 댓글에도 삭제만 뜬다 — 남의 말을 고쳐 쓰는 것과 지우는 것은 다른 일이다. 이 판정에 필요한 로그인 사용자와 OWNER 여부는 화면을 여는 세 곳(전체 목록·캘린더·알림)에서 넘겨준다.
갤러리 저장과 영상 편집은 상세 카드 아래의 독립된 버튼으로 제공한다.

1. 인증된 `POST /api/videos/{videoId}/download-url` 호출
2. 서명 URL 전용 Dio로 영상 파일을 앱 임시 디렉터리에 다운로드
3. Android MediaStore 또는 iOS Photos를 사용하는 `gal` 플러그인으로 저장
4. 임시 파일 삭제

MinIO/S3 서명 URL에는 저장소 인증 정보가 쿼리에 이미 포함되어 있으므로
2번 요청에는 앱의 `Authorization: Bearer` 헤더를 붙이지 않는다. 401 또는
403이면 만료 가능성을 고려해 다운로드 URL을 한 번 새로 발급받아 재시도한다.

외부 브라우저나 WebView를 열지 않는다. 다운로드 진행률을 표시하고 저장
중 버튼을 비활성화해 중복 다운로드를 막는다. 영상 카드의 동작하지 않던
공유 버튼과 복사 콜백은 제거했다.

## 편집 준비 화면

영상 상세에서 `영상 편집하기`를 누르면 검은 미리보기 기반 로딩 화면 대신
크림 배경의 전용 준비 화면을 먼저 표시한다. 준비 화면은 빵긋 마스코트,
자르기·음악·스티커 기능 카드와 실제 준비 진행률을 표시한다.

진행률은 고정된 장식 숫자가 아니다. 다운로드 URL 발급, 원본 영상 다운로드,
로컬 미리보기 초기화 단계를 반영하며 원본 다운로드 중에는 수신 바이트
비율에 따라 증가한다. 준비가 끝나면 기존 편집 화면으로 자동 전환한다.

## 설정과 가족 상태

설정 메인에는 알림 항목을 하나만 표시하고, 선택하면 카드형 팝업 안에서
기념일·주간 리포트·새로운 추억의 세 토글을 보여 준다. 토글은 Secure
Storage의 기존 키로 읽고 저장한다. 설정의 웃음 리포트 행만 제거했으며
홈의 웃음 리포트 기능은 유지한다. 보관 구독도 상태와 보관 기간을 설명하는
전용 카드형 팝업에서 활성화하거나 해지한다.

설정의 기존 알림 위치에는 가족 구성원 목록과 OWNER용 이메일 초대 카드
(MEMBER는 초대 요청 링크 카드)를 직접 표시한다. 기존 가족 관리 행 위치에는
알림 설정 행을 배치한다. 설정의 가족 카드와 받은 초대함은 하단 가족 탭과
동일한 `AppController` 상태와 API를 사용하므로 별도 가짜 데이터가 없다.
초대 수락 성공 직후 초대·Vault·구성원·권한·기기·영상 데이터를 다시
조회하고 수락한 기기가 들어 있는 Vault를 선택하므로 앱 재시작이 필요 없다.

프로필 수정 화면은 이름 입력 카드와 큰 프로필 미리보기를 중심으로 구성한다.
카메라 버튼에서는 휴대폰 갤러리 사진 또는 앱에 포함된 캐릭터 기본 이미지
9종을 선택할 수 있다. 선택한 프로필 이미지는 앱 전용 로컬 저장소에 복사하고
Secure Storage에 선택값을 보관해 설정 화면에도 반영한다. 서버에는 프로필
이미지 API가 없으므로 이미지 선택은 이 기기의 앱 안에서만 유지한다.

설정 화면 반영은 `ProfileAvatarStore.current` notifier가 맡는다. 설정의 작은
아바타는 `const ProfileAvatarView`라서 부모가 `setState`를 불러도 Flutter가
같은 인스턴스를 알아보고 서브트리 리빌드를 건너뛴다 — 저장소를 `build` 안에서
읽는 방식으로는 새로 고른 그림이 그 자리에 반영되지 않았다.

갤러리에서 고른 사진은 파일마다 다른 이름으로 저장한다. 같은 이름에 덮어쓰면
이미지 캐시가 파일 경로를 키로 잡고 있어 예전 사진을 계속 그린다. 저장이 끝난
뒤에 지금 쓰는 파일만 남기고 정리한다 — 고르는 시점에 지우면 사용자가 저장하지
않고 나갔을 때 저장소가 가리키는 파일이 사라진다.

## 장소 배치와 기기 순서

장소 이름과 기기가 어느 장소에 있는지는 금고 공통이다. 집의 사실이라 가족이 함께 본다 — 거실 홈캠은 누가 봐도 거실에 있다. 구성원 누구나 고칠 수 있다(홈캠을 안방으로 옮긴 사람이 그 사실을 적을 수 있어야 하고, 잘못 적어도 되돌리기 쉽다).

기기를 어떤 순서로 볼지는 사람마다 다르게 둔다. 보기 취향이라 한 사람이 바꿔도 다른 가족 화면은 그대로다.

지금 어느 장소를 보고 있는지(`selectedPlace`)는 화면 상태라 서버에 두지 않고 Secure Storage에 남긴다.

로컬 사본은 유지한다. 배치는 홈 화면이 처음 그려질 때 이미 필요해서, 서버 응답을 기다리면 기기 목록이 한 번 흔들리고 비행기 모드에서는 아예 못 읽는다. 로컬로 먼저 그리고 서버 값이 오면 갈아 끼운다.

서버 배치가 비어 있으면 이 폰의 로컬 배치를 한 번 올린다. 서버화 이전에 각자 정리해 둔 배치가 있는데 빈 목록으로 덮으면 모두의 장소·순서가 기본값으로 초기화된다.

## 홈·기기 등록·캘린더 화면 조정

홈의 라이브 영역 제목 옆 `실시간 보기` 문구는 제거했다. 기기가 없는 계정의
연결 안내 카드도 실제 라이브 카드와 같은 4:3 비율을 사용해 화면 높이가
상태에 따라 달라지지 않는다.

라이브 카드의 높이는 바깥 카드의 4:3 비율만으로 정한다. 카드 안쪽에서 비율을
한 번 더 걸지 않는다 — 두 제약이 어긋나면 논리 폭에 따라 소수점 단위로 넘친다.

홈 `오늘의 기록` 카드의 높이는 고정값이 아니라 내용이 요구하는 높이를 따른다.
갤럭시 S24+의 논리 폭은 411dp로 개발용 에뮬레이터 기본값(480dp)보다 좁아,
고정 높이는 실기기에서만 넘쳤다.

앱 전체의 시스템 글자 배율 상한은 1.3배다. 그보다 큰 기기 설정에서도 화면이
잘리지 않게 하고, 통계 타일 라벨은 잘리는 대신 글자가 줄어든다.

기기 등록 화면은 Owner와 Member 카테고리의 차이를 선택 영역 위에서 설명한다.
Owner는 새 기기를 최초 등록하고 가족을 초대하며, Member는 기존 Owner에게
초대를 요청한다.

하단 탭에서 여는 캘린더는 상단 뒤로가기 버튼을 표시하지 않는다. 날짜 셀
높이를 늘려 월 달력을 크게 표시하고, 선택 날짜에 영상이 있으면
`M월 d일의 추억` 제목 옆에 `더보기`를 표시해 전체 목록으로 이동한다.
