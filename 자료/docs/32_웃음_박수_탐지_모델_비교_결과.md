# 웃음·연속 박수 탐지 모델 비교 분석 결과

비교 결과를 검토한 뒤 합의한 감지 대상, Recall 우선순위, BRIO 100과 10m
조건, 후속 튜닝 범위는
[`33_오디오_이벤트_요구사항과_튜닝_결정.md`](./33_오디오_이벤트_요구사항과_튜닝_결정.md)에
정리한다.

## 1. 보고서 요약

이 보고서는 Jetson Orin Nano에서 YAMNet TFLite, EfficientAT MN10, PANNs
CNN10을 동일한 평가 데이터로 세 번씩 비교한 결과를 정리한다. 비교 배치 ID는
`audio-accuracy-comparison-20260803T235943Z`이며, 9회 실행에서 웃음과 박수
각각의 결과를 만들어 총 18개의 완료된 `summary.json`을 확인했다.

전체 test를 기준으로 EfficientAT MN10이 웃음 F1 0.855, 박수 F1 0.966으로
가장 높았다. 그러나 사전에 정의한 1차 서비스 기준을 그대로 적용하면 PANNs
CNN10만 통과한다. EfficientAT은 직접 수집 박수 Recall이 0.80으로 기준 0.85에
미달했고, PANNs는 직접 수집 웃음·박수 Recall과 60분 연속 음성 오탐 기준을
모두 만족했다.

그럼에도 PANNs를 바로 운영 후보로 선택하지는 않는다. PANNs는 외부 음성에서
웃음 거짓 이벤트가 시간당 12.86건이었고, GPU 평균 사용률 76.0%, 최대 전력
14.8 W로 세 모델 중 부담이 가장 컸다. EfficientAT은 종합 정확도가 가장 높고
자원 사용량이 PANNs보다 낮아 첫 섀도 비교 후보로 정한다. 이 선택은 “사전
게이트의 승자”라는 뜻이 아니라, 현재 YAMNet과 함께 운영 환경에서 추가 검증할
공학적 후보라는 뜻이다.

현재 결론은 다음과 같다.

- 현재 운영 이벤트 권한은 YAMNet에 유지한다.
- EfficientAT은 이벤트를 업로드하지 않는 섀도 모드로 먼저 실행한다.
- EfficientAT의 웃음 오탐과 박수 누락을 운영 음성에서 다시 측정한다.
- YOLOv8n TensorRT FP16과 동시 실행할 때 지연, 온도, 전력, FPS를 측정한다.
- 섀도 검증 기준을 만족하기 전에는 운영 모델을 교체하지 않는다.

## 2. 평가 목적과 질문

이번 비교는 단순히 F1이 가장 높은 모델을 찾는 실험이 아니다. 실제 서비스에
적용할 모델을 판단하기 위해 다음 질문에 답하는 것을 목표로 했다.

1. 동일한 음성에서 웃음과 연속 박수를 얼마나 놓치지 않고 구분하는가?
2. 대화, 단발 충격음, TV·음악 같은 음성에서 거짓 이벤트가 얼마나 발생하는가?
3. 서로 다른 입력 문맥을 사용하는 모델을 서비스 관점에서 어떻게 공정하게 비교하는가?
4. 클립 단위 정확도가 연속 판정, 쿨다운, 영상 생성으로 이어지는 이벤트 품질을 설명하는가?
5. 정확도가 높더라도 Jetson에서 YOLO와 함께 지속 실행할 수 있는가?

## 3. 평가 환경과 재현 조건

### 3.1 장치와 실행 환경

- 실행 장치: NVIDIA Jetson Orin Nano Developer Kit Super
- 전력 모드: 25 W
- 모델 실행: TFLite CPU 또는 PyTorch CUDA
- 비교 횟수: 모델별 3회, 총 9회
- 평가 결과: 이벤트별 2개, 총 18개 summary
- 평가 시각: 2026년 8월 4일 09:03~09:53 KST에 결과 생성
- 서비스 격리: 상시 녹화, 이벤트 업로드, Device Agent, 서보 제어 중지

세 모델의 실행 순서는 회차마다 바꿨다. 1회차는 YAMNet, EfficientAT, PANNs
순서였고, 2회차는 EfficientAT, PANNs, YAMNet 순서였다. 3회차는 PANNs,
YAMNet, EfficientAT 순서였다. 특정 모델이 항상 차가운 장치나 뜨거운 장치에서
실행되는 순서 효과를 줄이기 위한 구성이다.

### 3.3 데이터셋

validation 60개는 모델별 임계값 선택에만 사용했다. test는 임계값을 고정한 뒤
2,064개를 평가했다.

| 코호트 | 구성 | 역할 |
| --- | ---: | --- |
| `localDirect` | 직접 수집 10초 음성 60개 | 사무실 환경의 Recall과 F1 확인 |
| `continuousNegative` | 15분 음성 4개, 총 60분 | 실제 시간축의 거짓 이벤트/시간 확인 |
| `externalGeneralization` | ESC-50 2,000개 | 낯선 음성에 대한 일반화 확인 |

직접 수집 test는 웃음 단독, 연속 박수, 웃음+박수, 대화, 단발 충격음,
음악·TV·생활 소음을 각각 10개씩 포함한다. ESC-50에서는 `laughing` 40개와
`clapping` 40개를 각각의 양성으로 사용하고 나머지 1,920개를 음성으로
사용했다. 여기서 음성은 소리가 없다는 뜻이 아니라 두 목표 이벤트에 대한
negative 라벨이라는 뜻이다. 모든 2,124개 항목은 `verified` 상태이며, 직접 수집 test와
validation 사이 및 연속 음성 사이에서 중복 파일이 없음을 확인했다.

ESC-50는 CC BY-NC 3.0이므로 비상업적 교육 프로젝트의 평가 목적으로만
사용했다. ESC-50는 실제 사무실을 그대로 대표하지 않으므로 최종 서비스 통과
여부를 외부 데이터의 종합 점수 하나로 결정하지 않았다.

### 3.4 임계값과 이벤트 판정

validation에서 이벤트별 임계값을 따로 선택했다. 최소 Recall 목표는 0.85였고,
거짓 양성이 가장 적은 후보를 먼저 선택했다. 선택한 임계값은 test에서 다시
조정하지 않았다.

| 모델 | 웃음 임계값 | 박수 임계값 | 최소 판정 구간 |
| --- | ---: | ---: | ---: |
| YAMNet | 0.109375 | 0.738281 | 1.4625초 |
| EfficientAT MN10 | 0.016915 | 0.087252 | 10초 |
| PANNs CNN10 | 0.036898 | 0.153862 | 3초 |

임계값의 절대 크기는 모델 사이에서 비교하지 않는다. 각 모델의 출력 분포가
다르기 때문이다. 공통으로 12초 쿨다운을 적용했고, 같은 음성 파일과 같은
정답 라벨을 사용했다.

### 3.5 현재 이벤트 파이프라인과 기존 종단 검증

현재 운영 파이프라인은 RTSP 오디오 입력, YAMNet 점수 계산, 임계값 및 연속
양성 판정, trigger 생성, 12초 쿨다운, 웃음·박수 교차 유형 병합, 이벤트 영상
생성, 서버 업로드, 앱 표시 순서로 동작한다. 모델 비교의 window 예측은 이
파이프라인에서 첫 번째 판단기의 품질을 비교한 것이다.

저장소의 교차 유형 병합 기본값은 5초지만, 아래 종단 시험을 수행한 Jetson의
환경 파일에는 `EVENT_CROSS_TYPE_MERGE_GAP_SECONDS=12`를 명시했다. 따라서
이 보고서의 12초는 코드 기본값이 아니라 현장에서 검증한 운영 설정값이다.

YAMNet 기반 운영 파이프라인에서는 단발 박수를 무시하고 연속 박수를 CLAP으로
생성하는 것을 확인했다. 첫 이벤트 직후 다시 친 연속 박수는 12초 쿨다운 안에서
양성 점수로 인식됐지만 새 이벤트로 만들지 않았다. 웃음을 먼저 감지한 뒤
4.253초 후 박수를 감지한 시험에서는 12초 교차 유형 병합 범위 안에서
`LAUGHTER`와 `CLAP`을 하나의 영상으로 업로드했고 앱 표시까지 확인했다.

이 종단 검증은 현재 YAMNet 판정기에 대한 근거다. EfficientAT으로 판정기를
바꿨을 때도 같은 이벤트 시각, 쿨다운, 병합, 영상 포함 범위를 보장한다는 근거는
아니므로 섀도 모드 이후 별도 종단 검증이 필요하다.

아래 값은 세 회차에서 동일하게 재현됐다. 같은 모델과 고정된 데이터·임계값을
사용한 결정적 평가이므로 정확도가 매회 같았으며, 반복 실행은 주로 지연과 자원

| 모델 | 연속 음성 웃음 거짓 이벤트/h | 연속 음성 박수 거짓 이벤트/h | ESC-50 웃음 F1 | ESC-50 박수 F1 |

EfficientAT은 60분 연속 음성에서 웃음 거짓 이벤트 2건을 만들었다. 외부
일반화에서는 EfficientAT이 가장 높았지만 웃음 음성 1,960개 중 14개

4.1의 거짓 이벤트/시간은 모든 test 음성 코호트의 negative 재생 시간으로

값이므로 두 표의 수치가 다르다. 외부 일반화 데이터가 실제 사무실 오탐률을
희석하거나 과장하지 않도록 두 값을 모두 공개한다.

## 5. 지연시간과 Jetson 자원

아래 값은 모델별 세 회차의 평균이다. 최대값은 세 회차에서 관측된 가장 높은
값이다.

| 모델 | 평균 추론 | P95 추론 | GPU 평균/최대 | RAM 평균/최대 | 최고 온도 | 전력 평균/최대 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| YAMNet | **3.5 ms** | **4.4 ms** | **0% / 0%** | **2,281 / 2,562 MB** | **51.8°C** | **4.8 / 5.6 W** |
| EfficientAT MN10 | 43.4 ms | 50.9 ms | 36.0% / 68% | 2,988 / 3,381 MB | 53.2°C | 5.8 / 7.0 W |

세 모델 모두 한 번의 추론 시간은 각자의 hop보다 짧았다. 그러나 추론 시간이

ms라는 추론 수치만으로 빠르다고 말할 수 없다. 실제 반응 시간은 입력 문맥,
hop, 연속 양성 판정, 쿨다운, 업로드를 포함해 따로 측정해야 한다.

PANNs는 추론 시간은 EfficientAT보다 짧지만 GPU와 전력을 가장 많이 사용했다.
이 측정은 오디오 벤치마크를 격리한 결과이므로 YOLOv8n TensorRT FP16과 동시에
실행했을 때도 같은 수치가 유지된다고 단정할 수 없다.

## 6. 사전 서비스 기준 판정

사전에 정한 1차 통과 기준은 다음 두 가지다.

- `localDirect`에서 웃음과 박수 Recall이 모두 0.85 이상이어야 한다.
- `continuousNegative`에서 웃음과 박수 거짓 이벤트가 모두 시간당 1회 이하여야 한다.

| 모델 | 로컬 웃음 Recall | 로컬 박수 Recall | 연속 음성 최대 FP/h | 1차 결과 |
| --- | ---: | ---: | ---: | --- |
| YAMNet | 0.80 | 0.85 | 0.00 | 실패: 웃음 Recall |
| EfficientAT MN10 | 0.85 | 0.80 | 2.00 | 실패: 박수 Recall과 웃음 FP/h |
| PANNs CNN10 | 0.85 | 0.95 | 0.00 | **통과** |

이 표 때문에 EfficientAT을 “모든 기준에서 최종 우승한 모델”이라고 표현하면
안 된다. PANNs는 사전 1차 기준을 통과했지만 외부 웃음 오탐과 자원 부담이
컸다. EfficientAT은 사전 기준을 통과하지 못했지만 전체 test 정확도가 가장
높고 PANNs보다 운영 자원 부담이 작았다. 현재 데이터만으로는 자동 교체 모델을
확정하기보다 서로 다른 위험을 가진 후보로 보는 것이 맞다.

## 7. 시행착오와 결과 신뢰성

초기에는 세 모델에 YAMNet의 0.975초 입력을 공통 적용했다. EfficientAT은 이
조건에서 대부분의 클래스 점수가 1.0으로 포화돼 모든 샘플을 양성으로
예측했다. FP16과 FP32에서 같은 문제가 나타났고 10초 입력에서는 정상 점수
분포가 복원됐다. 이 결과는 정밀도 문제가 아니라 모델의 학습 문맥과 입력
조건이 맞지 않았던 사례로 판단해 최종 비교에서 제외했다.

PANNs를 FP16 autocast로 실행했을 때 12,676개 창 중 9,189개 이벤트 점수가
`NaN`이 됐다. 값을 0이나 1로 잘라서 결과를 만들지 않고 해당 실행을
`diagnostics`로 격리했다. PANNs는 FP32로 다시 실행했으며 저장 전에 모든
출력이 유한한 값이고 `[0, 1]` 범위인지 검사했다.

중단된 배치를 다시 시작할 때 완료된 YAMNet과 EfficientAT 1회차 결과는
건너뛰었다. 완료되지 않은 PANNs 디렉터리는 진단 자료로 보존한 뒤 같은 비교
ID에서 PANNs FP32부터 재개했다. 최종 집계기는 `diagnostics` 경로를 제외하고
정상 완료된 18개 summary만 포함했다.

## 8. 예리한 청중 질문에 대한 답변

### 8.1 입력 길이와 판정 방식이 다른데 공정한 비교인가?

모든 모델은 같은 원본 음성, 같은 분할, 같은 정답 라벨, 고정된 test를
사용했다. 임계값은 동일한 validation에서만 선택했다. 반면 입력 길이와 hop을
완전히 같게 만들지는 않았다. 그렇게 하면 EfficientAT처럼 긴 문맥으로 학습된
모델이 비정상적인 점수를 만들 수 있기 때문이다.

따라서 이 실험은 동일 입력 텐서에 대한 순수 모델 구조 비교가 아니다. 각
모델을 실제로 사용할 수 있는 권장 문맥으로 구성한 서비스 수준 비교다. 입력
창, hop, 최소 판정 구간을 결과와 함께 공개해 긴 문맥의 정확도 이점과 반응
지연을 동시에 판단하도록 했다.

### 8.2 클립 정확도가 실제 이벤트 품질로 이어지는가?

10초 클립의 Precision·Recall·F1만으로는 충분하지 않다. 이를 보완하기 위해
목표 이벤트가 없는 60분 연속 음성에 실제 연속 양성 판정과 12초 쿨다운을
적용해 거짓 이벤트/시간을 계산했다. 이 평가는 단순 거짓 양성 클립 수와 실제
알림 발생 횟수를 구분한다.

다만 EfficientAT으로 실제 영상 생성, 서버 업로드, 앱 표시까지 수행한 종단
결과는 아직 없다. 모델의 발생 시각과 실제 소리의 시작 시각 차이, 영상에
이벤트 순간이 포함되는지, 앱 표시까지의 지연은 섀도 모드와 후속 종단
검증에서 측정해야 한다.

### 8.3 EfficientAT이 사전 기준을 통과하지 못했는데 왜 섀도 후보인가?

EfficientAT을 즉시 운영 모델로 선택한 것이 아니다. 전체 test에서는 두
이벤트 F1이 가장 높았고, PANNs보다 GPU·온도·전력 부담이 낮아 현재 운영
YAMNet과 함께 실행해 볼 첫 공학적 후보로 선택한 것이다.

사전 기준에서는 PANNs만 통과했으므로 이 사실을 결과에서 분리해 공개한다.
섀도 측정에서 EfficientAT의 로컬 박수 누락과 연속 음성 웃음 오탐이 재현되면
교체하지 않는다. PANNs는 높은 자원 사용량과 외부 웃음 오탐 때문에 온라인
동시 실행보다 오프라인 후보로 남긴다. 이후 기준이나 후보 우선순위를 바꾼다면
결과를 본 뒤 규칙을 바꿨다는 사실도 함께 기록해야 한다.

## 9. 섀도 모드 검증 계획

섀도 모드에서는 YAMNet만 운영 이벤트를 생성한다. EfficientAT은 같은 RTSP
오디오를 읽지만 trigger 파일, MQTT 이벤트, 영상 업로드를 만들지 않는다.
두 모델의 판단을 공통 타임스탬프로 기록해 사용자에게 중복 알림이 전달되는
위험 없이 비교한다.

### 9.1 기록 항목

- 모델명, 모델 체크섬, 입력 창과 hop
- 음성 창 시작·종료 시각과 모델 판정 시각
- 웃음·박수 점수, 임계값, 연속 판정 상태
- YAMNet 운영 이벤트 ID와 EfficientAT 가상 이벤트 ID
- 사람이 확인한 정답과 오탐·미탐 사유
- 추론 평균·P95, GPU, RAM, 온도, 전력
- YOLO FPS, Edge AI 서비스 재시작 횟수와 로그 오류

### 9.2 전환 전에 확정할 기준

다음 값은 이번 결과에서 임의로 만들지 않고, 섀도 실행 전에 팀이 합의해
설정해야 한다.

- 섀도 실행 기간 또는 최소 검수 이벤트 수
- 소리 발생부터 가상 이벤트까지 허용할 P95 지연
- YOLO FPS의 허용 하락 폭
- 장시간 동시 실행의 허용 온도와 전력
- 웃음·박수별 최종 Recall과 거짓 이벤트/시간

기존 1차 기준을 유지한다면 로컬 Recall 0.85 이상과 거짓 이벤트 시간당 1회
이하를 먼저 적용한다. EfficientAT이 이를 만족하고 동시 실행 안정성 및 종단
검증까지 통과할 때만 YAMNet의 이벤트 생성 권한을 넘긴다. 통과하지 못하면
임계값, 입력 hop, 후처리를 조정해 다시 평가하거나 현재 YAMNet을 유지한다.

위 기준은 최초 비교를 시작할 때 정한 사전 게이트로 보존한다. 비교 결과 검토
후 합의한 후속 튜닝에서는 고정된 오탐 상한으로 후보를 먼저 탈락시키지 않고
Recall을 핵심 지표로 삼되 Precision, F1, F2, 시간당 오탐을 함께 비교한다.
후속 후보 선정 방식과 검증 한계는
[오디오 이벤트 요구사항과 튜닝 결정](./33_오디오_이벤트_요구사항과_튜닝_결정.md)을
따른다.
