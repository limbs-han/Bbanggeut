# 윌리엄 제임스 보안·개인정보 설계

> 문서 상태: 설계안  
> 적용 대상: Flutter 앱, Spring Boot, PostgreSQL, MinIO/S3, MQTT, Jetson Orin Nano, Raspberry Pi 5  
> 주 담당: 백엔드 박찬형 / 협업: PM 사지한, IoT 유지호, 프론트 김수원·서유정, AI 이재준  
> 영상·음성은 사생활 민감도가 높은 데이터다. 이 문서는 법률 자문을 대신하지 않으며 출시 전 실제 운영 지역의 개인정보 요건을 별도 검토한다.

## 1. 보안 목표

1. **기밀성:** 해당 기기의 활성 멤버십을 가진 사용자만 그 기기의 영상·음성·메타데이터에 접근한다.
2. **무결성:** 기기 이벤트·업로드·영상 메타데이터의 위조와 중복을 탐지한다.
3. **가용성:** 네트워크가 일시 중단되어도 로컬 순환 녹화와 터치 저장을 유지한다.
4. **투명성:** 카메라 읽기·순환 녹화 중에는 물리 LED를 상시 점등하고 원격 LIVE 중에는 1Hz 점멸 또는 2색 LED 대안으로 구분하며, 조회·다운로드·삭제 주체를 기록한다.
5. **최소 수집:** 영구 저장은 이벤트에 선택된 영상으로 제한하고 나머지 순환 버퍼는 자동 삭제한다. 실시간 영상은 권한 있는 활성 세션 동안만 별도 경로로 전달하고 저장하지 않는다.
6. **권리 보장:** 사용자가 접근 권한을 회수하고 영상·계정·기기 연결을 삭제할 수 있게 한다.

### 3.1 신뢰하지 않는 입력

- 앱이 보내는 <code>userId</code>, <code>deviceId</code>, 역할, object key
- 기기가 보내는 사용자 정보와 자신에게 속하지 않은 <code>deviceId</code>
- 영상 파일명, MIME type, 확장자, 길이, 체크섬
- 초대 링크, 1회용 등록 코드, 기기의 물리 등록 모드 상태·만료 시각
- MQTT topic과 payload
- 스트림 session ID, heartbeat 시각, 시청자 수, 라이브 경로와 미디어 계층 callback

서버는 인증 주체와 DB 관계를 기준으로 값을 재구성하고, 범위·형식·크기를 검증한다.

## 4. 인증과 기기 등록

### 4.1 사용자 인증

| 항목 | 단계 | 설계 |
| --- | --- | --- |
| 비밀번호 저장 | [기본] | Argon2id 또는 BCrypt의 검증된 라이브러리 사용, 평문·복호화 가능 저장 금지 |
| 액세스 토큰 | [기본] | 짧은 수명의 JWT, 최소 claim, 로그에 원문 기록 금지 |
| 리프레시 토큰 | [기본] | 앱 Secure Storage 보관, 서버에는 해시 또는 회전 가능한 세션으로 관리 |
| 로그아웃 | [기본] | 리프레시 세션 폐기, 기기 분실 시 모든 세션 종료 지원 |
| 로그인 방어 | [기본] | IP·계정 단위 속도 제한, 반복 실패 지연, 동일 응답으로 계정 존재 여부 은닉 |
| MFA | [심화] | OWNER 계정의 2단계 인증 |
| 소셜 로그인 | [심화·미확정] | 제공사 토큰의 발급자·대상·nonce 검증 |

토큰 수명과 로그인 제한 횟수는 배포 전에 보안 설정표에 확정한다. 예시 값을 소스코드에 하드코딩하지 않고 환경 변수로 관리한다.

### 4.2 최초 기기 소유권 등록

~~~mermaid
sequenceDiagram
    participant O as 최초 사용자
    participant APP as Flutter 앱

    O->>D: 물리 버튼 길게 눌러 등록 모드 진입
    D->>API: registrationMode=ENABLED, expiresAt=+120초 + 등록 코드 요청
    API->>DB: 등록 모드 갱신 + CSPRNG 등록 코드 생성(해시 저장, 활성 코드 간 유일)
    API-->>D: 등록 코드 평문(이 응답에만 존재)
    D->>O: 7" LCD에 XXXX-XXXX 표시
    O->>APP: 화면의 등록 코드 입력
    APP->>API: 인증 사용자 + 등록 코드
    API->>DB: 코드 해시 역조회로 기기 특정 + 120초 TTL·미사용·UNCLAIMED·rate limit 확인
    alt 모두 유효
        API->>DB: OWNER 생성 + 등록 코드 사용 처리 + 등록 모드 종료
        API-->>D: 기기별 장기 자격 증명 발급
        API-->>APP: 등록 성공
    else 실패
        API-->>APP: 정보 노출 없는 등록 실패(실패 5회/10분 시 계정·IP 차단)
    end
~~~

**기본 통제**

- 인쇄식 정적 제품 코드는 사용하지 않는다. 등록 코드는 등록 모드 진입 시마다 서버가 CSPRNG로 새로 생성하는 1회용 값이며, 최초 기기 등록에만 사용하고 구성원 추가에는 사용하지 않는다.
- 등록 코드는 혼동 문자(O/0, I/1/L 등)를 제외한 대문자·숫자 32자 문자셋 8자리로 하고, 활성 코드 간 유일성을 서버가 보장한다(코드 제출만으로 대상 기기가 특정된다). DB에는 원문 대신 SHA-256 해시만 저장하며, 원문은 기기 화면과 발급 응답에만 존재한다.
- 사용자가 기기의 물리 버튼을 길게 누르면 기기는 서버에 등록 모드 `ENABLED`와 120초 `expiresAt`을 알리고 등록 코드를 발급받아 7" LCD에 표시한다. 120초가 지나면 코드와 등록 모드 모두 무효로 취급하며, 오래된 상태가 남아 있어도 등록을 허용하지 않는다.
- 앱의 최초 등록 요청은 인증 사용자와 등록 코드만 보낸다. 서버는 코드 해시 역조회로 기기를 특정한 뒤 코드가 미사용·미만료인지, 기기 상태가 `UNCLAIMED`인지, 계정·IP별 rate limit을 넘지 않았는지 함께 확인한다.
- 성공 트랜잭션에서 `DeviceMembership(OWNER)` 생성, 등록 코드 사용 처리, 등록 모드 종료를 함께 수행한다. 같은 코드는 다시 사용할 수 없고, 등록 모드를 다시 켜면 항상 새 코드가 발급된다.
- 등록 실패는 계정·IP당 5회/10분으로 제한하고 초과 시 해당 계정·IP의 등록 시도를 일시 차단하며, 실패 감사 로그를 남긴다. 틀린 코드는 특정 기기에 귀속되지 않으므로 시도 제한은 코드가 아닌 추측 주체(계정·IP)에 적용한다.
- 서버는 기기 자격 증명에서 인증된 `device_id`를 확정하며, 기기가 요청 본문에 보낸 사용자 ID나 다른 기기 ID를 신뢰하지 않는다.
- 기기별로 서로 다른 자격 증명을 발급하고 분실·양도·초기화 시 폐기한다.
- 중고 양도는 기존 OWNER의 기기 해제로만 시작한다. 해제 트랜잭션은 기존 device 행을 `REVOKED`로 종결하고 영상·멤버십·자격 증명을 삭제(또는 삭제 작업 등록)한 뒤 같은 시리얼의 새 `UNCLAIMED` device 행을 생성한다. 새 소유자는 일반 등록 절차로만 `OWNER`가 되므로 이전 소유자의 영상에는 누구도 접근할 수 없다. 물리 리셋에 의한 소유권 이전 경로는 제공하지 않는다.

### 4.3 기기별 구성원 초대

- 해당 기기의 OWNER가 이메일 또는 앱 내 1회용 링크로 사용자를 초대한다.
- 초대 토큰은 원문을 DB에 저장하지 않고 해시로 비교하며 만료·1회 사용·취소 상태를 가진다.
- 초대는 대상 `device_id`와 수신자에 고정하고, 수락 시 그 기기의 활성 `DeviceMembership(MEMBER)`만 생성한다.
- 초대받은 사용자는 자신의 계정으로 로그인한 뒤 수락한다.
- 등록 코드나 OWNER 비밀번호를 구성원과 공유하지 않는다.
- OWNER는 해당 기기에 대한 구성원의 권한을 즉시 회수할 수 있으며, 그 사용자가 가진 다른 기기 멤버십은 변경하지 않는다.

## 5. 권한 모델

### 5.1 관계와 제약

~~~mermaid
erDiagram
    USER ||--o{ DEVICE_MEMBERSHIP : "기기별 역할"
    DEVICE ||--o{ DEVICE_MEMBERSHIP : "UNCLAIMED는 0개 가능"
    DEVICE ||--o{ VIDEO : "생성"
~~~

- `(user_id, device_id)`에는 하나의 멤버십만 존재한다.
- `UNCLAIMED` 기기는 멤버십이 0개일 수 있다. 등록 완료된 기기에는 활성 `OWNER` 멤버십을 정확히 하나만 허용하고, 최초 등록과 멤버십 생성을 하나의 DB 트랜잭션으로 처리한다.
- 한 사용자가 가진 여러 기기 멤버십은 서로 독립적이다. 특정 기기의 권한 회수는 다른 기기의 역할과 접근 권한을 변경하지 않는다.
- `Video.device_id`는 생성한 기기를 가리키며, 영상 권한 판정의 유일한 소속 기준이다.

### 5.2 역할별 권한

| 작업 | 해당 기기 OWNER | 해당 기기 MEMBER | 미인증·비구성원 |
| --- | --- | --- | --- |
| 기기 최초 등록·해제 | 허용 | 금지 | 금지 |
| 구성원 초대·권한 회수 | 허용 | 금지 | 금지 |
| 해당 기기 영상 목록·재생 | 허용 | 허용 | 금지 |
| 해당 기기 온디맨드 실시간 보기 | 허용 | 허용 | 금지 |
| 영상 다운로드 | 허용 | 허용 | 금지 |
| 영상 구간 편집 | 허용 | 허용 범위로 시작 | 금지 |
| 영상 삭제 | 허용 | MVP 정책상 금지 권장 | 금지 |
| 접근 로그 조회 | 허용 | 금지 | 금지 |
| 기기·보관 정책 변경 | 허용 | 금지 | 금지 |

MEMBER의 편집·다운로드·삭제 범위는 PM이 확정해 API 명세와 동일하게 맞춘다. 프론트에서 버튼을 숨기는 것만으로 권한을 구현하지 않고 서버가 모든 요청에서 검사한다.

### 5.3 객체 수준 권한 검사

모든 영상 API에서 다음 조건을 순서대로 확인한다.

1. 유효한 사용자 세션인가?
2. 요청한 Video가 존재하는가?
3. 서버가 조회한 `video.device_id`에 대해 현재 사용자의 활성 `DeviceMembership`이 존재하는가?
4. 계정·멤버십·기기·영상이 활성 상태인가?
5. 요청한 작업이 역할에 허용되는가?
6. 허용된 경우에만 짧은 서명 URL 또는 처리 결과를 발급한다.

대상 기기의 활성 멤버십이 없으면 `404`로 응답해 자원 존재를 숨긴다. 같은 기기의 활성 구성원이지만 `OWNER` 전용 작업처럼 역할이 부족한 경우에만 `403`을 사용한다. 이 정책을 API 전체에서 통일하고 클라이언트가 요청 본문에 보낸 `device_id`나 역할은 권한 판정의 근거로 사용하지 않는다.

라이브 세션 생성도 같은 원칙을 적용한다. 서버는 `POST /api/devices/{deviceId}/stream-sessions`에서 활성 `DeviceMembership(OWNER/MEMBER)`을 검사하고, heartbeat와 `DELETE`는 세션을 만든 사용자만 수행하도록 검증한다. 권한이 회수되면 해당 사용자의 활성 라이브 세션을 즉시 `EXPIRED`로 바꾸고 새 재생 자격뿐 아니라 이후 playlist·segment 요청도 거부한다. 한 사용자의 세션 종료가 다른 활성 시청자의 세션을 종료해서는 안 된다.

### 6.0 현재 개발 환경의 보안 상태와 사용 제한

위 표는 **목표 설계 요구사항**이며 현재 로컬 Compose가 모두 충족했다는 의미가 아니다.

- 현재 개발용 MinIO Compose에는 KMS 연동과 기본 SSE가 구축되지 않았다. 따라서 서버 측 저장 암호화는 **미구축** 상태이며, 실제 사용자·가정 영상이나 운영 데이터를 넣어서는 안 된다.
- 현재 Mosquitto Compose는 평문 연결과 공유 개발 계정을 사용하고 기기별 topic ACL이 없다. 운영 요구사항인 MQTTS, 기기별 자격 증명, 최소 publish/subscribe ACL, 자격 증명 회전·폐기는 **미구축** 상태다.
- 현 구성은 로컬 개발과 합성·비민감 데모 데이터에만 사용한다. 외부 네트워크 공개 또는 실제 사용자 데이터 처리 전 MinIO/S3의 서버 측 암호화와 Mosquitto의 MQTTS·기기별 ACL을 구축하고 아래 보안 시험을 통과해야 한다.
- 저장소는 기본 암호화 정책과 업로드 객체의 암호화 상태를 확인하고, 키 접근 권한·회전·복구 절차를 문서화한다. MQTT는 평문 listener와 익명 접속을 차단하고, 다른 `deviceId` topic 접근 거부와 인증서·기기 자격 증명 폐기를 실증한다.

### 6.1 서명 URL 원칙

- 만료시간의 초기 권장 범위는 1~5분이며 실제 네트워크 측정 후 확정한다.
- URL은 최소 권한 작업만 허용한다. 업로드 URL로 읽거나 다른 키에 쓰지 못해야 한다.
- 앱 로그, 분석 SDK, 오류 리포트, 화면 캡처에 전체 URL과 query token을 남기지 않는다.
- 이 절의 URL은 저장 영상 MinIO/S3 객체용이다. 권한 회수 후 이미 발급된 저장 영상 URL은 만료까지 남을 수 있으므로 만료를 짧게 하고, 고위험 삭제·회수는 프록시 재생 또는 저장소 정책 전환을 검토한다.
- 라이브 playlist·segment에는 저장 영상 서명 URL을 재사용하지 않는다. 라이브는 아래 요청 시점 검증으로 세션 종료·만료·권한 회수 후의 새 요청을 차단한다.

### 6.2 온디맨드 라이브 통제

- 앱의 세션 생성 `POST` 전에 대상 기기의 활성 `DeviceMembership(OWNER/MEMBER)`을 검사한다. 최초 재생이 수초간 `PENDING`인 것은 허용하되 준비 timeout을 두고 무한 대기하지 않는다. 생성 트랜잭션에서 `lastActivityAt=createdAt`, `viewerExpiresAt=createdAt+45초`로 초기화한다.
- 앱은 `PENDING/READY` 세션 화면을 유지하는 동안 15초마다 heartbeat를 보내고 정상 화면 종료 시 `DELETE`한다. 유효 heartbeat마다 `lastHeartbeatAt`, `lastActivityAt`, `viewerExpiresAt=lastActivityAt+45초`를 갱신하며 만료된 세션은 활성 시청자 수에서 제외한다. 첫 heartbeat가 한 번도 없으면 `createdAt+45초`에 `EXPIRED`로 회수한다.
- 기기별 활성 시청자 수와 송출 상태 변경은 원자적으로 처리한다. 여러 시청자는 기기당 하나의 ingest를 공유하며 한 세션의 종료가 다른 시청을 중단시키지 않는다. API 세션 상태는 `PENDING/READY/CLOSED/EXPIRED/FAILED`로 통일하고 앱의 “종료됨” 표시는 `CLOSED/EXPIRED`를 묶은 UI 표현으로만 사용한다.
- 송출 중지 기준시각은 마지막 시청자의 `lastActivityAt` 또는 정상 `DELETE` 시각이다. 서버는 그 기준시각부터 최대 60초에 MQTT `STOP_STREAM`을 전송한다. 첫 heartbeat가 없으면 `lastActivityAt=createdAt`이므로 `createdAt+60초`가 STOP deadline이다. 세션을 45초에 `EXPIRED`로 바꾼 뒤 다시 60초를 더 기다리지 않으며, 새 세션이나 유효 heartbeat가 들어오면 예약된 중지를 취소한다.
- 라이브 재생 자격의 보안 동작은 확정하되 구현은 미확정이다. 후보 ① 인증 프록시가 매 playlist·segment 요청에서 세션 소유자·`READY`·`viewerExpiresAt`·활성 멤버십을 조회한다. 후보 ② 미디어 계층이 매우 짧은 opaque token을 매 요청 서버에 introspection한다. 어느 후보든 `CLOSED/EXPIRED` 또는 권한 회수 이후의 새 요청을 즉시 거부해야 하며, 자체 검증 JWT의 짧은 만료만 기다리는 방식은 허용하지 않는다. 이미 단말에 전달된 버퍼는 회수 대상이 아니며 이후 요청 차단을 검증한다.
- 라이브 제어는 `{env}/wj/v1/devices/{deviceId}/commands` 단일 토픽과 `START_STREAM/EXTEND_STREAM/STOP_STREAM` 타입만 사용한다. 각 명령은 command ID로 멱등 처리하고 기기별 MQTT ACL을 적용한다. `START_STREAM`과 `EXTEND_STREAM` payload의 `hardExpiresAt`은 기본적으로 발행 시점에서 120초 뒤이며, 서버는 활성 시청자가 있을 때만 이를 주기적으로 연장한다.
- 기기 live publisher는 명령 수신 시 `hardExpiresAt`의 남은 수명을 검증해 로컬 단조 시계 deadline으로 변환하고 자체 종료한다. 서버·MQTT 장애로 `STOP_STREAM`이 유실돼도 마지막 연장으로부터 약 120초 안에 종료해 송출을 무기한 계속하지 않는다.
- 이벤트 MP4 업로드와 라이브 ingest를 서로 다른 자격·경로로 분리하며, 라이브 HLS를 MinIO/S3 이벤트 객체로 영구 보관하지 않는다.
- Jetson은 H.264/AAC를 한 번만 인코딩하고 출력을 순환 버퍼와 기기 live publisher로 tee한다. publisher는 이를 별도 미디어 계층 후보에 ingest하며, 미디어 계층은 재인코딩 없이 `-c copy`로 HLS remux·fan-out한다. GOP/keyframe은 2초 기준으로 정렬해 불필요한 추가 인코더와 원본 처리 경로를 만들지 않는다.
- MediaMTX 같은 전용 미디어 계층은 구현 후보다. 채택 시 익명 publish/play 금지, TLS, 기기별 ingest 자격, 세션 재생 자격, 관리 API 비공개, 녹화 기본 비활성, 토큰 로그 마스킹을 검증해야 한다.

### 6.3 종단간 암호화의 범위

완전한 E2EE는 서버가 영상을 복호화할 수 없어 서버 FFmpeg 편집, 썸네일, 라이브 중계·HLS remux, 생성형 콘텐츠 기능과 충돌한다. 따라서 MVP는 다음을 적용한다.

- **[기본]** TLS 전송 암호화 + 비공개 저장소 암호화 + 강한 권한 검사
- **[심화]** 기기별 암호화 키
- **[장기 검토]** 서버 처리 기능을 포기하거나 사용자 단말 처리로 옮기는 E2EE 모드

서버가 AI·편집 목적으로 복호화할 수 있는 구조를 E2EE라고 표현하지 않는다.

### 7.1 보관 원칙

- 순환 버퍼는 호출·터치의 2분 전 영상을 보장할 만큼만 유지하고, 여유 시간을 포함한 실제 길이는 장비 측정 후 확정한다.
- 이벤트에 선택되지 않은 로컬 세그먼트는 업로드하지 않고 보관 한도를 넘으면 자동 삭제한다.
- 라이브 데이터는 활성 시청 세션 동안 별도 경로로 전달하고 이벤트 영상 저장소에 영구 보관하지 않는다. 제품 후보의 녹화 기능도 기본 비활성화한다.
- 업로드 성공 후 로컬 이벤트 영상은 재시도·무결성 확인에 필요한 짧은 기간만 보관하고 삭제한다.
- 서버 영상 기본 보관 기간, 휴지통 유예, 감사 로그 보관 기간은 **[미확정]**이다.
- 자동 삭제 작업은 성공·실패 건수를 남기되 영상 내용이나 서명 URL을 로그에 기록하지 않는다.
- 계정 탈퇴, 기기 등록 해제·양도 시 객체 저장소·DB·캐시·파생본을 포함한 삭제 범위를 정의한다. 계정 탈퇴로 다른 사용자의 기기 영상까지 삭제하지 않도록 소유권과 멤버십 삭제를 구분한다.
- 백업이 있다면 삭제 데이터의 백업 만료 시점과 복구 제한도 고지한다.

### 7.2 사용자 고지·동의

- 단일 프라이버시 LED는 카메라 프레임 읽기·순환 녹화 중 상시 점등하고, 원격 LIVE publisher 송출 중에는 1Hz(500ms ON/500ms OFF)로 눈에 띄게 점멸한다. 2색 LED라면 녹화 색상은 계속 점등하고 라이브 색상을 1Hz 점멸하는 대안을 허용한다.
- 점멸의 짧은 OFF 구간과 촬영 중 지속 소등을 구분한다. 사용자에게 LED 끄기 옵션을 제공하지 않으며, 상태 통신 오류 중 촬영 프로세스가 살아 있으면 LIVE 점멸 패턴을 유지하는 fail-safe를 적용한다.
- 카메라·마이크의 작동, 선행 2분 순환 버퍼, 웃음 자동 감지, 서버 전송 조건을 첫 설정에서 명확히 설명한다.
- 실시간 보기는 권한 있는 사용자의 요청 때만 시작되고 마지막 시청자 종료 후 제한 시간 안에 중지된다는 점을 고지하며, 라이브 송출 중임을 앱과 기기 상태 표시로 구분한다.
- 방문자·동거인을 위한 촬영 안내를 기기 주변에 표시할 수 있게 한다.
- 얼굴 분석과 생성형 콘텐츠는 **[심화·별도 동의]**로 분리하고 기본값을 꺼짐으로 둔다.
- 원본 영상의 외부 AI API 전송은 기본 금지하며, 필요 시 제공사·목적·보관·국외 전송 여부를 고지하고 별도 동의를 받는다.
- 서비스 개선·모델 학습 목적으로 사용자 영상을 재사용하는 동의는 서비스 이용 동의와 분리하고 기본값을 거부로 둔다.

## 9. 애플리케이션 보안 기준

### 9.1 API

- Spring Security의 deny-by-default 정책을 적용한다.
- DTO 화이트리스트로 입력을 받고 엔터티 직접 바인딩을 피한다.
- 편집 오프셋은 <code>0 ≤ start &lt; end ≤ duration</code>을 검증한다.
- 파일 크기, 콘텐츠 형식, 요청 본문 크기, 목록 페이지 크기를 제한한다.
- CORS는 Flutter 웹을 실제 제공할 때만 필요한 origin으로 제한한다. 모바일 앱이라는 이유로 인증서 검증을 끄지 않는다.
- SQL은 JPA의 파라미터 바인딩을 사용하고 동적 정렬 필드를 화이트리스트로 제한한다.
- 오류 응답에 스택 트레이스, 저장소 키, 토큰, 내부 호스트명을 포함하지 않는다.
- OpenAPI·Swagger UI는 운영에서 인증 뒤에 두거나 비활성화한다.
- 스트림 세션 생성은 대상 기기의 활성 멤버십을 검사하고, heartbeat·`DELETE`는 세션 소유자를 검사한다. 기기별 활성 세션 집계와 `START_STREAM/EXTEND_STREAM/STOP_STREAM` 전이는 원자적으로 처리한다.
- 세션 생성 시 `lastActivityAt=createdAt`, `viewerExpiresAt=createdAt+45초`로 저장한다. heartbeat는 `lastActivityAt`과 `viewerExpiresAt`을 갱신한다. 송출 stop deadline은 마지막 `lastActivityAt` 또는 정상 `DELETE` 기준 `+60초` 하나만 사용하며 TTL 만료 시점부터 새 60초를 더하지 않는다. 첫 heartbeat가 없으면 createdAt 기준 45초 만료·60초 STOP을 사용한다.
- 라이브 요청 인증 후보는 playlist·segment마다 세션 소유자·`READY`·`viewerExpiresAt`과 대상 기기의 활성 멤버십을 조회한다. 세션 `CLOSED/EXPIRED` 또는 권한 회수 트랜잭션이 완료된 뒤의 요청은 거부한다.
- 활성 시청 중에만 기본 120초 `hardExpiresAt`을 연장하고, 마지막 연장 후 서버·MQTT 제어가 끊겨도 기기가 약 120초 안에 자체 종료하는지 측정한다.

### 9.2 Flutter 앱

- 액세스·리프레시 토큰을 일반 preferences나 로그에 저장하지 않고 Secure Storage를 사용한다.
- 화면 캡처 차단은 플랫폼·사용성 영향을 검토해 **[심화]**로 적용하되, 앱 전환 화면에 영상 썸네일이 노출되지 않도록 처리한다.
- 딥링크 초대 토큰을 분석 SDK에 전송하지 않는다.
- 로그아웃·권한 회수·401 응답 시 로컬 영상 URL·캐시·세션을 정리한다.
- 다운로드 파일이 공유 저장소에 놓이면 노출될 수 있으므로 저장 위치와 사용자 경고를 제공한다.
- 세션 생성 직후 `PENDING`부터 `READY` 재생 화면을 유지하는 동안 15초 heartbeat를 보내고 화면의 정상 종료·로그아웃·권한 오류에서 세션 `DELETE`를 최선 노력으로 호출한다. 앱 강제 종료는 서버 TTL이 처리하므로 백그라운드에서 무기한 heartbeat를 보내지 않는다.
- 스트림이 준비되는 수초 동안 `PENDING`을 표시하고, 세션별 매우 짧은 재생 자격과 라이브 경로를 로그·분석 SDK에 남기거나 장기 캐시하지 않는다. 세션 종료·권한 오류 시 재생기를 중지하고 자격을 메모리에서 제거한다.

### 9.3 IoT

- 서비스는 전용 OS 사용자로 실행하고 root 상시 실행을 피한다.
- 자격 증명 파일은 최소 파일 권한으로 저장하고 Git·이미지에 포함하지 않는다.
- 서버 인증서 검증을 활성화하고 시간 불일치로 검증이 실패하지 않게 NTP를 운영한다.
- 로컬 제어 포트는 외부 네트워크에 공개하지 않고 방화벽·바인드 주소를 제한한다.
- 재부팅 후 프라이버시 LED와 카메라 상태가 일치하는 fail-safe 초기화 순서를 둔다. 카메라 읽기·순환 녹화는 상시 점등, 실제 원격 publisher 송출은 단일 LED 1Hz 점멸 또는 2색 LED의 녹화색 점등+라이브색 점멸로 표시하며 촬영 중 지속 소등을 금지한다.
- 업데이트 파일은 출처·해시·서명을 확인하고 이전 버전 롤백 경로를 둔다.
- `{env}/wj/v1/devices/{deviceId}/commands`만 구독하고 `START_STREAM/EXTEND_STREAM/STOP_STREAM`을 command ID로 멱등 처리하며 기기별 topic ACL을 사용한다. 활성 시청 중 서버가 연장한 기본 120초 `hardExpiresAt`이 지나면 live publisher가 ingest를 중단한다.
- Jetson 단일 H.264/AAC 인코더 출력을 순환 버퍼와 기기 live publisher로 tee하고, 별도 미디어 계층 후보의 2초 GOP 기준·HLS `-c copy` remux 여부를 실행 인자와 장비 측정으로 검증한다.

## 13. 사고 대응 절차

~~~mermaid
flowchart LR
    DETECT["탐지·신고"] --> CONTAIN["세션·기기 키·URL 차단"]
    CONTAIN --> PRESERVE["민감정보 제외 증적 보존"]
    PRESERVE --> ASSESS["영향 사용자·영상·기간 분석"]
    ASSESS --> FIX["원인 제거·키 회전·패치"]
    FIX --> NOTIFY["PM 보고·필요 통지 검토"]
    NOTIFY --> REVIEW["재발 방지·문서 갱신"]
~~~

### 13.1 즉시 조치 체크리스트

1. 노출된 계정 세션, 기기 자격 증명, 저장소 키를 폐기한다.
2. public access·CORS·버킷 정책·서명 URL 발급을 점검한다.
3. 영상 원문을 복제하지 않고 감사 로그와 배포 변경 이력을 보존한다.
4. 영향받은 사용자·기기·멤버십·객체·시간 범위를 확인한다.
5. PM이 법적·조직적 통지 필요성을 검토한다.
6. 수정 후 SEC 테스트를 재실행하고 회고에 재발 방지 항목을 남긴다.

## 14. 출시 전 보안 게이트

다음 항목 중 하나라도 충족하지 못하면 외부 네트워크에 영상 서비스를 공개하지 않는다.

- [ ] 저장소 public access 차단 확인
- [ ] MinIO/S3 서버 측 암호화(KMS 또는 SSE)와 업로드 객체 암호화 상태 확인 — 현재 개발용 MinIO Compose 미구축, 통과 전 실제 사용자 데이터 금지
- [ ] TLS 인증서 검증 및 HTTP→HTTPS 전환 확인
- [ ] 복수 기기·OWNER·MEMBER·비구성원 객체 권한 시험 통과
- [ ] 화면 등록 코드 + 120초 TTL + `UNCLAIMED` + 실패 5회/10분 차단 + 사용 후 재사용 거부 시험 통과
- [ ] 기기별 자격 증명과 폐기 절차 확인
- [ ] 토큰·비밀번호·서명 URL 로그 미노출 확인
- [ ] 카메라·순환 녹화 중 LED 상시 점등, 원격 LIVE 중 단일 LED 1Hz 점멸 또는 2색 대안, 상태 통신 오류·재부팅에서 촬영 중 지속 소등 없음 확인
- [ ] 라이브 세션 권한·`PENDING/READY/CLOSED/EXPIRED/FAILED` 상태·생성 시 lastActivityAt=createdAt·viewerExpiresAt=+45초·15초 heartbeat·동일 activity 기준 최대 60초 `STOP_STREAM` 시험 통과
- [ ] 첫 heartbeat 없는 PENDING 세션의 createdAt+45초 만료·createdAt+60초 STOP 확인
- [ ] 라이브 요청 인증 후보가 매 playlist·segment의 세션 소유자·READY·만료·active membership을 검사하고 종료·만료·권한 회수 뒤 새 요청을 즉시 거부하는지 확인
- [ ] 단일 MQTT commands 토픽·`START_STREAM/EXTEND_STREAM/STOP_STREAM`·기본 120초 `hardExpiresAt` 연장·제어 단절 후 엣지 자체 종료 시험 통과
- [ ] 운영 Mosquitto MQTTS·기기별 자격 증명·topic ACL·평문/익명 차단 확인 — 현재 Compose의 평문 공유 개발계정·ACL 없음은 비민감 데모 전용
- [ ] 다중 시청 시 기기 ingest 1개와 다른 세션 비간섭 확인
- [ ] 라이브 미디어 계층의 익명 접근·관리 API 노출·자동 녹화 차단 확인
- [ ] Jetson 단일 H.264/AAC 인코더 출력 → 기기 live publisher → 별도 미디어 계층 후보의 2초 GOP·HLS `-c copy` remux·fan-out, 이벤트 저장소와 라이브 경로 분리 확인
- [ ] 순환 버퍼와 서버 보관·삭제 정책 확정
- [ ] 영상 삭제 시 파생본 처리 확인
- [ ] 실제 테스트 계정 비밀번호가 Git·문서에 없는지 확인
- [ ] 얼굴 분석·외부 생성 API가 기본 비활성화인지 확인
- [ ] 보안 사고 연락 담당과 키 회전 방법 확인
