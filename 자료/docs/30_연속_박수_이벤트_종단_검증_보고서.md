# 연속 박수 이벤트 종단 검증 보고서

## 1. 문서 목적

이 문서는 연속 박수 감지 기능을 구현한 이유와 판정 방식, 2026년 8월 3일
Jetson 실장 환경에서 수행한 종단 검증 결과를 기록한다. 단순히 이벤트가 한 번
발생한 결과만 남기지 않고, 단발 박수 억제와 쿨다운, 서버 업로드, 앱 표시,
웃음·박수 혼합 이벤트까지 어떤 조건에서 확인했는지 구분한다.

## 2. 구현 목적

기존 홈캠은 웃음만 의미 있는 오디오 이벤트로 저장했다. 박수도 축하나 놀이처럼
보존 가치가 있는 순간이지만, 문을 닫는 소리나 물체 충돌 같은 단발 충격음을
박수로 오인할 가능성이 있다. 따라서 YAMNet의 분류 점수 하나만 사용하지 않고
반복되는 충격음과 시간적 연속성을 함께 확인하는 방식으로 구현했다.

## 3. 동작 구조

오디오 입력부터 앱 표시까지의 흐름은 다음과 같다.

1. Media Source가 BRIO 100 마이크의 오디오를 로컬 RTSP의 AI 스트림으로 전달한다.
2. YAMNet 프로세스가 `Clapping`, `Applause` 계열 점수를 계산한다.
3. `ConsecutiveClapDetector`가 점수, onset 수, 연속 양성 구간과 쿨다운을 검사한다.
4. 조건을 만족하면 `type=CLAP`인 트리거 JSON을 생성한다.
5. 업로더가 순환 녹화 구간에서 이벤트 전후 영상을 구성한다.
6. 웃음과 박수가 병합 범위 안에 있으면 영상 하나에 두 이벤트 유형을 기록한다.
7. 서버 업로드 후 앱은 제목, 이벤트 유형, 영상과 음성을 하나의 추억으로 표시한다.

박수 감지의 운영 검증값은 다음과 같다.

| 설정 | 값 | 의미 |
|---|---:|---|
| `YAMNET_CLAP_THRESHOLD` | `0.30` | `Clapping`·`Applause` 집계 점수 하한 |
| `YAMNET_CLAP_CONSECUTIVE` | `2` | 필요한 연속 양성 구간 수 |
| `YAMNET_CLAP_REQUIRED_ONSETS` | `3` | 분석 구간 안의 최소 분리 충격음 수 |
| `YAMNET_CLAP_MIN_ACTIVE_SECONDS` | `0.4` | 최소 양성 유지 시간 |
| `YAMNET_CLAP_MAX_GAP_SECONDS` | `0.75` | 양성 구간 사이에 허용하는 최대 간격 |
| `YAMNET_CLAP_COOLDOWN` | `12` | 새 박수 이벤트를 억제하는 시간 |
| `EVENT_CROSS_TYPE_MERGE_GAP_SECONDS` | `12` | 웃음·박수 교차 유형 병합 범위 |

저장소 기본값은 박수 감지 비활성화와 교차 유형 병합 5초다. 위 값 중 박수 감지
활성화와 12초 병합 범위는 백엔드와 앱의 다중 유형 표시가 반영된 검증 장치의
환경 파일에 적용했다.

## 4. 시험 환경

- 실행 장치: NVIDIA Jetson Orin Nano
- 카메라·마이크: Logitech BRIO 100
- 오디오 분류: YAMNet
- 영상 객체 탐지: YOLOv8n TensorRT FP16
- 미디어 입력: 로컬 MediaMTX RTSP AI 스트림
- 녹화 방식: MPEG-TS 순환 녹화
- 이벤트 영상 범위: 트리거 전 60초, 후 60초
- 같은 유형 병합 범위: 30초
- 교차 유형 병합 범위: 최종 검증 시 12초
- 안전 조건: 앱 Live View 종료, 서보 배터리 실드 OFF, 서보 서비스 중지

## 5. 순수 연속 박수 검증

### 5.1 단발 박수 음성 테스트

박수를 정확히 한 번만 쳤을 때 `CLAP` 트리거 수가 증가하지 않았다. YAMNet의
박수 계열 점수만으로 즉시 이벤트를 만들지 않고 onset과 연속 구간 조건이 실제로
단발 충격음을 걸러내는 것을 확인했다.

### 5.2 연속 박수 양성 테스트

3초 안에 약 0.3~0.5초 간격으로 박수를 5~7회 쳤다. 다음 트리거가 생성됐다.

| 항목 | 측정값 |
|---|---|
| 이벤트 유형 | `CLAP` |
| 신뢰도 | `0.921494` |
| 대표 클래스 | `Clapping` |
| onset 수 | `5` |
| 양성 구간 수 | `2` |
| 활성 시간 | `0.49초` |

이벤트 영상은 서버에 업로드됐고 앱에서 박수 이벤트 제목과 유형, 영상과 음성을
확인했다.

### 5.3 12초 쿨다운 테스트

첫 연속 박수가 감지된 직후 Enter 입력 없이 다시 5~7회 박수쳤다. 두 번째 동작은
박수 양성 조건을 만족했지만 새로운 이벤트를 만들지 않았다.

- 기준 이벤트 ID: `98757609-c6f1-4a7d-b2b9-7fc5bb697dec`
- 쿨다운 안의 예상 밖 트리거 수: `0`
- 쿨다운으로 억제된 양성 판정 수: `6`
- 억제 구간의 측정 간격: `1.440~5.754초`
- 억제 구간의 최고 점수: `0.960948`

초기 시험에서는 두 번째 `CLAP` 이벤트가 생겨 쿨다운 실패처럼 보였다. 로그의
실제 트리거 시각을 비교하니 두 이벤트 간격은 13.864초였고, 두 번째 시험이 이미
12초 쿨다운을 지난 뒤 시작된 것이 원인이었다. 이후 터미널 알림과 동시에 두 번째
박수를 치는 방식으로 시험 절차를 바꿔 쿨다운 동작을 확인했다.

## 6. 웃음·박수 혼합 이벤트 검증

### 6.1 시행착오

혼합 이벤트는 단순히 두 소리를 내는 것만으로 안정적으로 생성되지 않았다.

| 시험 순서 | 트리거 간격 또는 결과 | 판정 |
|---|---:|---|
| 웃음과 박수를 동시에 수행 | 박수 연속 양성 구간 부족 | 병합 불가 |
| 박수 후 웃음, 5초 정책 | `9.109초` | 범위 초과 |
| 박수 감지 직후 웃음, 5초 정책 | `10.035초` | 범위 초과 |
| 박수 감지 직후 웃음, 12초 정책 | `17.735초` | 범위 초과 |
| 웃음 감지 직후 박수, 12초 정책 | `4.253초` | 병합 성공 |

동시에 웃고 박수친 시험에서는 웃음이 박수의 짧은 충격음을 음향적으로 가려
박수 양성 구간이 1회에 그쳤다. 박수를 먼저 친 시험에서는 박수 감지는 약 2초로
빨랐지만 웃음 트리거가 늦게 발생해 병합 범위를 벗어났다. 병합 범위를 계속
늘리면 서로 관계없는 두 사건까지 하나로 합칠 위험이 있으므로, 18초 이상으로
확대하지 않았다.

### 6.2 최종 성공 시험

먼저 자연스럽게 웃고, `LAUGHTER` 감지가 확인되자 즉시 웃음을 멈춘 뒤 박수를
6~8회 쳤다.

| 항목 | 웃음 | 박수 |
|---|---|---|
| 이벤트 ID | `7f2c8252-a424-44f5-844a-7d14147730dd` | `91d7445f-63c6-4aaf-93ec-2ae01da2102b` |
| 감지 시각(UTC) | `2026-08-03T07:41:08.919Z` | `2026-08-03T07:41:13.172Z` |
| 신뢰도 | `0.213831` | `0.976288` |
| 대표 클래스 | `Laughter` | `Clapping` |

두 트리거 간격은 4.253초로 12초 정책 안에 들어왔다. 업로더는 웃음 이벤트를
대표 이벤트로 선택하고 박수 이벤트 ID를 `mergedEventIds`에 기록했다.

- 대표 이벤트 ID: `7f2c8252-a424-44f5-844a-7d14147730dd`
- 병합 이벤트 ID: `91d7445f-63c6-4aaf-93ec-2ae01da2102b`
- 서버 영상 ID: `1d21bccc-3043-42f2-9b43-03c3006ad632`
- 업로드 완료 시각: `2026-08-03T07:42:50.423Z`
- 업로드 유형: `['LAUGHTER', 'CLAP']`
- 앱 제목: `웃음과 박수가 함께 포착됐어요`

앱에서 혼합 영상이 하나만 생성된 것과 웃음·박수 유형이 함께 표시되는 것을
확인했다. 영상에는 웃음 후 박수 장면과 음성이 포함됐고 길이도 약 2분 범위였다.
업로드가 끝난 뒤 장치의 트리거와 임시 MP4 파일이 정리된 것도 확인했다.

검증 당시 원본 트리거 사본은 장치에 다음 경로로 보존했다.

```text
/home/ssafy/ai_events/diagnostics/laughter-first-20260803T074011Z-laughter.trigger.json
/home/ssafy/ai_events/diagnostics/laughter-first-20260803T074011Z-clap.trigger.json
```

## 7. 시험 중 발견한 미디어 문제

한 차례 RTSP 스트림에 AAC 트랙 정보는 있었지만 실제 오디오 패킷이 흐르지 않는
상태가 발생했다. 직접 마이크를 5초 녹음한 결과 48 kHz 모노 PCM 480,178바이트가
생성돼 마이크 하드웨어는 정상임을 확인했다. Media Source를 재시작한 뒤 RTSP
오디오 프로브에서 96,000바이트를 수신했고 YAMNet 연결도 복구됐다.

이 문제는 박수 판정 로직의 오류가 아니라 미디어 파이프라인의 일시적인 정지로
판단했다. 같은 현상이 반복되면 오디오 패킷 흐름을 주기적으로 확인하고 자동으로
Media Source를 복구하는 상태 점검 기능이 필요하다.

## 8. 최종 상태와 해석 범위

최종 시험 뒤 Device Agent, MediaMTX, Media Source, 로컬 녹화, 녹화 정리 타이머,
Edge AI 서비스가 모두 `active`였다. FFmpeg 프로세스 3개와 YOLO, YAMNet,
업로더 프로세스가 각각 1개씩 동작했다.

이번 검증으로 다음 범위는 확인됐다.

- 단발 박수는 이벤트를 만들지 않는다.
- 반복 박수는 `CLAP` 이벤트를 만든다.
- 12초 쿨다운 안의 반복 양성 판정은 새 이벤트를 만들지 않는다.
- 박수 이벤트가 서버에 업로드되고 앱에서 영상과 음성으로 재생된다.
- 웃음 감지 직후 박수친 경우 두 유형이 영상 하나로 병합된다.

다만 다음 내용을 과장해서 해석하면 안 된다.

- 모든 음량과 거리에서 박수 정확도가 검증된 것은 아니다.
- 웃음과 박수를 동시에 내는 상황에서는 박수 감지가 보장되지 않는다.
- 박수를 먼저 치고 웃는 순서는 웃음 감지 지연에 따라 12초를 넘을 수 있다.
- 현재 임계값은 한 사무실과 BRIO 100 마이크에서 얻은 운영 검증값이다.

## 9. 후속 개선 항목

- 거리, 배경 소음, 사람 수를 바꾼 반복 데이터셋을 수집한다.
- 웃음과 박수가 겹친 다중 라벨 샘플을 validation과 test에 추가한다.
- 이벤트 발생 시각과 모델 판정 시각을 분리해 감지 지연을 측정한다.
- 단순 트리거 시각 대신 오디오 구간의 실제 onset 시각을 활용한 병합을 검토한다.
- RTSP 오디오 무패킷 상태를 감지하는 헬스체크와 자동 복구를 검토한다.
- 운영 로그에서 오탐, 미탐, 쿨다운 억제 횟수를 장기적으로 수집한다.
