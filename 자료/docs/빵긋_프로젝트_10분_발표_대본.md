## 1. 기획 배경

가족과 함께하는 즐거운 순간은 대부분 예고 없이 찾아옵니다. 웃음이 발생한 순간에는 함께 웃고 있기 때문에 휴대폰을 꺼내 촬영하기 어렵고, 촬영을 시작하더라도 웃음이 발생하기 전의 상황은 이미 지나간 경우가 많습니다.

기존 홈캠을 이용하면 전체 영상을 확인할 수 있지만, 사용자가 긴 영상을 직접 돌려보면서 의미 있는 순간을 찾아야 합니다.

## 2. 사용자 관점의 서비스 이용 흐름과 주요 기능

### 기기 등록과 다중 기기 관리

사용자는 로그인한 뒤 기기의 물리 버튼을 누르고, 화면에 표시된 등록 코드를 앱에 입력하는 것만으로 기기를 연결할 수 있습니다.

한 계정에 여러 기기를 등록할 수 있기 때문에 거실, 아이 방, 부모님 댁처럼 서로 다른 공간의 기기를 앱 하나에서 선택하고 관리할 수 있습니다.

### 실시간 말하기

[Push-to-Talk 버튼 시연]

라이브 화면에서는 양방향 음성 통신도 제공합니다.

사용자가 말하기 버튼을 누르면 휴대폰의 목소리가 기기의 스피커로 전달됩니다. 집에 있는 아이나 반려동물에게 말을 걸고, 현장의 소리와 반응을 바로 확인할 수 있습니다.

사용자가 말하는 동안에는 기기에서 전달되는 수신 음량을 줄여, 스피커 소리가 다시 휴대폰 마이크로 들어가 발생하는 하울링을 줄였습니다.

### 사람 자동 추적

[카메라 앞에서 사람이 좌우로 이동]

카메라는 화면 속 사람의 위치를 파악하고 움직임을 따라 좌우와 상하로 회전합니다.

사람이 조금 움직일 때마다 카메라가 흔들리지 않도록 화면 중심에서는 움직임을 최소화했습니다. 이를 통해 사용자가 직접 카메라 방향을 조작하지 않아도 사람을 화면 안에 안정적으로 유지합니다.

### 웃음·박수 자동 감지

[웃음 또는 박수 감지 시연]

기기는 주변 소리를 분석해 웃음이나 박수가 발생한 순간을 자동으로 찾습니다.

순간적인 소음을 웃음으로 잘못 판단하지 않도록 소리가 일정하게 이어지는지 확인하고, 박수 역시 한 번의 큰 소리가 아니라 여러 번의 충격음이 함께 나타나는지 검사합니다.

호출 이름 감지 기능을 활성화한 경우에는 사용자가 등록한 이름이 들렸을 때도 별도의 이벤트를 생성할 수 있습니다.

### 추억 영상 자동 생성

웃음이나 박수를 감지한 순간부터 녹화를 시작하면, 웃음이 시작된 이유와 직전 상황을 놓치게 됩니다.

빵긋은 평소 영상을 기기 안에 임시로 보관하다가 이벤트가 발생하면 그 전후 구간만 하나의 추억 영상으로 만듭니다. 따라서 사용자는 웃음이 터진 순간뿐 아니라 그 순간으로 이어진 자연스러운 맥락까지 확인할 수 있습니다.

또한 짧은 시간 안에 같은 종류의 웃음이 여러 번 발생하면 각각의 영상으로 만들지 않고 하나의 사건으로 판단해 병합합니다. 이를 통해 비슷한 영상과 알림이 지나치게 많이 생성되는 것을 줄였습니다.

완성된 영상은 사용자의 추억 목록에 저장되며, 정상적으로 업로드가 끝난 영상만 앱에 표시됩니다.

### 알림, 영상 재생 및 편집

새로운 추억 영상이 완성되면 사용자에게 알림을 보내 바로 확인할 수 있도록 합니다.

사용자는 알림이나 영상 목록에서 영상을 확인할 수 있습니다. 영상의 제목과 메모를 작성하고 즐겨찾기에 등록할 수도 있습니다.

편집 화면에서는 영상 자르기, 화면 비율 변경, 음량 조절, 필터, 자막, 이모지 스티커 등을 적용할 수 있습니다.

한국어 음성을 인식해 자막도 자동으로 생성할 수 있습니다. 이 과정은 휴대폰 안에서 처리해 가족의 대화 음성을 외부로 보내지 않습니다. 편집된 영상은 갤러리에 저장하거나 다른 앱으로 공유할 수 있습니다.

### 캘린더, 웃음 리포트와 가족 공유

앱에서는 캘린더를 통해 날짜별 이벤트 영상을 확인할 수 있습니다.

또한 이번 주와 지난주의 웃음 횟수, 가장 많이 웃은 요일, 요일별 웃음 분포 등을 보여주어 단순히 홈캠 영상을 저장하는 것을 넘어 가족의 일상을 하나의 긍정적인 기록으로 표현합니다.

또한 가족을 초대하면 구성원들이 같은 추억 금고에서 영상을 함께 확인할 수 있습니다.

## 3. 기술 선택 이유 및 A/B 테스트

### 로깅 대시보드

저희는 목적이 다른 두 개의 로깅 대시보드를 제작했습니다. 첫 번째 서보·비전 진단 대시보드는 YOLO가 탐지한 객체 위치와 추적 명령, 팬·틸트 각도, YAMNet 웃음 점수, 이벤트 영상의 생성과 업로드 단계를 실시간으로 확인합니다. 이를 통해 AI 감지부터 하드웨어 제어와 영상 업로드까지 어느 구간에서 문제가 발생했는지 추적했습니다. 두 번째 WJ Edge Observatory는 모델별 FPS와 P95 지연, Precision, Recall, F1, mAP뿐 아니라 Jetson의 GPU, RAM, 온도와 전력 사용량을 비교합니다. 동일한 데이터셋과 조건에서 모델을 반복 실행하고 정확도와 자원 사용량을 함께 비교해 YOLO와 YAMNet을 선정하는 근거로 사용했습니다.

### HLS와 WebRTC 비교

초기 라이브 스트리밍에는 HLS를 사용했습니다.

HLS는 영상을 여러 개의 파일 조각으로 만든 뒤 순서대로 전달하기 때문에 안정적이지만, 영상을 일정 시간 모아서 조각으로 만들어야 합니다. 그 결과 실제 상황과 앱 화면 사이에 약 5~6초의 지연이 발생했습니다.

[HLS와 WebRTC 타이머 비교 화면 제시]

특히 양방향 음성에서는 사용자가 말한 뒤 상대방의 반응을 보기까지 수 초가 걸리면 자연스러운 대화가 어렵습니다.

따라서 실시간성을 우선하여 WebRTC로 변경했고, 앱의 영상 수신에는 WHEP, 휴대폰 음성 송신에는 WHIP를 사용했습니다.

### YOLO 및 YAMNet 선택

영상 모델은 Jetson에서 동일한 조건으로 YOLOv8n, YOLO11n, YOLO26n을 비교했습니다.

실험 결과 YOLOv8n은 약 28.2 FPS로 다른 후보보다 높은 실시간 처리 성능을 보였습니다. 홈캠의 자동 추적은 아주 복잡한 객체 분류보다 사람의 위치를 빠르게 찾는 것이 중요했기 때문에 YOLOv8n을 채택했습니다.

음향 모델은 YAMNet과 EfficientAT를 비교했습니다. YAMNet은 평가 데이터에서 Recall 1.0을 유지하면서 CPU 처리 시간이 EfficientAT보다 약 4배 빨랐습니다.

더 큰 서버 모델을 사용하면 다양한 AI를 적용할 수 있지만, 영상과 음성을 서버로 계속 보내면 지연, 네트워크 비용과 개인정보 문제가 발생합니다. 저희가 필요한 사람 추적과 웃음 감지는 Jetson에서도 처리할 수 있었기 때문에 Edge AI로 구성했습니다.

### 객체 인식 및 추적
초기에는 YOLO 모델이 인식한 사람 바운딩박스 전체를 기준으로 ByteTrack을 사용해서 중앙에 홈캠의 포커스가 위치하도록 했습니다. 
그러나 사람 바운딩박스 전체를 기준으로 하자 홈캠의 수직 이동이 거의 없는 문제가 발생했고, 이에 사람 바운딩박스를 통합하고, 위쪽 부분 0.35를 포커스 하는 것으로 전환했습니다.
또한 프레임당 계산하는 YOLO모델의 계산 점수 등락과 사람의 조금의 움직임에도 민감하게 홈캠이 반응하여 계속해서 움직이는 현상이 발생했습니다.
이를 막기 위해 통합 바운딩 박스 방식은 유지하되, 사람 바운딩 박스 각각의 중심이 홈캠의 세이프티 영역에 위치해 있으면 포커스를 옮기지 않는 형식으로 통합했습니다.

## 4. 전체 아키텍처

### 전체 서비스 동작 구조

[전체 아키텍처 이미지 제시]

앞에서는 사용자가 경험하는 기능을 중심으로 설명드렸다면, 이제 그 기능들이 내부에서 어떻게 연결되는지 아키텍처를 통해 설명드리겠습니다.

전체 구조는 기기 영역, 서버 영역, Flutter 앱으로 구분됩니다.

먼저 기기 내부에서는 FFmpeg가 카메라와 마이크를 한 번만 열어 인코딩하고, 로컬 MediaMTX가 스트림을 녹화 프로그램, YOLO, YAMNet에 분배합니다.

YOLO는 사람의 위치를 계산해 서보모터가 카메라 방향을 조절하도록 하고, YAMNet은 웃음과 박수를 감지합니다. 화면 중심에는 데드존을 두어 작은 움직임에는 모터가 반응하지 않도록 했고, 소리 감지 결과가 일정 횟수 이상 이어질 때만 이벤트로 판단해 오탐을 줄였습니다.

기기는 평상시 영상을 60초 단위로 순환 저장합니다. YAMNet이 이벤트를 감지하면 종류, 발생 시각과 전후 영상 길이가 담긴 트리거를 만들고, 로컬 업로더가 해당 구간을 찾아 FFmpeg로 하나의 MP4를 생성합니다. 가까운 시간에 같은 이벤트가 반복되면 하나의 사건으로 병합해 비슷한 영상과 알림이 쌓이지 않도록 했습니다.

기기와 Spring 서버의 일반 API 통신은 HTTPS를 사용하고, 라이브 시작과 종료 같은 제어 명령은 MQTTS로 Mosquitto를 통해 전달합니다.

사용자가 라이브를 시작하면 서버는 먼저 접근 권한을 확인한 뒤 MQTT로 기기에 시작 명령을 보냅니다. 앱은 시청 중이라는 신호를 약 15초마다 보내고, 정상 종료 시에는 서버가 종료 명령을 전달합니다. 앱이 강제 종료되거나 네트워크가 끊겨도 신호가 멈추고 제한 시간이 지나면 기기가 스스로 송출을 종료합니다.

기기가 실시간 영상을 서버로 보낼 때는 RTSPS를 사용하고, 앱이 실시간 영상을 재생할 때는 WebRTC와 WHEP를 사용합니다. 앱에서 기기로 보내는 음성에는 WebRTC와 WHIP를 사용합니다.

이벤트 영상 파일은 Spring 서버를 거치지 않고 Presigned HTTPS URL을 통해 MinIO에 직접 업로드합니다. 업로드가 끝나면 서버가 파일 크기와 SHA-256 체크섬을 확인하고, 정상적으로 완료된 영상만 앱에 공개합니다.

서버에서는 Nginx 하나가 기기와 앱의 HTTPS 요청을 함께 받습니다. Spring Boot는 사용자 인증과 권한, 기기, 라이브 세션과 영상 메타데이터를 관리합니다.

기기 등록에서는 기기 자체를 인증하는 토큰과 사용자의 소유권을 연결하는 일회성 코드를 분리했습니다. 사용자는 2분 동안 유효한 코드를 입력해 기기를 등록하고, 서버는 코드의 만료와 재사용 여부를 검사합니다. 각 기기와 영상, 라이브 세션은 고유한 기기 식별자로 구분하며, 식별자뿐 아니라 실제 구성원 권한까지 함께 확인합니다.

PostgreSQL은 사용자, 기기, 권한, 영상 정보처럼 영구적으로 보관해야 하는 관계형 데이터를 저장합니다.

Redis는 MQTT heartbeat로 자주 변경되는 기기 상태를 90초 TTL로 관리하고, 로그인과 기기 등록 시도 횟수를 제한합니다.
