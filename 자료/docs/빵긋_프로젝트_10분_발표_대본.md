## 1. 기획 배경

### 0:25~1:10 — 해결하려는 문제와 프로젝트 목표

가족과 함께하는 즐거운 순간은 대부분 예고 없이 찾아옵니다. 웃음이 발생한 순간에는 함께 웃고 있기 때문에 휴대폰을 꺼내 촬영하기 어렵고, 촬영을 시작하더라도 웃음이 발생하기 전의 상황은 이미 지나간 경우가 많습니다.

기존 홈캠을 이용하면 전체 영상을 확인할 수 있지만, 사용자가 긴 영상을 직접 돌려보면서 의미 있는 순간을 찾아야 합니다. 또한 모든 영상을 계속 외부 서버에 전송하고 저장하면 개인정보와 저장 비용 문제도 발생합니다.

그래서 저희는 다음과 같은 목표를 세웠습니다.

> 집 안의 AI가 웃음이나 박수 같은 의미 있는 순간을 자동으로 찾고, 해당 순간의 전후 영상만 추억으로 만들어 사용자에게 전달하자.

주요 사용자는 어린 자녀가 있는 가족, 반려동물과 함께 생활하는 사용자, 떨어져 사는 부모님의 일상을 공유하고 싶은 가족입니다.

## 2. 사용자 관점의 서비스 이용 흐름과 주요 기능

이제 사용자가 실제로 서비스를 이용하는 순서에 따라 주요 기능을 설명드리겠습니다.

### 1:35~2:00 — 기기 등록과 소유권 연결

사용자가 로그인 후 기기의 물리 버튼을 누르면 기기 화면에 2분 동안 사용할 수 있는 일회성 등록 코드가 표시됩니다. 사용자가 앱에 이 코드를 입력하면 서버는 코드의 유효기간과 사용 여부를 확인하고 기기와 사용자를 연결합니다.

최초 등록자는 해당 기기와 추억 금고의 `OWNER`가 됩니다. 등록 코드는 한 번 사용하면 다시 사용할 수 없고, 2분이 지나면 자동으로 만료됩니다.

여기서 기기의 신원을 확인하는 과정과 사용자가 기기의 소유자임을 등록하는 과정은 분리했습니다. 즉, 서버가 정식 기기임을 확인하는 것과 사용자가 해당 기기의 주인임을 증명하는 것은 서로 다른 문제로 처리했습니다.

### 2:00~2:15 — 다중 기기 관리

한 명의 사용자는 여러 기기를 등록할 수 있습니다.

예를 들어 거실, 아이 방, 부모님 댁에 각각 기기를 설치하고 앱에서 원하는 기기를 선택할 수 있습니다. 서버는 각 기기에 서로 다른 UUID를 부여하고, 영상과 라이브 세션, MQTT 토픽을 모두 이 `deviceId`로 구분합니다.

또한 UUID만 아는 것으로 접근할 수 없도록, 사용자가 해당 기기 또는 추억 금고의 구성원인지 권한도 함께 검사합니다.

### 2:15~3:05 — 라이브 영상 시청 시연

[앱에서 라이브 화면 진입]

이제 실제 라이브 기능을 보여드리겠습니다.

사용자가 라이브 버튼을 누르면 앱이 서버에 라이브 세션 생성을 요청합니다. 서버는 사용자가 해당 기기를 볼 수 있는지 권한을 확인한 뒤, MQTT를 통해 기기에 라이브 시작 명령을 전달합니다.

기기는 명령을 받으면 MediaMTX로 RTSPS 영상을 송출하고, 준비가 완료됐다는 응답을 서버에 보냅니다. 이후 앱은 WebRTC로 실시간 영상을 재생합니다.

[라이브 영상 재생 확인]

앱은 라이브를 시청하는 동안 약 15초마다 서버에 heartbeat를 보냅니다. 이 heartbeat는 앱 전체가 살아 있는지 확인하는 신호가 아니라, 사용자가 현재 이 라이브 세션을 계속 시청하고 있다는 것을 증명하는 신호입니다.

앱이 정상적으로 화면을 닫으면 세션 종료 API가 호출되고 서버가 기기에 MQTT `STOP` 명령을 보냅니다.

하지만 앱이 강제 종료되거나 네트워크가 끊기면 종료 API가 전달되지 않을 수 있습니다. 이때 heartbeat가 중단되면서 서버가 더 이상 세션을 연장하지 않고, 기기는 마지막으로 전달받은 `hardExpiresAt`이 지나면 스스로 스트리밍을 종료합니다.

따라서 정상 종료와 비정상 종료를 모두 처리할 수 있습니다.

### 3:05~3:25 — 양방향 음성 통신

[Push-to-Talk 버튼 시연]

라이브 화면에서는 양방향 음성 통신도 제공합니다.

사용자가 말하기 버튼을 누르면 휴대폰의 마이크 음성이 WebRTC의 WHIP 경로를 통해 MediaMTX로 전달되고, 기기의 스피커에서 재생됩니다.

사용자가 말하는 동안에는 기기에서 전달되는 수신 음량을 줄여, 스피커 소리가 다시 휴대폰 마이크로 들어가 발생하는 하울링을 줄였습니다.

### 3:25~3:45 — YOLO 기반 사람 추적

[카메라 앞에서 사람이 좌우로 이동]

기기에서는 YOLO가 카메라 영상을 분석하며 사람의 위치를 찾습니다.

사람이 화면 중심에서 벗어나면 YOLO가 이동 방향을 계산하고, 서보모터 제어 프로그램이 카메라를 좌우 또는 상하로 움직입니다.

화면 중앙에는 데드존을 두었습니다. 사람이 데드존 안에 있을 때는 모터를 움직이지 않도록 하여, 사람의 위치가 조금씩 변할 때마다 카메라가 계속 떨리는 문제를 줄였습니다.

YOLO의 역할은 이벤트 영상을 생성하는 것이 아니라, 사람을 화면 안에 유지하는 자동 프레이밍입니다.

### 3:45~4:10 — YAMNet 기반 웃음·박수 감지

[웃음 또는 박수 감지 시연]

마이크에서 들어오는 소리는 YAMNet이 분석합니다.

YAMNet은 입력된 소리에 대해 웃음, 말소리, 음악, 박수 등 여러 소리의 가능성을 점수로 반환합니다.

한 번 기준값을 넘었다고 바로 이벤트를 생성하지는 않습니다. 순간적인 소음을 웃음으로 잘못 판단할 수 있기 때문에, 임계값을 넘는 결과가 일정 횟수 이상 연속으로 발생했는지 확인합니다.

박수는 YAMNet의 분류 점수뿐 아니라 실제 충격음이 여러 번 발생했는지도 함께 검사하여, 문이 닫히는 소리와 같은 단발성 충격음을 박수로 오인하는 것을 줄였습니다.

호출 이름 감지 기능을 활성화한 경우에는 사용자가 등록한 이름이 들렸을 때도 별도의 이벤트를 생성할 수 있습니다.

[여기서 실제 시연 종료]

### 4:10~4:45 — 이벤트 영상 생성 및 업로드

AI가 웃음이나 박수를 감지했다고 해서 그 순간부터 녹화를 시작하는 것은 아닙니다.

기기에서는 평상시 영상을 60초 단위 파일로 계속 순환 저장합니다. 이벤트가 발생하면 YAMNet이 이벤트 종류, 발생 시각, 신뢰도, 전후 영상 길이가 포함된 트리거 JSON을 로컬 폴더에 생성합니다.

별도의 로컬 업로더가 이 폴더를 1초마다 확인합니다. 새로운 트리거가 발견되면 미리 녹화된 파일에서 이벤트 전후 구간을 찾고 FFmpeg로 하나의 MP4를 생성합니다.

이 구조를 사용한 이유는 웃음이 감지된 순간부터 녹화하면 웃음이 발생하게 된 직전 상황을 놓치기 때문입니다.

또한 짧은 시간 안에 같은 종류의 웃음이 여러 번 발생하면 각각의 영상으로 만들지 않고 하나의 사건으로 판단해 병합합니다. 이를 통해 비슷한 영상과 알림이 지나치게 많이 생성되는 것을 줄였습니다.

MP4가 완성되면 기기는 Spring 서버에 영상 정보를 전달하고 Presigned URL을 발급받습니다. 실제 MP4는 Spring을 거치지 않고 MinIO에 직접 업로드됩니다.

업로드가 끝나면 서버가 실제 파일의 크기와 SHA-256 체크섬을 확인합니다. 정상적으로 일치한 영상만 `READY` 상태로 변경하여 손상되거나 일부만 업로드된 영상이 앱에 노출되는 것을 방지합니다.

### 4:45~5:15 — 알림, 영상 재생 및 편집

웃음 영상이 `READY` 상태가 되면 사용자에게 알림이 생성되고, 푸시 토큰이 등록되어 있다면 FCM 푸시 알림도 전송합니다.

사용자는 알림이나 영상 목록에서 영상을 확인할 수 있습니다. 영상의 제목과 메모를 작성하고 즐겨찾기에 등록할 수도 있습니다.

편집 화면에서는 영상 자르기, 화면 비율 변경, 음량 조절, 필터, 자막, 이모지 스티커 등을 적용할 수 있습니다.

자막은 한국어 Whisper 모델을 휴대폰에서 직접 실행해 생성합니다. 가족의 대화 음성을 별도의 STT 서버로 전송하지 않아 개인정보를 보호할 수 있고, 편집된 영상은 휴대폰 갤러리에 저장하거나 다른 앱으로 공유할 수 있습니다.

### 5:15~5:30 — 캘린더, 웃음 리포트와 가족 공유

앱에서는 캘린더를 통해 날짜별 이벤트 영상을 확인할 수 있습니다.

또한 이번 주와 지난주의 웃음 횟수, 가장 많이 웃은 요일, 요일별 웃음 분포 등을 보여주어 단순히 홈캠 영상을 저장하는 것을 넘어 가족의 일상을 하나의 긍정적인 기록으로 표현합니다.

커뮤니티 기능 대신 현재는 가족 초대와 추억 금고 공유를 제공합니다. `OWNER`가 가족을 초대하면 구성원들이 같은 추억 영상을 함께 확인할 수 있습니다.

## 3. 기술 선택 이유 및 A/B 테스트

### 5:30~5:50 — 로깅 대시보드

저희는 목적이 다른 두 개의 로깅 대시보드를 제작했습니다. 첫 번째 서보·비전 진단 대시보드는 YOLO가 탐지한 객체 위치와 추적 명령, 팬·틸트 각도, YAMNet 웃음 점수, 이벤트 영상의 생성과 업로드 단계를 실시간으로 확인합니다. 이를 통해 AI 감지부터 하드웨어 제어와 영상 업로드까지 어느 구간에서 문제가 발생했는지 추적했습니다. 두 번째 WJ Edge Observatory는 모델별 FPS와 P95 지연, Precision, Recall, F1, mAP뿐 아니라 Jetson의 GPU, RAM, 온도와 전력 사용량을 비교합니다. 동일한 데이터셋과 조건에서 모델을 반복 실행하고 정확도와 자원 사용량을 함께 비교해 YOLO와 YAMNet을 선정하는 근거로 사용했습니다.

### 5:50~6:15 — HLS와 WebRTC 비교

초기 라이브 스트리밍에는 HLS를 사용했습니다.

HLS는 영상을 여러 개의 파일 조각으로 만든 뒤 순서대로 전달하기 때문에 안정적이지만, 영상을 일정 시간 모아서 조각으로 만들어야 합니다. 그 결과 실제 상황과 앱 화면 사이에 약 5~6초의 지연이 발생했습니다.

[HLS와 WebRTC 타이머 비교 화면 제시]

특히 양방향 음성에서는 사용자가 말한 뒤 상대방의 반응을 보기까지 수 초가 걸리면 자연스러운 대화가 어렵습니다.

따라서 실시간성을 우선하여 WebRTC로 변경했고, 앱의 영상 수신에는 WHEP, 휴대폰 음성 송신에는 WHIP를 사용했습니다.

### 6:15~6:40 — YOLO 및 YAMNet 선택

영상 모델은 Jetson에서 동일한 조건으로 YOLOv8n, YOLO11n, YOLO26n을 비교했습니다.

실험 결과 YOLOv8n은 약 28.2 FPS로 다른 후보보다 높은 실시간 처리 성능을 보였습니다. 홈캠의 자동 추적은 아주 복잡한 객체 분류보다 사람의 위치를 빠르게 찾는 것이 중요했기 때문에 YOLOv8n을 채택했습니다.

음향 모델은 YAMNet과 EfficientAT를 비교했습니다. YAMNet은 평가 데이터에서 Recall 1.0을 유지하면서 CPU 처리 시간이 EfficientAT보다 약 4배 빨랐습니다.

더 큰 서버 모델을 사용하면 다양한 AI를 적용할 수 있지만, 영상과 음성을 서버로 계속 보내면 지연, 네트워크 비용과 개인정보 문제가 발생합니다. 저희가 필요한 사람 추적과 웃음 감지는 Jetson에서도 처리할 수 있었기 때문에 Edge AI로 구성했습니다.

### 6:40~7:05 — HTTP Polling과 MQTT 비교

서버와 기기의 제어 통신에는 HTTP 대신 MQTT를 사용했습니다.

HTTP는 기기가 서버로 요청을 보내기에는 적합하지만, 서버가 공유기 내부의 기기로 먼저 명령을 보내기는 어렵습니다. 가정용 기기는 사설 IP와 NAT 뒤에 있고 IP가 변경될 수 있기 때문입니다.

HTTP만 사용한다면 기기가 서버에 주기적으로 새 명령이 있는지 물어보는 polling이 필요합니다. 명령이 없어도 요청이 반복되고, 확인 주기만큼 반응이 늦어집니다.

MQTT에서는 기기가 먼저 브로커와 연결을 유지하고 자신의 명령 토픽을 구독합니다. 서버가 메시지를 발행하면 기기가 이벤트 기반으로 바로 받을 수 있습니다.

영상 파일은 크기가 크므로 MQTT로 보내지 않고, MQTT는 라이브 시작·종료 명령, 기기 heartbeat와 상태 같은 작은 메시지에만 사용했습니다.

### 7:05~7:20 — RTSPS 선택

기기에서 서버의 MediaMTX로 보내는 실시간 영상에는 RTSPS를 사용했습니다.

RTSP는 실시간 미디어 송출을 제어하기에 적합하지만, 평문 RTSP만 사용하면 영상과 인증 정보가 네트워크에 노출될 수 있습니다.

따라서 RTSP에 TLS를 적용한 RTSPS를 사용해 서버 인증서를 검증하고 전송 구간을 암호화했습니다. 또한 기기 계정은 자신의 라이브 경로에만 영상을 발행할 수 있도록 publish-only 권한을 적용했습니다.

### 7:20~7:45 — 기기 인증 토큰 분리

초기에는 하나의 영구 토큰을 계속 사용하는 구조를 고려했지만, 토큰이 유출됐을 때 계속 악용될 수 있다는 문제가 있었습니다.

현재는 기기의 최초 등록을 위한 15분짜리 Bootstrap Token과 실제 운영에 사용하는 30일짜리 Operating Token을 분리했습니다.

기기는 Bootstrap Token으로 최초 Enrollment를 수행하고, 서버가 정식 기기임을 확인하면 Operating Token으로 교환합니다. 이후 Bootstrap Token은 폐기됩니다.

사용자가 기기의 소유권을 등록할 때는 이 토큰을 앱에 전달하지 않고, 별도의 2분짜리 일회성 등록 코드를 사용합니다.

```text
Bootstrap Token → 기기의 최초 서버 등록
Operating Token → 운영 중 HTTP·MQTT 인증
등록 코드 → 사용자와 기기의 소유권 연결
```

서버에는 운영 토큰 원문 대신 SHA-256 해시만 저장하며, 운영 토큰 회전과 폐기도 지원합니다.

## 4. 전체 아키텍처

### 7:45~8:35 — 프로토콜 중심 아키텍처 설명

[전체 아키텍처 이미지 제시]

전체 구조는 기기 영역, 서버 영역, Flutter 앱으로 구분됩니다.

먼저 기기 내부에서는 FFmpeg가 카메라와 마이크를 한 번만 열어 인코딩하고, 로컬 MediaMTX가 스트림을 녹화 프로그램, YOLO, YAMNet에 분배합니다.

YAMNet이 이벤트를 감지하면 로컬 트리거 JSON을 만들고, 업로더가 녹화 파일에서 이벤트 전후 구간을 MP4로 생성합니다.

기기와 Spring 서버의 일반 API 통신은 HTTPS를 사용하고, 라이브 시작과 종료 같은 제어 명령은 MQTTS로 Mosquitto를 통해 전달합니다.

기기가 실시간 영상을 서버로 보낼 때는 RTSPS를 사용하고, 앱이 실시간 영상을 재생할 때는 WebRTC와 WHEP를 사용합니다. 앱에서 기기로 보내는 음성에는 WebRTC와 WHIP를 사용합니다.

이벤트 영상 파일은 Presigned HTTPS URL을 통해 MinIO에 직접 업로드합니다.

서버에서는 Nginx 하나가 기기와 앱의 HTTPS 요청을 함께 받습니다. Spring Boot는 사용자 인증과 권한, 기기, 라이브 세션과 영상 메타데이터를 관리합니다.

PostgreSQL은 사용자, 기기, 권한, 영상 정보처럼 영구적으로 보관해야 하는 관계형 데이터를 저장합니다.

Redis는 MQTT heartbeat로 자주 변경되는 기기 상태를 90초 TTL로 관리하고, 로그인과 기기 등록 시도 횟수를 제한합니다.

정리하면 다음과 같습니다.

> AI는 기기에서 처리하고, 명령은 MQTT, 실시간 송출은 RTSPS, 앱 재생은 WebRTC, 영상 파일은 HTTPS로 처리했습니다.
