# 빵긋 AI 활용 자기평가

## (1) AI 활용 방식

**3단계**: 사전학습 모델을 단순 호출하는 수준을 넘어, 엣지 디바이스 런타임에 맞춰 모델을 선정·교체하고 TensorRT FP16 추론과 온디바이스 파이프라인을 실제 운영 코드에 적용했다.

- Jetson Orin Nano에서 YOLO+ByteTrack이 사람·고양이·강아지를 추적하고, 오디오 판정기가 웃음을 감지해 자동으로 클립을 만든다. 모든 추론이 서버가 아니라 가정 내 디바이스에서 끝난다.
- YOLO 운영 코드는 `.pt`와 `.engine`을 구분해 TensorRT 엔진을 우선 선택한다. 엔진은 파일 존재 여부만 보지 않고 SHA-256 검증과 실제 640×640 더미 입력 추론 probe를 통과해야 채택된다. 엄격한 `tensorrt` 모드에서는 검증 실패를 PyTorch fallback으로 숨기지 않는다.
- **운영 오디오 판정기를 YAMNet에서 EfficientAT MN10으로 교체했다.** 자체 수집 데이터로 두 모델을 비교하고, 3일간 섀도 검증을 거친 뒤 이벤트 권한을 이양했다. 상세는 아래 (1-1)에 적는다.
- 모바일 자동 자막도 서버 호출형 STT가 아니라 Android ML Kit Basic 음성 인식으로 16kHz mono WAV를 폰 안에서 처리한다. 같은 홈캠 클립에서 ML Kit은 CER 23.3%·약 18초, 폐기한 Whisper 경로는 CER 35.0%·약 235초였다. 정확도와 속도가 동시에 유리해 온디바이스 경로를 채택했다.

### (1-1) YAMNet → EfficientAT MN10 교체

운영 모델을 바꾸는 일은 되돌리기 어렵기 때문에, 세 단계를 나눠 진행했다.

**1단계 — 비교 근거 확보.** 자체 수집한 오디오 평가셋으로 YAMNet과 EfficientAT MN10을 같은 조건에서 측정했다. 평가 구성은 validation 60개, test 2,064개이며 test에는 자체 10초 음성 60개, 자체 연속 음성 60분(15분×4), ESC-50 2,000개가 포함된다. 전체 2,124개가 검증 완료 상태이고 split 간 중복도 검사했다.

**2단계 — 섀도 검증(3일).** EfficientAT을 YAMNet과 **같은 RTSP 오디오**에 붙여 동시에 돌리되, 점수와 가상 이벤트만 기록하게 했다. 이 기간 섀도 실행기에는 trigger·MQTT·업로드 인자가 존재하지 않아 구조적으로 이벤트를 만들 수 없었다. 두 모델의 판정을 12초 범위에서 대조해 단독 발화 구간을 수동 검수했다.

**3단계 — 권한 이양.** `AUDIO_EVENT_MODEL` 환경변수 하나가 이벤트 권한을 가진 판정기를 고르도록 런처를 바꿨다. 값은 `efficientat`(기본), `yamnet`(롤백), `none`(오디오 이벤트 중단) 세 가지다. 런처가 이 값 하나에서 기동 플래그와 권한 플래그를 모두 파생시키므로, **두 판정기가 같은 소리로 트리거를 두 번 쓰는 조합이 존재하지 않는다.** `efficientat`일 때 YAMNet은 기동조차 하지 않는다.

교체를 안전하게 만든 설계 결정 네 가지:

1. **트리거 포맷 재사용** — EfficientAT이 YAMNet과 동일한 트리거 작성 함수를 그대로 쓴다. 덕분에 클립 추출·병합·업로드 경로는 한 줄도 바뀌지 않았고, 업로더는 생산자가 누구인지 알 필요가 없다.
2. **Fail-closed 인자 검증** — 이벤트 생성 인자를 `--operational` 없이 주면 무시하는 게 아니라 거부한다. 섀도 실행이 실수로 실제 이벤트를 만드는 경로를 없앴다.
3. **MQTT 식별자 분리** — 클라이언트 ID와 상태 메시지의 component를 하드코딩에서 인자로 뺐다. 두 판정기가 같은 ID를 쓰면 서로의 연결을 끊고, retained 상태 메시지가 살아 있는 판정기를 offline으로 표시한다.
4. **진단 스키마 유지** — EfficientAT이 기존 판정 키를 같은 이름으로 남기게 해서, 서보 대시보드와 기동 준비 확인 로직이 분기 없이 그대로 동작한다.

운영 임계값은 웃음 0.03, 박수 0.08725224, 연속 양성 창 각 1개, 쿨다운 12초, context 10초, hop 2.5초다. 박수 이벤트 발행은 백엔드 계약 배포 전까지 차단해 두었고, YAMNet 코드와 자산은 롤백 경로로 저장소에 남겼다.

감도는 사용자가 세 단계로 고를 수 있다. 민감 0.12, 기본 0.15, 둔감 0.30이다. 단계 간격을 균등하게 두지 않았다. 각 값은 실측 분포에서 "말소리 창이 넘는 비율 / 웃음 창이 넘는 비율"을 보고 골랐다.

임계값을 정하는 방식 자체를 두 번 바꿨다. 처음에는 튜닝 스크립트의 검증셋 argmax(0.01691491)를 썼는데 실기기에서 평범한 실내 대화에 발화했다. 다음에는 눈으로 관찰한 점수 몇 개(대화 0.072, 웃음 0.229~0.293)에 맞춰 조정했다. 이것도 틀렸다.

결정적인 건 진단 로그 **112,724창 전수 분석**이었다. 말소리가 지배한 창 79,624개의 중앙값은 0.0009지만 상위 1%가 0.1166, 최대가 0.4463이었다. 관찰한 값 몇 개는 이 분포의 꼬리를 전혀 대표하지 못했다. 실제로 임계값 0.08에서 나간 발화 471건 중 **98.7%가 말소리**였다.

**표본 몇 개로 정한 운영점은 분포의 꼬리에서 무너진다**는 것이 이 프로젝트에서 배운 가장 비싼 교훈이다. 지금은 임계값을 바꿀 때 반드시 전수 로그를 다시 본다.

임계값만으로 못 막는 구간도 확인했다. 말소리가 창을 지배하는데 웃음 점수만 살짝 넘는 경우로, 오발화 창의 우세 비율(웃음 점수 ÷ 창 최대 점수) 중앙값이 0.057이었다. 1등 소리의 6%짜리 근거로 이벤트가 나가고 있었다. 이건 임계값을 어디에 두든 고쳐지지 않아서, 우세 비율 조건을 넣되 실측 근거가 없으므로 꺼둔 채로 창마다 값만 기록하게 했다. 다음 재보정 때 사후 스윕으로 운영점을 고른다.

## (2) 데이터 활용

**3단계**: 공개 데이터셋만 쓰지 않고 실제 서비스 환경에서 자체 데이터를 수집했으며, 조건·split·길이·표본 수를 고정한 샘플링 절차를 적용했다. 이 데이터가 모델 교체 판단의 근거가 됐다.

- 자체 오디오 수집 항목은 웃음 단독, 연속 박수, 웃음+박수, 대화, 단발 충격음, TV·음악·생활 소음의 6개 시나리오로 구성된다. 다인 웃음, 거리 변화, 박수 순서, 혼합 이벤트 순서까지 수집 지시에 포함했다.
- validation과 test를 서로 다른 세션·take로 분리하고, split별 60개·시나리오별 10개·총 120개를 강제한다. 각 파일은 PCM S16LE, mono, 48kHz, 정확히 10초로 생성하며 리샘플·패딩·트림으로 표본 수를 고정한다. 길이가 흔들리면 모델 간 비교가 성립하지 않기 때문이다.
- 공개 데이터셋은 자체 데이터를 대체하지 않고 보강한다. test 2,064개 중 ESC-50 2,000개는 생활 소음 오탐을 넓게 보기 위한 것이고, 실제 판정 품질은 자체 홈캠 녹음으로 확인했다.
- 비전 평가도 직접 구축한 데이터셋을 썼다. 395장, 사람 박스 581개, 빈 장면 52장, 중복 이미지 0장으로 구성하고 모델별 3회씩 총 9회 반복 측정했다.

## (3) 모델 적용 방식

**3단계**: 실제 서비스의 Gemini 2단계 멀티모달 생성 경로에 구조화 출력과 제약 기반 프롬프트 엔지니어링을 적용했다.

- 만화 생성은 두 모델을 이어 붙인다. 먼저 `gemini-3.5-flash`가 영상에서 4컷 구성을 만들고, `gemini-2.5-flash-image`가 그림을 생성한다.
- 첫 단계 프롬프트는 시간 정보가 붙은 전사문과 영상 프레임을 함께 입력한다. 응답을 자유 텍스트로 받지 않고 JSON Schema를 지정해 인물·배경·**정확히 4개의 컷**으로 출력 형태를 강제한다.
- 이미지 프롬프트에는 문자·숫자·로고·말풍선 배제, 2×2 읽기 순서, 인물 일관성 유지, 컷별 정지 장면 규칙을 넣었다. 모델 출력도 컷 수와 필수 필드를 검사해 계약 위반이면 거절한다. 생성 모델을 신뢰하지 않고 계약으로 다루는 방식이다.
- 오디오 판정기는 임계값을 임의로 정하지 않고 validation split에서 탐색해 확정했다. 모델을 교체할 때도 같은 절차로 운영점을 다시 잡았다.

## (4) 서비스 연계성

**2단계**: AI가 자동 포착·자동 자막·편집 추천이라는 핵심 기능을 담당한다.

- 프로젝트의 대표 가치가 "웃긴 순간을 Jetson 엣지 AI가 자동 포착"하는 것이다. MVP 4단계는 웃음 감지→클립 생성→업로드→앱 재생으로 이어지고, MVP 5단계에도 온디바이스 STT와 서버 자동 편집 추천이 들어간다.
- 웃음 감지는 이벤트 UUID를 만들고 최초 감지 60초 전부터 마지막 감지 60초 후까지 MP4로 추출해 서버로 전송한다. 반복 이벤트는 30초 내 병합하고, 웃음과 박수는 5초 내 병합한다.
- 자동 편집 추천은 오디오·음량·영상·표정 분석을 결합해 편집 recipe를 만들고, 앱 편집 화면이 이를 호출해 편집 프로젝트에 반영한다.
- 다만 회원가입·기기 등록·라이브 시청·수동 편집·다운로드는 AI 프로세스와 분리된 독립 서비스 단위로 동작한다. AI가 멈춰도 이 흐름은 유지되므로 "AI가 없으면 서비스 전체가 성립하지 않는다"까지는 주장하지 않는다.

## (5) 경량화

**3단계**: 비전과 오디오 두 축 모두 엣지 디바이스 제약에 맞춰 모델을 경량화하고, 추론 지연·처리량·자원 사용량을 수치로 검증했다.

- **비전**: YOLOv8n을 TensorRT FP16, batch 1, 640×640 엔진으로 변환해 운영한다. Jetson Orin Nano 25W 모드에서 평균 27.095 FPS, Wall P95 39.303ms, Recall 96.56%, mAP50-95 81.3%를 기록했다. 운영점 F1은 96.72%(FP 18건, FN 20건)다.
- **자원 실측**: 최대 GPU 85%, RAM 3,309MB, 온도 53.656°C, 보드 입력 전력 5.475W. 가정용 기기라 발열과 전력이 정확도만큼 중요한 제약이었다.
- **오디오**: 모바일 환경을 겨냥해 설계된 EfficientAT MN10을 CUDA FP16으로 추론한다. context 10초를 hop 2.5초로 겹쳐 처리해 연산량을 늘리지 않으면서 짧은 웃음을 놓치지 않게 했다.
- **파이프라인**: 미디어 입력을 한 번만 H.264/AAC로 인코딩한 뒤 YOLO·오디오·라이브·로컬 RTSP로 분기한다. 같은 영상을 네 번 인코딩하지 않기 위해서다. YOLO 입력은 지연이 쌓이지 않도록 최신 프레임만 유지한다.
- **측정 신뢰성**: 벤치마크 대시보드는 수치가 없을 때 추정값을 채우지 않고 `N/A`로 표시하며, 완료된 결과 파일만 비교한다. 처리량·지연·정확도와 자원 사용량을 분리해 표시한다.

## 현재 검증 상태

정직하게 남겨 둘 항목을 함께 기록한다.

- EfficientAT 교체는 저장소 코드와 테스트로 종단 연결이 확인됐으나, 교체 이후의 현장 오탐율은 운영 로그로 다시 확인해야 한다.
- 작은 웃음, 아기·어린이 웃음, 거리별 성능, TV·스피커 재생음 억제는 이번 교체로 검증되지 않았다.
- 박수 이벤트는 백엔드 계약 배포 전까지 발행하지 않는다.
