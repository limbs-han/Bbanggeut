# 프레임 타임라인 구조 비교와 텍스트 탭 멈춤 원인 보고

작성일: 2026-08-02 (KST)
작성 배경: "텍스트 들어가면 멈춘다. 구조가 문제 아니냐. 다른 편집 툴의
프레임 단위 구조를 조사해서 지금 구조와 비교하라"는 요청.

## 1. 결론 요약

1. **멈춤은 타임라인 구조 문제가 아니었다.** 도구 패널 제목 줄의
   `SizedBox(height: N, child: FilledButton(...))` 조합이 원인이었고,
   이 조합을 제거해 실기기에서 멈춤 없이 동작함을 확인했다(§2).
2. 프레임 타임라인 구조 자체는 상용·오픈소스 편집기들이 쓰는 패턴과
   대체로 같다(§3). 구조를 갈아엎을 근거는 찾지 못했다.
3. 개선 여지는 스크럽 중 seek 정책, 긴 영상 고배율 줌에서의 썸네일
   가상화 두 가지다(§4).

## 2. 텍스트 탭 멈춤의 실제 원인

### 증상 (S24+ 실기기, 2026-08-02 재현)

- 텍스트 탭을 누르면 도구 패널·하단 네비가 그려지지 않고 입력이 죽은
  것처럼 보인다. 100% 재현.
- 앱이 죽은 것이 아니다: Dart isolate 정상(idle), 위젯 트리 정상
  (VM service `debugDumpApp`으로 확인), 예외 출력 없음, 스레드 전부 유휴.
- 렌더 트리를 뜨면 패널·네비 노드가 `NEEDS-LAYOUT NEEDS-PAINT`인 채
  영원히 방치된다. 보이지 않는 네비 위치를 누르면(다른 탭 전환) 그대로
  복구된다 — 즉 "그 탭의 프레임 하나"만 미완료로 남는 버그다.

### 원인 격리 과정

- Impeller를 끄고(Skia) 같은 증상 → 렌더러 무관.
- 패널 내용을 비우면 정상 → 내용물 문제로 확정.
- 이분 탐색 결과: `SizedBox(height: 34, child: FilledButton(...))`가
  있으면 멈추고, SizedBox 래퍼를 빼고 `minimumSize` 스타일로 크기를
  정하면 정상. 버튼 종류(FilledButton vs .icon)는 무관.
- 지난 세션의 "구간 줌 탭 빈 패널·입력 정지"(구 `_ZoomPanel`)도
  `SizedBox(height: 32, child: FilledButton.icon(...))`을 갖고 있었다.
  당시 패널 교체로 우연히 나은 것이며 같은 원인이었다.

### 조치 (커밋 a8be9e0, a99389a)

- `_TextPanel`·`_AiCaptionPanel`의 고정 높이 SizedBox 래퍼 제거.
- 재발 방지: 같은 조합을 가진 죽은 코드(구 `_ZoomPanel` 등) 삭제.
- 실기기 확인: 텍스트 탭 진입 → 추가 → 영상 위 입력 → 키보드 위 꾸밈 줄
  → 타이핑 반영 → 완료 → 손잡이 조작까지 전 구간 정상.
- 미해결: 왜 이 조합이 프레임 레이아웃을 미완료로 남기는지는 Flutter
  3.44.6 프레임워크 내부 문제로 보인다. 별도 최소 재현을 만들어
  업스트림에 보고할 가치가 있다(예외도 로그도 없어 앱에서 더 파기 어렵다).

## 3. 프레임 단위 타임라인: 다른 편집기 vs 현재 구조

출처는 공개 자료 기준이다. CapCut 등 상용 앱 내부 구현의 1차 자료는
없어서, SDK 문서·구현 공개 사례로 비교한다.

### 3.1 스크럽 방식 — 고정 플레이헤드

| | 업계 | 현재 구현 |
|---|---|---|
| 방식 | 고정 플레이헤드 아래로 필름이 움직임 (IMG.LY CE.SDK 설계 노트, RN+FFmpeg 구현 사례) | 동일 (`TrimRangeBar`) |
| 이유 | 트리밍 중 타임라인이 스크롤되면 편집 중인 클립이 움직여 버림 | 동일한 이유로 채택됨 |
| 스냅 | 인접 경계·플레이헤드에 스냅 + 햅틱 (IMG.LY) | 처음·끝·재생 위치 12px 스냅 + 햅틱 |

구조적으로 표준 패턴과 같다.

### 3.2 썸네일 스트립

| | 업계 사례 | 현재 구현 |
|---|---|---|
| 추출 밀도 | RN 구현: 1초당 1장 일괄 추출 | 4장 먼저 → 약 4초당 1장, 24~72장 상한 |
| 캐시 | 스프라이트/Blob, 수 MB 수준 | 지점별 파일, 기약분수 이름으로 줌 간 재사용 |
| 가상화 | 대부분 없음(전체 렌더) | 없음 |
| 줌 대응 | 줌 레벨별 재추출 필요성만 언급된 자료 존재, 표준 해법 없음 | 8배 줌에서 72장 상한 |

밀도·캐시는 업계 사례보다 오히려 정교하다. 가상화가 없는 것도 공개
사례들과 같다.

### 3.3 프레임 정확도

- 업계: UI는 픽셀→시간 변환만 하고, 정확도는 플레이어 seek 모드가 정한다.
  ExoPlayer는 스크럽 중 `CLOSEST_SYNC`(키프레임, 빠름), 손 뗄 때
  `EXACT`(정확, 느림)가 통용 패턴.
- 현재: 30fps 33/34ms 보정으로 프레임 경계를 맞추고 `video_player`의
  `seekTo`를 쓴다. video_player 플러그인은 seek 모드를 노출하지 않아
  항상 정확 seek이다 — 스크럽 반응성에서 손해를 볼 수 있는 지점(§4).

### 3.4 텍스트 입력 중 처리

- 업계: iMovie도 뷰어 위 in-place 입력이며 정지 프레임 위에서 편집한다.
  타이밍 조절은 타임라인에서 분리. Banuba/IMG.LY SDK도 캔버스 직접 조작.
- 현재: 동일(입력 시 재생 정지, 영상 위 제자리 입력, 키보드 위 꾸밈 줄).
- Flutter 특화 주의점(조사): 키보드가 올라올 때 video_player의 Texture
  **크기가 바뀌지 않게** 하는 것이 핵심. 현재 구조는 VideoPlayer를
  원본 픽셀 크기 SizedBox + FittedBox(transform 스케일)로 감싸므로
  Texture 논리 크기가 고정된다 — 이 위험은 이미 피하고 있다.

## 4. 남은 개선 후보 (우선순위 순)

1. **스크럽 중 seek 모드**: 스크럽 중 키프레임 seek, 손 뗄 때 정확
   seek. video_player가 API를 노출하지 않으므로 자체 MethodChannel로
   ExoPlayer `SeekParameters`를 만지거나 플러그인 포크가 필요하다.
   스크럽 반응성 체감이 목표. 실측(프레임 표시 지연) 후 판단.
2. **썸네일 가상화**: 8배 줌 + 긴 영상에서 72장 상한이 모자라면 보이는
   구간만 추출·렌더하는 방식으로. 현재 상한이 충분한지 실사용 확인 먼저.
3. **업스트림 보고**: SizedBox+FilledButton 프레임 미완료 버그의 최소
   재현 프로젝트. 앱과 무관하게 재현되면 flutter/flutter에 이슈.
