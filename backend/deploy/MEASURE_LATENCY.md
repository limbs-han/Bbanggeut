# 라이브 지연 측정 절차 (S15P11E201-89)

LL-HLS 전환(87) 전후를 같은 방법으로 재서 비교하기 위한 문서다. **전환 전 baseline을
먼저 기록**하지 않으면 전환 후 숫자가 좋아졌는지 판단할 근거가 없다.

지연은 두 부분으로 나눠 잰다.

| 구간 | 측정 방법 | 자동화 |
|---|---|---|
| 서버 구간 (구간 노출 지연 + 플레이리스트 깊이) | `measure-hls-latency.sh` | 가능 |
| 전체 glass-to-glass (카메라 앞 → 화면 표시) | 아래 수동 절차 | 불가 (물리 측정) |

---

## 1. 서버 구간 — 자동

기기가 실제로 송출 중이어야 한다. 앱에서 라이브 시청을 시작해 세션을 만든 뒤,
그 재생 URL을 그대로 넘긴다.

```bash
./measure-hls-latency.sh 'https://i15e201.p.ssafy.io/live/<streamId>/index.m3u8?token=<t>' 90
```

재생 토큰 TTL이 30초라 90초 측정 중에 만료된다. 두 가지 중 하나를 쓴다.

- EC2에 SSH로 들어가 MediaMTX HLS 포트(loopback 8888)를 직접 겨냥한다. 이 경로는
  Nginx 인증을 거치지 않으므로 토큰이 필요 없다.
  ```bash
  ./measure-hls-latency.sh 'http://127.0.0.1:8888/<streamId>/index.m3u8' 90
  ```
- 또는 30초 이하로 짧게 여러 번 돌린다.

**읽는 법**

- `구간 노출 지연` — 인코딩 시각부터 플레이리스트에 실릴 때까지. 일반 HLS는 세그먼트가
  다 만들어져야 실리므로 세그먼트 길이(현재 2초)에 근접한 값이 나온다. **LL-HLS 전환이
  직접 줄이려는 값이 이것이다.**
- `플레이리스트 총 길이` — 플레이어가 라이브 엣지에서 뒤로 떨어져 시작하는 거리의 하한.
  네이티브 플레이어는 보통 여기서 3세그먼트를 더 버퍼링한다.

이 둘의 합이 **서버가 만드는 지연의 하한**이고, 전체 지연은 항상 이보다 크다.

## 2. 전체 glass-to-glass — 수동

물리 측정이라 사람이 직접 해야 한다.

**준비물**: 밀리초까지 표시되는 스톱워치(다른 폰이나 모니터 전체화면), 사진 찍을 세 번째 기기.

**절차**

1. 스톱워치를 켜서 홈캠(젯슨 카메라)이 화면을 정면으로 비추게 둔다.
2. 앱에서 그 홈캠의 라이브 시청을 시작하고, 재생이 안정될 때까지 20초쯤 기다린다.
3. **스톱워치 실물과 앱 화면이 한 프레임에 같이 들어오게** 사진을 찍는다.
4. 사진에서 두 시각을 읽는다. `실물 시각 − 앱에 표시된 시각` = glass-to-glass 지연.
5. 최소 10회 반복한다. 값이 튀므로 중앙값과 최댓값을 같이 남긴다.

**주의**

- 재생 시작 직후는 버퍼가 덜 찬 상태라 값이 낮게 나온다. 반드시 안정화 후 측정한다.
- 측정 폰의 네트워크(Wi-Fi/LTE)를 기록한다. 조건이 다르면 비교가 무의미하다.
- 같은 조건에서 전환 전후를 재야 한다.

## 3.5 젯슨 인코더 실측 사실 (2026-07-28 코드 확인)

지연 계산의 전제라 정확히 남긴다. **운영 젯슨의 라이브 경로는 재인코딩을 하지 않는다.**

```text
media-source.sh (카메라 → 1회 인코딩 → UDP 4갈래 tee)
  -c:v libx264 -preset ultrafast -tune zerolatency
  -g $CAMERA_FPS -keyint_min $CAMERA_FPS   ← CAMERA_FPS=30 이므로 GOP 1초
  -bf 0 -sc_threshold 0
        ↓ udp://127.0.0.1:23002
stream.py (앱 시청 중에만 실행)
  FFMPEG_VIDEO_ARGS='["-c:v","copy"]'      ← 재인코딩 없음, GOP 그대로 통과
        ↓ RTSPS
EC2 MediaMTX
```

따라서:

- **키프레임 간격은 이미 1초**다. `hlsSegmentDuration`을 1s로 내리는 데 기기 변경이 필요 없다.
- `wj_device_agent/config.py`의 `-g str(fps*2)`(2초)는 **운영에서 쓰이지 않는다** — `-c:v copy`가 덮어쓴다. 이 값만 보고 GOP를 2초로 판단하면 안 된다.
- `homecam-publisher.sh`의 GOP 2초는 **라즈베리파이 프로토타입 경로**이며 젯슨 라이브와 무관하다.
- 세그먼트를 1초 밑으로 더 내리려면 그때는 젯슨 `CAMERA_FPS`/GOP를 함께 낮춰야 한다.

`backend/infra/mediamtx/mediamtx.yml`(로컬 개발용)은 2s로 남겨 뒀다. 데모 소스가
`-c copy`로 재생하는 기성 MP4라 GOP를 알 수 없어 1s로 자를 수 있다는 보장이 없다.

## 4. 측정 전에 알아둘 제약

- **앱 플레이어 버퍼는 현재 조절할 수 없다.** `frontend/lib/ui/live_screen.dart`는
  `video_player` 패키지의 `VideoPlayerController.networkUrl`을 그대로 쓰는데, 이 패키지는
  버퍼 크기·라이브 엣지 추종 설정을 노출하지 않는다. 측정 결과 플레이어 버퍼가 지연의
  큰 비중이면 87(서버 설정)만으로는 목표에 못 미치고, 플레이어 계층 교체
  (`media_kit`, `better_player` 등) 검토가 별도로 필요하다.
- **MediaMTX 이미지가 `bluenviron/mediamtx:1` 부동 태그다.** 재배포 시점에 따라 1.x 안에서
  버전이 달라질 수 있다. 측정값을 기록할 때 실제 버전을 같이 남긴다.
  ```bash
  docker inspect --format '{{index .Config.Labels "org.opencontainers.image.version"}}' william-james-mediamtx-1
  ```
