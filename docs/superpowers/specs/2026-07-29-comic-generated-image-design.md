# 4컷 만화 설계 — 전사문으로 그림을 생성한다

작성 2026-07-29 · 브랜치 `feat/frontend/comic` (base `develop/frontend`)

## 문제

영상에서 4컷 만화를 만든다. 영상 프레임을 쓰지 않고 **생성 AI가 그린 그림**을 쓴다.

## 이미 있는 것

`develop/frontend`에 온디바이스 자막(FN-A39)이 들어와 있다. 그래서 만화에 필요한 재료
절반이 준비돼 있다.

| 있는 것 | 4컷에서 쓰는 방식 |
|---|---|
| `features/stt/transcript_store.dart` | `videoId`로 캐시된 전사문을 **그대로 읽는다.** 다시 전사하지 않는다 |
| `features/stt/caption_line.dart` | 자막 줄 자료형(`startMs`, `endMs`, `text`) |
| 영상 다운로드 (`API-32`) | 편집 화면과 같은 경로 |

## 결정과 근거

### 그림은 생성 AI로 만든다

영상 프레임 4장을 뽑는 방식(예전 `ai_comic` 설계)을 버렸다. 프레임은 만화가 아니라
사진 4장이다. 그리고 프레임을 서버로 보내지 않으므로 사생활 보호에도 유리하다.

**전사문(글)만 서버로 보낸다.** 영상·오디오·프레임은 기기를 떠나지 않는다.

### 키는 서버가 들고 있다

이미지 생성 API 키를 앱에 넣으면 APK를 뜯어 가져갈 수 있다. 그러면 남의 계정으로
아무나 이미지를 생성한다. 앱은 **우리 서버**에 요청하고, 서버가 키로 대신 부른다.

**이 기능은 두 역할에 걸쳐 있다.** 서버 통로는 `feat/backend/*` 브랜치에서 따로 만든다.
이 문서는 **앱 쪽과 두 쪽이 주고받을 API 계약**을 정한다.

### API를 두 단계로 나눈다

구성(어떤 대사를 어느 컷에, 각 컷의 장면)을 먼저 받아 사용자가 고친 뒤에 그림을
만든다. 이미지 생성은 호출마다 돈이 들어서, 엉뚱한 구성에 돈을 쓰지 않으려는 것이다.

### 그림에 글자도 말풍선도 넣지 않는다

대사는 **영화 자막처럼** 각 컷 아래쪽에 앱이 얹는다.

말풍선까지 금지하는 이유는 두 가지다. 첫째, 앱이 얹는 자막과 스타일이 섞인다. 둘째,
**말풍선이라는 자리가 있으면 모델이 거기에 글자를 넣으려 한다** — PC 시험에서 글자
금지를 명시했는데도 3컷에 "CRASH"가 박혔다. 자리를 없애면 글자가 들어갈 구실이 줄어든다.

## API 계약

두 엔드포인트. 기존 `/api/<자원>` 관례를 따른다.

### 4컷 구성 받기

```
POST /api/videos/{videoId}/comic/script

요청
{
  "lines": [
    { "startMs": 1500, "text": "그거 만지지 마" },
    { "startMs": 5200, "text": "안 만졌는데요" }
  ]
}

응답 200
{
  "cuts": [
    {
      "beat": "빌드업",
      "scene": "아이가 탁자 위 물건에 손을 뻗고, 엄마가 말리는 순간",
      "dialogue": "그거 만지지 마"
    },
    { "beat": "전개", "scene": "...", "dialogue": "안 만졌는데요" },
    { "beat": "절정", "scene": "...", "dialogue": null },
    { "beat": "여운", "scene": "...", "dialogue": "안 만졌다면서" }
  ]
}
```

- `cuts`는 **항상 4개**다. 그보다 적거나 많으면 앱이 오류로 다룬다.
- `dialogue`는 null일 수 있다 — 대사 없이 상황만 있는 컷이다.
- `scene`은 이미지 프롬프트에 들어갈 장면 묘사다. 사용자에게도 보여준다.

### 그림 받기

```
POST /api/videos/{videoId}/comic/image

요청
{
  "cuts": [ ...위와 같은 4개 (사용자가 고친 것)... ],
  "style": "webtoon"
}

응답 200
{ "image": "<base64 PNG>" }
```

- `style`은 `webtoon` / `watercolor` / `crayon` 중 하나. 기본 `webtoon`.
- 이미지는 **정사각형 한 장에 2x2 격자**다. 읽는 순서는 왼쪽 위 → 오른쪽 위 →
  왼쪽 아래 → 오른쪽 아래.
- **왜 base64인가**: 만화를 서버에 보관하지 않는다. 앱이 받아 갤러리에 저장하고
  끝낸다. "내가 만든 만화 목록"이 필요해지면 그때 MinIO 저장으로 바꾼다.

### 서버가 지켜야 할 것

앱 쪽에서는 강제할 수 없으니 백엔드 브랜치에 그대로 옮겨 적는다.

1. **키는 서버에만 둔다.** 응답에 키를 절대 담지 않는다.
2. **사용자별 호출 횟수를 제한한다.** 이미지 생성은 돈이 든다.
3. **이미지 프롬프트에 다음을 넣는다** (PC 시험으로 다듬은 것):
   - 그림 안에 글자를 넣지 마라 — 대사·효과음·의성어·간판·시계 숫자 모두 금지
   - **말풍선도 그리지 마라** — 빈 말풍선도 안 된다
   - 대사는 인물의 표정과 몸짓으로만 표현하라
   - 소리나 충격은 집중선·움직임선·먼지처럼 **선과 형태로만** 나타내라
   - 카메라 화면처럼 보이게 하지 마라 — 녹화 표시, 렌즈 테두리, 타임스탬프, UI 금지
   - 네 컷의 인물은 같은 사람으로 보이게 머리색·의상·체형을 유지하라
   - 특정 실존 인물을 닮게 하지 마라
   - 정사각형 한 장에 2x2 격자, 컷 사이에 흰 여백과 검은 테두리
4. **장면 묘사에 소리를 언급하지 않는다.** "큰 소리가 났다"고 쓰면 모델이 의성어를
   그린다 — 시험에서 확인했다. "물건이 바닥에 흩어져 있다"처럼 눈에 보이는 것만 쓴다.

## 앱 구조

```
features/comic/
  comic_gateway.dart      서버 통로 — 인터페이스 + Http + Fake
  comic_script.dart       ComicCut 자료형과 직렬화
  comic_controller.dart   상태 (전사문 → 구성 → 이미지 → 저장)
  comic_screen.dart       화면
  panel_subtitle.dart     컷 아래 자막 띠 위젯
```

### 가짜 게이트웨이가 기본값이다

`COMIC_GATEWAY` 실행 인자가 없으면 `FakeComicGateway`가 붙는다. 고정 구성 4개와
4칸으로 나뉜 그림을 돌려주므로, **서버 없이 화면 전부를 만들고 테스트할 수 있다.**
자막에서 `FakeCaptions`를 쓴 것과 같은 방식이다.

```dart
const comicGateway = String.fromEnvironment('COMIC_GATEWAY');
// 비어 있으면 Fake, 있으면 Http
```

## 화면 흐름

영상 상세의 **[4컷 만화 만들기]** 버튼에서 들어간다. 영상 상태가 `READY`가 아니면
버튼을 누를 수 없다 — 클립을 못 내려받으면 전사도 없다.

**버튼은 `ui/content_video_detail_screen.dart`에 넣는다.** `ui/video_detail_screen.dart`의
`VideoDetailScreen`은 `ContentVideoDetailScreen`으로 넘기는 껍데기이고, 같은 파일의
`_LegacyVideoDetailScreen`은 **아무도 부르지 않는 죽은 코드**다. 거기에 넣으면 빌드는
되고 버튼은 화면에 안 보인다 — 예전에 실제로 그렇게 넣었다가 발견했다.

```
① 전사문 확인   TranscriptStore에서 읽는다
                없으면 "대사를 먼저 알아들어야 해요" + 편집 화면으로 안내
② 구성 받기     서버에 전사문 → 4컷 목록을 보여준다 (beat·scene·dialogue)
③ 고치기        컷마다 대사를 눌러 고친다. 지울 수도 있다(대사 없는 컷)
④ 그림 만들기   버튼을 누르면 이미지를 받는다. 도는 동안 진행 표시
⑤ 자막 얹기     그림 위 각 컷 아래쪽에 "- 대사" 형태로 얹는다
⑥ 저장          화면을 PNG로 떠서 공유 시트로 갤러리에 저장
```

### 자막을 얹는 방식

이미지를 2x2로 나눠 각 칸의 아래쪽에 얹는다. 컷 번호와 칸의 대응은 읽는 순서와 같다.

| 컷 | 위치 |
|---|---|
| 0 | 왼쪽 위 |
| 1 | 오른쪽 위 |
| 2 | 왼쪽 아래 |
| 3 | 오른쪽 아래 |

- 어두운 반투명 띠 + 흰 글자. 영화 자막과 같은 모양이다.
- `- ` 접두어를 붙인다 — 영화 자막에서 화자가 바뀜을 나타내는 관례다.
- `dialogue`가 null이거나 빈 컷에는 띠를 그리지 않는다.
- 위치를 사용자가 옮기지 않는다. 자막은 자리가 정해져 있는 것이 읽기 쉽다.

### 저장

`RepaintBoundary`로 화면을 떠서 PNG로 만들고 공유 시트로 넘긴다. 예전 만화 편집기가
쓴 방식과 같고 새 의존성이 없다. 앱 저장소에 따로 보관하지 않는다.

## 실패 처리

어느 단계가 막혀도 사용자가 다음으로 갈 수 있어야 한다.

| 실패 | 결과 |
|---|---|
| 전사문 없음 | "대사를 먼저 알아들어야 해요" + 편집 화면 안내. 만화를 만들 수 없다 |
| 구성 요청 실패 | 사유와 [다시 시도] 버튼. 전사문은 그대로 있다 |
| 구성이 4개가 아님 | 오류로 다룬다. 서버 계약 위반이므로 사유를 그대로 보여준다 |
| 이미지 요청 실패 | 구성은 화면에 남아 있고 [다시 만들기]로 재시도. 고친 대사를 잃지 않는다 |
| 그림에 글자가 섞여 나옴 | 막을 수 없다(시험에서 확인). 사용자가 보고 [다시 만들기]를 누른다 |
| 격자가 2x2가 아니게 나옴 | 자막 위치가 어긋난다. 사용자가 보고 다시 만든다 |
| 저장 실패 | 만화는 화면에 남아 있고 다시 저장할 수 있다 |

## 예전 `ai_comic`에서 가져올 것과 버릴 것

**패키지 전체를 버린다.** `ai_comic/`은 프레임 기반 파이프라인과 포트 12개로 짜여
있어 생성 이미지 방식에 맞지 않는다. 프레임 추출·VAD·STT 어댑터를 걷어내면 남는 것이
"전사문 → 서버 → 이미지 → 자막"이고, 그건 새로 짜는 편이 짧다.

| 버림 | 이유 |
|---|---|
| `ai_comic/` 패키지 (파이프라인·포트·도메인·LLM) | 프레임 기반 설계 |
| `native_frame_extractor`, `frame_analysis` | 프레임을 안 쓴다 |
| `speech_analysis`, `audio_analysis`, `android_media`, `ffmpeg_audio`, `rms_vad_classifier`, `capturing_stt` | `features/stt`에 이미 있다 |
| `app_consent_gate`, `app_scratch_cleaner` | 임시 파일과 동의 흐름이 단순해져 필요 없다 |

| 가져옴 | 어디서 |
|---|---|
| 이미지 프롬프트 (2x2, 글자 금지, 인물 일관성, 카메라 UI 금지) | `comic_image_test.py` — PC 시험으로 다듬은 것. **서버 쪽에 옮겨 적는다** |
| 4컷 구성 규칙 (기·승·전·결, 대사 인용) | `ai_comic/prompts/caption_system_prompt.md` — **서버 쪽으로** |
| 화면을 떠서 저장하는 방식 | 예전 `comic_editor_screen`의 `RepaintBoundary` 사용 |

## 하지 않는 것 (필요해지면 그때)

- 만화를 서버나 앱에 보관하기 — 갤러리 저장으로 끝낸다
- 화풍 고르기 UI — 요청에는 `style`이 있지만 화면에는 노출하지 않고 `webtoon` 고정
- 자막 위치·글꼴·색 조절
- 컷 수를 4개 외로 바꾸기
- 컷 하나만 다시 그리기 — 격자 한 장이라 부분 재생성이 안 된다
- 전사문 없이 사용자가 대사를 직접 써서 만화 만들기

## 확인 방법

- `ComicGateway` 계약: 요청 본문 모양과 응답 파싱 (가짜 서버로)
- `cuts`가 4개가 아닐 때 오류가 된다
- `ComicController` 상태 전이: 전사문 없음 / 구성 중 / 구성 완료 / 이미지 중 / 완료 / 실패
- 대사를 고치면 구성에 반영되고, 이미지를 다시 만들 때 고친 것이 넘어간다
- 화면: 컷 4개가 2x2로 배치되고, 대사 있는 칸에만 자막 띠가 있다
- 실기기: 저장한 PNG에 자막이 함께 들어 있다

## 미확정과 천장

- **격자 정렬을 믿고 자막을 얹는다.** 모델이 2x2를 정확히 그려 준다는 보장이 없다.
  PC 시험에서는 일관됐지만 어긋나면 자막 위치가 틀어진다. 사용자가 보고 다시 만드는
  것 외에 대응이 없다.
- **서버 통로가 없으면 진짜 그림이 안 나온다.** 가짜 게이트웨이로 화면과 흐름은
  완성할 수 있지만, 끝까지 확인하려면 백엔드 작업이 필요하다.
- **이미지 호출 비용.** 호출 제한을 서버가 걸어야 한다. 앱은 막을 수 없다.
- 전사문이 부실하면(자막 기능의 실측: 2분 영상에 143자) 구성 품질도 그만큼이다.
